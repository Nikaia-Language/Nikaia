## 1. Question

ADR-265 cut the prover into a frontend, a logic and a solver, and fixed what a
query and an answer are. The solver behind it is Fourier-Motzkin with integer
tightening and case splitting on demand: right for nearly every query the
compiler asks (D1 names the ones it misses), and exponential in the number of variables and in the disjunctions a
proof needs. The goal is a solver that **wins the QF_LIA division of SMT-LIB
against z3 and cvc5 and then widens**, written so that it can become Nikaia,
and parallel where Nikaia is strong.

**Which architecture is that solver built on, and what is decided before the
first algorithm** — so that each later engine is a part that fits, and not a
rewrite?

Two conditions are fixed and not weighed here: ADR-265 D4 holds everywhere
(deterministic, a budget counted in work, never time), and **the checker stays
small**: every strategy, engine and theory produces the same proof format.

## 2. How others do it

| Solver | Its answer | What it costs there | Source |
| :--- | :--- | :--- | :--- |
| **z3** | CDCL(T); a general simplex over rationals with bound propagation for arithmetic (Dutertre and de Moura), branch-and-bound, Gomory and GCD cuts for integers; model-based theory combination; tactics composed into strategies, some with time limits; rationals with a small-integer fast path | Answers can depend on the time limits of tactics; parallel mode is a portfolio whose result depends on timing; proofs exist but are not the default and are not small | from memory, not checked |
| **cvc5** | CDCL(T); simplex with a "theory of linear arithmetic" that switches between several solvers; theory combination by a care graph; proofs in Alethe, LFSC and its own format, checked by external checkers | A proof checker for every rule it can emit is large; proof production costs a measurable factor | from memory, not checked |
| **Yices 2** | CDCL(T) with a fast simplex for linear arithmetic, MCSAT for non-linear arithmetic | No proofs; MCSAT is a second search architecture | from memory, not checked |
| **MathSAT 5, SMTInterpol** | CDCL(T); for integers branch-and-cut, "cuts from proofs" (Dillig, Dillig and Aiken, CAV 2009) and Diophantine equality handling | Interpolation drives the design; SMTInterpol is on the JVM | from memory, not checked |
| **Kissat, CaDiCaL** (SAT) | Clause arena with 32-bit references, blocking literals in watch lists, binary clauses held apart, inprocessing, mode switching (focused / stable) at conflict counts; LRAT proofs from CaDiCaL | Not an SMT solver; the techniques are the floor for the Boolean core | from memory, not checked |
| **Mallob, Painless** (parallel SAT) | Clause sharing between many solver instances, portfolio and divide-and-conquer | Results and run time depend on timing; not reproducible by construction | from memory, not checked |
| **Local search for LIA** (Cai et al., CAV 2022) | Critical moves over integer assignments find models fast on satisfiable instances | Proves nothing unsat; complements CDCL(T) | from memory, not checked |

**What does not transfer:**

* **Time as a limit.** z3's tactics and every portfolio race decide by the
  clock. ADR-265 D4 forbids it; everything below counts work.
* **GMP and other libraries.** `nikaia-logic` has no dependencies
  (ADR-265 D1): the big numbers are its own.
* **A proof format per feature.** cvc5 shows what a proof system that grew
  with the solver costs a checker. Here the format is fixed first (D4), and a
  technique that cannot be written in it is not used, or is used only to
  *find* what is then derived in it.
* **The tactics language.** A strategy is a component with features, rules and
  parameters (D7), not a scripting layer users write.

## 3. Options, weighed

The ten points are decided in §4, each with its rejected alternatives. Here
the one choice that frames the others: **the search architecture.**

### Option A — keep Fourier-Motzkin with case splitting, and tune it

What is built today. Exact, certificates are Farkas combinations by
construction. Its elimination grows doubly exponentially in the variables; the
measurement (§4 D1) shows the cost already on twelve.

### Option B — CDCL(T) with a general simplex, theories behind one interface

The structure every leading SMT solver shares. The Boolean search learns from
conflicts; the simplex is incremental and backtracks by restoring bounds, not
by recomputing; a conflict's explanation is a row, which is a Farkas
certificate.

### Option C — MCSAT as the skeleton

Model-constructing search assigns theory variables as decisions. Strong for
non-linear arithmetic; for linear integer arithmetic it does not beat B, and
its proofs are less settled.

### Option D — bind z3 or cvc5 and keep only a checker

Fast today. A dependency (ADR-265 D1), a time-based answer (D4), and no road
to a solver in Nikaia.

### Weighed

| | D1 the special case pays | D2 the compiler works | D3 no cost for the common case | D4 consistent | If it is wrong |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **A** | No: one hard query with many variables costs the build | Yes | Yes for tiny queries | Yes | The hard queries stay *unknown*: a check at run time, not a wrong answer |
| **B** | Yes: work goes where conflicts are | Yes | Only with a fast path (D5): a CDCL(T) set-up costs more than a 2-atom query | Yes: one proof format | A rewrite of the engine, not of the interfaces |
| **C** | Yes | Yes | Same as B | Two architectures if B is still needed for proofs | A second skeleton beside B |
| **D** | Yes | Yes | No: about 1.5 ms per query through z3's API, several hundred times today's solver | No: time decides | Undoing a dependency |

**B is chosen.** A lost on D1, C on D4 for linear arithmetic (kept for
non-linear arithmetic, §6), D on D3 and D4.

## 4. Decision

### D1 — The workload is measured first, and its numbers decide.

The queries are those the prover asks while the compiler's test suite runs,
dumped as SMT-LIB and replayed in-process against an instrumented copy of the
solver; the stress set adds four families the suite does not reach (guards,
unrelated disjunctions, `+1 or +2` paths, parity). Method, machine and every
table: [`docs/solver-workload.md`](../../solver-workload.md).

Two sets: the **353 recorded queries** every solver change has been replayed
against since 0.0.357, and **all 1 697 queries** the compiler's test suite asks
at 0.0.368.

| per query | 353: median | p90 | p99 | max | 1 697: median | p90 | p99 | max |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| variables | 1 | 2 | 3 | 4 | 1 | 3 | 3 | 4 |
| atoms `lin <= 0` | 2 | 8 | 10 | 12 | 2 | 5 | 8 | 12 |
| disjunctions | 0 | 1 | 3 | 3 | 0 | 1 | 2 | 3 |
| branches searched | 1 | 3 | 5 | 5 | 1 | 2 | 3 | 5 |
| solve time, µs | 2.8 | 13.5 | 22.4 | 34.7 | 2.6 | 8.3 | 15.5 | 34.0 |

* **Non-zeros per atom: 1.01 and 1.05 on average.** 83 % (353) and 68 %
  (1 697) of the queries hold only interval atoms (one variable); 89 % and
  83 % only interval or difference atoms (`x - y`). Every coefficient is 1 or
  2. **No query has more than four variables.**
* **Where the time goes** (summed: 1.9 ms over the 353, 7.1 ms over the
  1 697): reading the formula into atoms 26 % and 28 %, Fourier-Motzkin 60 %
  and 58 %, the search around it 14 % and 13 %; checking a proved query's
  certificate adds 25 % and 17 %.
* **Inside a compile** the prover - frontend and solver - takes 1 % of
  `nikaia lower` on `examples/calc` and 6 % on `examples/inventory`, before
  `rustc` has run at all.
* **What is missed:** 92 of the 1 697 are *unknown*, and they are four shapes,
  all an equality with the coefficient 2 (`blank = 2·n`, `blank = 1`). 56 of
  them are provable: Fourier-Motzkin eliminates `n` over the rationals and
  loses the parity of `2·n`. The other 36 are satisfiable, and
  back-substitution lands on `x = 1/2`. z3 agrees with every answer that was
  given.
* **Repetition:** 30 of the 353 and 105 of the 1 697 are distinct up to the
  names of their variables.
* **The compiler's own Nikaia code asks nothing:** its `.nika` tools contain no
  `assert` today.
* **For scale:** z3 through its Python API spends about 1.5 ms on a trivial
  query with a fresh solver and 0.14 ms with one reused; cvc5 more. On the
  compiler's queries the comparison is one of set-up costs. On parity with
  twelve variables z3 answers in 12 ms, cvc5 in 97 ms, and this solver runs
  out of budget after 12 288 eliminations.

**What the numbers decide:** the compiler's workload is *tiny and almost all
intervals*, so it decides the **fast paths** and the rule that the common case
pays nothing (D5, D9); it does not decide the **core**, which is sized by
SMT-LIB (D10). Two of the owner's build steps are weighed against them in
D12.

**Rejected:** designing from the benchmark literature alone (the compiler's
queries would pay a general engine's set-up on every one of them); designing
from the compiler's queries alone (four variables decide nothing about a core
that has to win QF_LIA).

### D2 — Variables are `u32`; rows are sparse; small problems run dense.

A variable, a term, a clause and a literal are `u32` indices into arenas
(ADR-265 D2). A row - an atom, a tableau row, a derived bound - is **sparse**:
two parallel arrays, column indices (`u32`, ascending) and coefficients
(D3's numbers). A query whose variables fit one vector register - **eight or
fewer; every one of the 1 697 the compiler asked has at most four** - runs on
a **dense kernel**
of fixed width instead, chosen by the strategy layer (D7), not by the engine.

**Why sparse is the representation:** the compiler's atoms hold 1.05
non-zeros each; the stress set's chains hold two of 33 variables (6 %);
SMT-LIB's linear problems are sparse by construction (from memory, not
checked: tableau densities of a few per cent are typical). A dense row of a
problem with ten thousand variables would be all zeros and all bandwidth.

**Why a dense kernel at all:** below eight variables the bookkeeping of a
sparse row (indices, merge on combination) costs more than the arithmetic,
and eight `i64` lanes are one AVX-512 register or two AVX2 ones (D9).

**Rejected:** dense everywhere (fails every large problem); `BTreeMap<String,
i64>` as today (each combination compares strings; it is what makes
Fourier-Motzkin's 60 % above); a hash map per row (iteration order would have
to be fixed by hand for D4, and it is slower than a sorted merge at these
sizes).

### D3 — Numbers: an `i64` fast path, and a deterministic fall-back to big integers and fractions.

* **Coefficients** of a row are integers. A tableau row over the rationals is
  stored **integral with one denominator per row** (`Σ aⱼxⱼ / d`), so the inner
  loop is integer multiply-add; the row is reduced by its gcd after a pivot.
* **The fast path** holds a coefficient in an `i64` while it fits in 32 bits,
  so one product fits 63 bits and one combination `a·x + b·y` cannot overflow;
  the result is checked against the 32-bit range, and a coefficient that
  leaves it **promotes** that one number to a big integer. Promotion is a
  function of the values, so it happens at the same operation on every run
  and every machine: D4 holds without a rule of its own.
* **Big integers** are the crate's own: `u32` limbs with `u64` products, which
  Nikaia can express (ADR-252 keeps `i128` out). A number is a tagged word:
  small inline, or a `u32` reference into a big-number arena (D9). A
  52-bit-limb kernel using the multiply-add instructions of AVX-512 IFMA is a
  kernel behind the same type (ADR-009), not a second representation.
* **Values** of the simplex are rationals with the same fast path, extended by
  the infinitesimal `δ` for strict bounds (Dutertre and de Moura).
* **Unknown(Overflow) disappears** as an answer; it stays only as the reason a
  budget ran out when big numbers grow past the budget's limit on limbs (D4 of
  ADR-265: work, counted).

**Rejected:** `i64` only (ADR-265 D2 today: a proof lost to overflow is a
check at run time, acceptable for the compiler, not for SMT-LIB); `i128`
(ADR-252); floating point with exact repair (fast LP solvers do it, but every
answer and certificate must be exact anyway, and keeping IEEE results equal
across targets with fused multiply-add is a constraint on every kernel for a
gain the measurement has not shown); full rationals everywhere (a gcd per
operation in the inner loop).

### D4 — One proof format: Farkas, cutting planes with splits, and LRAT for clauses.

A *proved* answer's certificate is one **proof log**, append-only, that every
engine and strategy writes into. Its steps:

1. **Clause steps, LRAT-like.** An input clause; a learned clause with the
   ids of the clauses that derive it by reverse unit propagation, in order, so
   that checking is linear; deletion of a clause by id. DRAT without hints is
   rejected: checking it needs search.
2. **Theory lemmas for linear arithmetic.** A clause `¬a₁ ∨ … ∨ ¬aₖ` justified
   by a **Farkas combination** of the atoms' bounds: non-negative multipliers
   for inequalities, any sign for equalities, rational multipliers (written
   as integers over one common denominator), ending in `0 < 0` or `c <= 0`
   with `c > 0`; strict bounds carry their strictness.
3. **Integer rounding (Chvátal-Gomory).** A derived bound over **integer
   variables with integer coefficients** is divided by a positive integer and
   its constant rounded towards the integers - today's `Tighten`.
4. **A split.** The clause `L <= k ∨ L >= k + 1` for an integer form `L` with
   integer coefficients and an integer `k`: valid by itself, checked by
   looking at `L` and `k`. Branch-and-bound is a split and a resolution.
5. **An extension.** A fresh integer variable `q` defined by
   `0 <= L - m·q <= m - 1` for an integer form `L` and an integer `m > 0`:
   `q` is the floor of `L / m`, which exists for every value of `L`, so the
   definition cannot make a satisfiable problem unsatisfiable. SMT-LIB's
   `div` and `mod` by a constant are exactly this, and it is what keeps some
   proofs short: twelve numbers that are each `-1` or `1` never sum to `1`,
   which splits take 2¹² cases to show and which `q = ⌊(x + 1) / 2⌋` per
   number, a two-case lemma each (`x + 1 - 2q = 0`) and one rounding show in
   linear size.

**Which cuts are allowed:** every cut that is a Chvátal-Gomory derivation (a
combination and a rounding) - Gomory's fractional cuts, the GCD test on an
equality, Hermite-normal-form cuts on equality rows - and every **split cut**
(a cut valid on both sides of a split: Gomory mixed-integer, mixed-integer
rounding, lift-and-project, cuts from proofs), written as the split, one
derivation per side and the resolution. A heuristic may *find* a cut by any
means, floating point included; it is written as one of these, exactly, or it
is not used.

**Small means:** the checker replays, it never searches. Its rules are the
five above plus one per further theory (D6), each a replay; the checker for
linear integer arithmetic and clauses stays under **1 500 lines**, and a rule
that would push it past needs a record. Alethe (ADR-265 D6) stays an export:
each step above has an Alethe counterpart (`resolution`, `la_generic` with
integer strengthening), which is how the format is checked by a checker this
crate did not write.

**Rejected:** extension with arbitrary definitions (a definition that is
not satisfiable for every value would be unsound; the floor is the one form
needed and the one that is always satisfiable); Alethe as the internal format (a large rule set, ADR-265 D5);
a certificate per engine (one checker per engine is not small); no
certificate for cuts, trusting the cut generator (the most error-prone code
of an integer solver would be trusted).

### D5 — CDCL(T) is the skeleton from the start; fast paths keep the small queries free.

The search is a CDCL loop over Boolean literals - decisions, unit
propagation, conflict analysis to a first-UIP clause, backjumping, restarts,
clause-database reduction - and every theory sits behind **one interface**:

| call | what it does |
| :--- | :--- |
| `assert(lit)` | a literal became true at the current level; the theory takes its bound or equality, and may answer with a conflict at once (two bounds that cross) |
| `propagate()` | literals the theory implies cheaply (bound propagation), each explained later on demand |
| `check(final: bool, budget)` | consistency of what is asserted: *consistent*, a **conflict** (a clause and its certificate step), or **lemmas** to add (a split, a cut) |
| `explain(lit)` | the clause and certificate step behind a literal it propagated |
| `backtrack(level)` | forget what was asserted above `level`; the simplex keeps its basis and restores bounds |
| `model()` | values that satisfy what is asserted, checked by evaluation (ADR-265 D3) |
| `shared()` | the terms and equalities it shares with other theories (D6) |

The simplex is built against this interface from its first line: general
simplex with bounds on variables, one slack variable per distinct linear form
(atoms on the same form share it), pivoting by a deterministic rule with
Bland's rule as the fall-back that guarantees termination.

**Fast paths** are the same interface, cheaper: a query with no Boolean
choice skips the CDCL loop; **interval** atoms (68 % of the compiler's
queries hold nothing else) are decided by bounds on single variables;
**difference** atoms (a further 15 %) by negative-cycle detection, whose certificate is the cycle - a
Farkas sum with every multiplier one. Fourier-Motzkin stays as the
**cross-check** (every answer of the new engine is compared with it on
everything it can decide) and as an engine the strategy may pick for tiny
dense problems (D7). **No fast path allocates** for a query below the dense
width: the common case pays nothing for the skeleton (ADR-258 D3).

**Rejected:** CDCL as a later step (the simplex would be built against
Fourier-Motzkin's interface and rebuilt); offline DPLL - enumerate Boolean
models, ask the theory each (exponential in the disjunctions, as the case
splitting before 0.0.368 was); MCSAT as the skeleton (§3, C).

### D6 — Theories are combined by model-based theory combination over an e-graph.

The architecture takes further theories - equality with uninterpreted
functions, bit-vectors, arrays - by one procedure, decided now although only
linear integer arithmetic is built first:

* **Equality with uninterpreted functions** is congruence closure over an
  **e-graph**, which is also the hub where theories meet: a term two theories
  share is a node in it. Its explanations are congruence and transitivity
  steps - one small checker rule.
* **Combination is model-based** (de Moura and Bjørner): each theory's model
  proposes equalities between shared terms, the CDCL loop decides them as
  literals, and a theory that disagrees answers with a conflict. Convexity is
  not required, which bit-vectors and integers are not.
* **Bit-vectors** are bit-blasted into the clause core first; the encoding is
  a deterministic function of the term, which the checker regenerates rather
  than trusts (a generator, not a search). Word-level reasoning before
  blasting is a later engine.
* **Arrays** add read-over-write and extensionality lemmas on demand; each is
  an instance of an axiom schema, checked as an instance.

**Rejected:** Nelson-Oppen with eager equality propagation (needs convex,
stably infinite theories, which bit-vectors and integers are not); Shostak
(needs canonisers and solvers per theory); a care graph as cvc5 builds it
(a refinement of the same idea, open to measurement later, not a different
architecture).

### D7 — The strategy layer is its own component, and it switches only at work counts.

A **strategy** chooses before the start and switches during the search; it
is not inside an engine:

* **Features** are read before the start in one pass over the query: counts
  of variables, atoms, disjunctions and non-zeros, the share of interval and
  difference atoms, coefficient sizes, integer or real, the size of the
  Boolean structure. They pick the pipeline: which preprocessing, which fast
  path or engine, which parameters.
* **Signals** during the search are work counters only - conflicts, pivots,
  restarts, cut rounds, promotions to big numbers, the ratio of propagations
  to decisions - read at **checkpoints fixed by the work count** (every 2ᵏ
  conflicts, say). A switch happens at a checkpoint or not at all, so the
  same query and budget switch at the same point on every run (ADR-265 D4).
* **What crosses a switch:** the learned clauses, the theory lemmas with
  their certificate steps, the bounds the theory derived, and the proof log,
  which is shared by every engine and only appended to. A switch never throws
  away a derived fact.
* **Every heuristic is a named parameter** - restart intervals, decay, the
  pivoting rule, cut frequency, the dense width - in one parameter set with
  versioned defaults. The parameter set is part of an answer's input: the
  answer depends on the query, the budget, the solver's version and the
  parameters, and on nothing else.

**Rejected:** strategies inside the engines (no engine could be measured
alone, and none could be replaced); a strategy that reads the clock (D4);
user-written tactic scripts (a language to maintain for a choice the
features already make).

### D8 — The database caches finished results; anything it lets the solver read is a committed input.

* **Result cache.** The key is the query in **normal form** - variables
  numbered by first occurrence, atoms normalised (gcd, sorted columns),
  facts in a canonical order - hashed, with the solver's version, the
  parameter set and the budget. The value is the answer with its certificate
  or model. A hit **re-checks** the certificate or the model against the
  query before it is used (1.9 µs on average for a certificate today): the cache needs no more
  trust than the solver. Because an answer is a function of exactly what is in
  the key, a hit returns what recomputing would; D4 holds by construction.
  The cache lives with the build's output and is keyed on content
  (ADR-021).
* **Lemma store.** Lemmas learned in one query and reused by another would
  make an answer depend on which queries ran before it. They are allowed only
  as a **committed input**: a file, versioned with the project, written by an
  explicit command and never during a build, whose hash is part of every
  key it can affect. Without that file nothing is shared between queries.
* **Measurements per query** - the features of D7, the work counters, wall
  time - are written, never read while solving: they are the input of the
  offline tuning in §6, and of nothing else.

**Measured:** 105 of the 1 697 queries are distinct up to renaming, so a
result cache would answer more than nine in ten in the test suite - an upper
bound, because the suite compiles similar programs many times. A hit saves
today's solve (4.2 µs on average) minus the re-check (1.9 µs for a
certificate): for the
compiler's queries the cache is worth little per query, and it is built for
the hard ones and for SMT-LIB runs, where one hit saves seconds.

**Rejected:** a lemma store written during builds (the answer would depend on
build order); a cache trusted without re-checking (a stale or corrupt entry
would drop a check).

### D9 — The core's memory layout is the SAT solvers' best, and SIMD goes where rows and scores are.

* **Clauses** live in one arena of `u32` words: a header (size, flags, the
  learned clause's glue) followed by the literals; a clause reference is a
  `u32` word index. Literals are `u32` (`variable << 1 | sign`).
* **Watch lists** hold the clause reference and a **blocking literal**, so
  most visits never touch the clause. **Binary clauses** are not in the arena:
  their watch entry holds the other literal. Scanning a watch list
  **prefetches** the next clause's header.
* **Garbage collection** compacts the arena in reference order, which is
  deterministic.
* **Simplex rows** are structure-of-arrays (D2), a column index lists the
  rows a variable occurs in, and big numbers sit in their own arena behind a
  tagged word (D3).
* **SIMD where it pays:** row combination in the dense kernel and on long
  sparse rows (multiply-add with the 32-bit-range check of D3), hashing of
  normal forms for the cache (D8) and of terms for hash-consing, and the
  scoring of candidate moves in local search, which evaluates one move
  against many constraints. Not in unit propagation, which is pointer chasing.
* **Where the code lives:** the engine's loops are plain loops over flat
  arrays, which vectorise; explicit vector instructions are kernels behind
  `std` with a SWAR baseline and multiversioning per target (ADR-009). The
  same split holds after the port to Nikaia.
* **Threads:** each thread owns its arenas, layered over the frozen query
  (ADR-265 D2); nothing in the core is shared and written behind a lock.

**Rejected:** pointer-based clauses (`Box`, `Rc`: twice the memory and no
compaction); hashing with a random seed anywhere (iteration order would vary
between runs; a fixed seed is the rule).

### D10 — The measuring rod: SMT-LIB QF_LIA first, against z3 and cvc5, with differential fuzzing.

* **Sets:** the compiler's queries (D1), the stress families, **SMT-LIB
  QF_LIA and QF_LRA** (non-incremental), and a growing set of found bugs.
* **Differential fuzzing:** random and mutated QF_LIA and QF_LRA formulas are
  answered by this solver, z3 and cvc5; every *proved* is certificate-checked
  and every *refuted* model evaluated, so a disagreement is a bug in one of
  the three, found without trusting any.
* **Scoring** is SMT-COMP's: solved count first, then PAR-2 time. Wall time
  is used **to measure, never to decide an answer**; the solver runs with a
  work budget calibrated to the time limit on the measuring machine.
* **The first goal is QF_LIA**: more solved than z3 and cvc5 on the same
  machine, single-threaded first, then with threads; then QF_LRA; then the
  further theories of D6.

**Rejected:** measuring on the compiler's queries alone (they are 4 µs each,
D1); comparing at different machines or with time-limited strategies on our
side.

### D11 — D4 of ADR-265 everywhere: the rules a parallel solver keeps.

Parallel across queries is a fixed partition by index with answers in index
order. Cube-and-conquer splits by a deterministic look-ahead and combines by a
fixed rule (proved when every cube is; refuted by the first refuted cube **by
index**). Clause sharing happens only at epochs fixed by work counts. These
are ADR-265 D4's rules; this record adds only that the strategy layer's
checkpoints (D7) and the epochs are the same points, so that a switch and a
share never interleave differently.

**Where this differs from the order the owner gave, and why:**

* **Step 2 is kept, and its first criterion is "no harm".** The measured
  compiler queries cost 4 µs each and 7 ms for the whole test suite; a thread
  costs more than the work. Parallel across queries pays for SMT-LIB runs and for large
  projects, so it is built now - behind a work threshold that keeps the
  compiler's batch on one thread.
* **The port to Nikaia (ADR-265 D8 step 4) moves after step 3.** The engine is
  written in Rust, measured against z3 and cvc5, and ported once its shape
  has settled - with the interfaces made for the port from the start (flat
  arrays, `u32` indices, no `Rc`, no trait objects in inner loops, `u32`
  limbs). Porting first would port Fourier-Motzkin. The port needs one thing
  the language does not have: arithmetic that reports overflow instead of
  aborting (§6).
* **Fourier-Motzkin stays as an engine as well as the cross-check**: on the
  compiler's tiny queries it is measured, and the strategy layer may keep it
  where it wins.

## 5. Consequences

* For a program nothing changes: a check is dropped where a certificate
  shows it holds (ADR-264). More queries are answered; none is answered
  differently.
* `nikaia-logic`'s certificate type changes again in step 1 (the proof log of
  D4); `verify` keeps its signature. The Alethe export follows each step.
* The checker grows by named rules, each a replay; its size is a number this
  record fixes (D4) and that a later record has to move.
* The solver's speed becomes a measured claim against z3 and cvc5 on public
  benchmarks (D10), not an impression; the measurement lives in the notes.
* The cost accepted: a CDCL(T) engine, a simplex, big numbers and a strategy
  layer are a large body of code, written before the port, and the measuring
  rod needs SMT-LIB's benchmarks in the build environment.

## 6. What this does not decide

* **SMT-LIB in the environment.** The benchmark sets are downloaded from
  Zenodo, which the development container's network policy does not reach
  today; where they are kept, and how a run is reproduced, is open.
* **Overflow-reporting arithmetic in Nikaia** - `checked_add` and its kin, or
  a wider multiply - which the port needs; a language record.
* **The `Real` sort** in terms and in the SMT-LIB reader, for QF_LRA, and
  whether `δ`-rationals are a number type of the crate or of the simplex
  alone.
* **Incremental SMT-LIB** (`push`/`pop`): ADR-265 D3 keeps queries
  self-contained; whether the solver offers an incremental interface for
  SMT-LIB's incremental track is decided when that track is a goal.
* **Non-linear arithmetic**, where MCSAT (§3, C) is the candidate.
* **Floating-point LP** with exact repair, if the measurement ever shows the
  simplex's exact arithmetic is the bottleneck.
* **Outlook, without preparatory work now:** an offline search for heuristics
  - automatic configuration of D7's parameters, evolved heuristic code,
  superoptimisation of small kernel loops - is safe because every answer it
  produces is checked; and a JIT, or code specialised at run time, only for
  fixed formulas in hot loops (a cut separation routine, a local-search score).
