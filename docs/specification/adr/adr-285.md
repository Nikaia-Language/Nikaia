## 1. Question

**What is an integer in this language?** Which types a program writes; what
happens when a result, a conversion or a literal does not fit; how the bits are
reached; how a number is spelled; and what type a number gets when the program
writes none.

Without an answer, each part reaches the user in `rustc`'s words or as two
programs: an overflow that aborts in a debug build and wraps in `--release`; a
`len()` in `usize` that puts an `as i64` in every loop; an `as` that makes
`-3 as usize` 18,446,744,073,709,551,613 in a language where a conversion that
does not fit aborts; `let big = 3000000000` refused as *literal out of range
for `i32`*, about a type the program never wrote; `1_000_000` read as `1`
beside an undeclared name; `fixed.rs`, which cannot be written without `^`,
`>>` and a `u64`; and `let i = 0` then `v[i].push(x)`, which leaves `rustc` no
type to settle on.

Each answer leans on the others - the literal rule on the type list, the
conversion rule on the overflow rule, the use-site typing on all of them - so
they are decided together.

**What does not transfer.** Rust's `as` is defined to truncate and has no

language promises one meaning in every build (Part I 1.2), which is the
promise Rust's debug/release split breaks.

The weights pulled apart in one place. Reading every use of a number
(D23-D25) is work the compiler could have left to the language below;
it is paid so that the developer writes no annotation that the uses already
answer ([ADR-258](adr-258.md) D2), and it costs one list per open number,
read once per function body - the cost ADR-135 D2 already pays for an empty
list.

## 4. Decision

**The integer types**

### D1 — A length is an `i64`, and so is an index.

Every `std` entry that hands back a length or a count - `Vec::len`,
`String::len`, a map's and a set's `len`, `Seq::count` - returns an `i64`, and
an index takes one. The program writes no conversion in either direction; the
compiler emits both. Out of a length the conversion cannot fail. Into an index
it fails only for a negative number, and that failure **reports as an access
out of bounds** (*"the index is -1"*), because it is one - not as a failed
conversion the program never wrote. An index written only in literals is left
bare for the language below's own inference.

### D2 — The integer types a program writes are `i64`, `i32`, `u8`, `u64` and `u32`; no machine-width type is among them.

`u8` is named because `fs::read` hands one back; `u64` and `u32` because a
hash over bytes asks for them (D3). `usize` and `isize` stay out: a length is an `i64` (D1), and nothing a
program writes needs a machine-width type. `f64` is the floating-point type.

### D3 — `u64` and `u32` have every rule the other integers have, and no integer value is lost silently.

A result that does not fit aborts (D5); `wrapping_`, `saturating_` and
`truncating_` are their names (D6, D13). A wider type takes a narrower one
without `as` wherever no value can be lost (D32); every other conversion is
`as`, checked where it may not fit (D12). `u64 + i64` has no type that holds
both and is refused where both sides are known (`NK1199`), the message naming
both types and the help handing over the `as`.

*Amended October 6, 2026 (#439).*

### D4 — `text.bytes()` is the text's UTF-8, one `u8` at a time.

A sequence, as `chars()` is, so a hash over it is the hash other languages
compute over the same text.

**Overflow**

### D5 — An arithmetic overflow aborts, at every build.

The same program computes the same thing under every build, and a benchmark
measures what is shipped. Part III A.2's list of unrecoverable errors carries
the overflow beside a division by zero. A check the compiler proves unneeded
is not emitted ([ADR-306](adr-306.md)), which changes no result.

### D6 — Wrapping and saturating arithmetic get names, not operators.

`h.wrapping_mul(31).wrapping_add(c)`, `level.saturating_add(increase)`. The
names are Rust's, one for one, so the emitted code stays idiomatic.

### D7 — The full set, including the three that are always forgotten.

`wrapping_add`, `_sub`, `_mul`, `_div`, `_neg`, `_abs`, `_shl`, `_shr`, and
`saturating_` wherever Rust has it. `-x` and `x.abs()` on a signed type's
smallest value overflow, and so does that value divided by `-1`; a shift by
the width or more is an abort of the same category (D11).

### D8 — The arithmetic check is carried by the generated project, not by helper functions, and reaches this language's crates only.

The emitted code says `a + b`; the generated Cargo project turns
`overflow-checks` on for every crate of this language - the program and every
Nikaia dependency - and off for foreign packages, whose hash functions wrap
on purpose. The known limit: whoever rebuilds the
generated project with other settings gets other numbers, as whoever edits
the generated code by hand does.

**Bits**

### D9 — `&`, `|`, `^`, `<<` and `>>` are operators, and `!` on an integer flips every bit.

On integers only, both sides one type, a shift's count excepted (any
integer). The compound forms `&=`, `|=`, `^=`, `<<=`, `>>=` stand beside
`+=`. On a `bool` they are refused (`NK1198`), naming `&&`, `||` or `!=`: a
`&` that does not short-circuit would be a second spelling of one thing.

### D10 — Bit operators bind tighter than comparisons, and one beside a comparison is parenthesised.

`* / %`, `+ -`, `<< >>`, `&`, `^`, `|`, the comparisons, `&&` and `||` -
Rust's and Go's order. A bit operator written beside a comparison without
parentheses is `NK1197`, the help handing over `(a & mask) == 0`.

### D11 — A shift loses the bits it moves out; a count as wide as the type, or negative, aborts.

`>>` fills with zeros on an unsigned type and with the sign on a signed one.

**Conversions**

### D12 — A narrowing conversion is written `as` only where it is shown to fit.

A conversion that can lose a value - a wider integer to a narrower one, a
signed one to an unsigned one or back, an `f64` to an integer or to an `f32` -
is written `as` only where the compiler shows it fits:

* a constant that does not fit is `NK1116` (D29);
* a value the prover shows within the destination's range converts, and the
  emitted conversion carries no check;
* any other narrowing `as` is `NK1241`. The program says by name what it means:
  `checked_<T>()` hands back a `T?`, `null` where the value does not fit, and
  the program handles it; `truncating_<T>()` is the backend's conversion (D13).

Which conversions narrow is the checker's answer, since `as i32` narrows or
widens by what it is given, and the list is written as the conversions that
**always** fit, so an unforeseen pair is treated as narrowing.

**Why not an abort.** A value lost in a conversion is a failure the program
cannot see where it is written. Where a proof can find it, it is found while
building; where none can, the program decides, at the line, between handling
it and keeping what the backend makes of it. A stop at run time is what is
left when neither was asked for, and a conversion is a place where asking
costs one name. Arithmetic overflow (D5) is not changed by this: it has no
spelling a program writes in its place on every operator.

*Changed October 8, 2026 (#552): a narrowing `as` aborted where it did not fit.*

### D13 — Keeping the low digits is said by name; asking whether it fits is said by name; an integer to a float is not checked.

`truncating_i32`, `truncating_i64`, `truncating_u32` and `truncating_u64`
lower to Rust's `as`, from the sources a program can narrow out of: a wider
integer and an `f64`. There is no name out of a machine-width type, because
no program can hold one (D1, D2). Out of an `f64` the backend's `as` makes
`1e20 as i32` `2147483647` and `NaN` `0`; the name is how a program says that
is what it wants. `checked_i32`, `checked_i64`, `checked_u32`, `checked_u64`
and `checked_f32` hand back `null` where the value does not fit, out of an
integer and out of an `f64`, where a value that is not a number does not fit
an integer. An integer to an `f64` loses digits at large
values without overflowing (`9007199254740993` comes back `9007199254740992`);
every language does this, there is no sensible point to stop, and it is a
stated limit, not a check. The `f64` helper goes through `i128`, because
`i64::MAX as f64` rounds **up** and the obvious comparison accepts one value
too many.

### D14 — `as` names a type this language offers, and nothing else.

`i32`, `i64`, `u8`, `u32`, `u64`, `f64`, `bool`, `char`, `String` and its
view. Anything else - `n as usize`, `n as u128` - is `NK1122`, naming the
type and saying that the compiler writes the machine's conversions itself.
This list answers *which types a program may write*; the narrower list of D12
answers *which conversions can lose something*.

### D15 — A `std` parameter the language below counts in `usize` is written as an `i64`, and the conversion is emitted.

`str::repeat(&str, n: i64)`, and the emitter writes `nikaia_std::count::of`
around the argument, so `"  ".repeat(indent)` needs no conversion. A negative
count aborts with a message of its own - *"a count cannot be negative: the
count is -1"* - because it is not an access out of bounds. The list is chosen
by name, because it is a fact about Rust's library and the emitter knows no
types; a test keeps the ledger and the emitter from drifting. A count written
only in literals is left bare, as an index is. No ledger signature names
`usize`.

**How a number is spelled**

### D16 — A number literal may be written `1_000_000`, `0xFF`, `0b1010` or `0o17`.

*Changed by [ADR-322](adr-322.md): a decimal whole number may end in a scale (`1G`, `4Gi`), and an exponent is written `e`.*

An underscore stands between digits and nowhere else. The prefixes are
lower-case; hexadecimal digits either case. A float takes the separator
(`1_000.5`) and no prefix. A digit the radix does not have (`0b1210`) is
refused. A `-` written directly against the digits is part of the literal, so
`-9223372036854775808` is `i64::MIN` and `-0xFF` is `-255`; `- 5` and `-x` are
the unary operator.

### D17 — The radix is a spelling, and a literal is a value.

`0xFF` is `255` and takes its type exactly as `255` does (D20-D25):
`let mask = 0xFF` is an `i32`, `let mask: u8 = 0xFF` a `u8`.

### D18 — The separator is not in the value, anywhere.

`1_000` is `1000` to the checker, the ledger, the fold, and a diagnostic's
text.

### D19 — A literal may be as large as a `u64` holds.

Up to `18446744073709551615`. A literal above `i64::MAX` is a `u64`'s and
nothing else's; one wider than a `u64` is refused by name. With no `u64`
asking, it is refused against `i64` (`NK1116`), the help naming `u64`.

**What type a number takes**

### D20 — Where a use asks for a type, the use decides.

Part I 2.4's first half: `let small = 42` handed to `fn wide(n: i64)` is an
`i64`. This compiler, not the language below, reads the use (D24).

### D21 — Where nothing asks, a literal takes the first type that holds it: `i32`, else `i64`.

`let count = 42` is an `i32`, `let big = 3000000000` an `i64`. The question is
about the value: `-2147483648` is an `i32`. A fallback, not Kotlin's whole
rule, so backward inference survives.

### D22 — A constant expression written only in literals takes the first type that holds it.

The unit is the expression, decided once on the outermost expression that
folds and reaching every literal under it: `2000000000 + 2000000000` is
`2000000000i64 + 2000000000i64`. A value no type holds is refused in this
language's words. A sequence index and a repeat count are left bare (D1, D15).
A value that fits is untouched.

### D23 — A `let` without an annotation whose value is only numbers is an open number.

A literal, a sum of literals, or an operation over other open numbers. One
operation has one type, so `a + b`, `a < b` and `c = a + b` make one number of
all of them. A shift's count joins nothing.

### D24 — Its uses ask for its type, and every use in the function is read first.

A use asks where a type stands beside the number: a parameter, a `return` or
last expression, an annotated `let`, a field, a typed operand or comparison
(`i < xs.len()` asks for an `i64`), an assignment either way. An index asks
for an `i64` only where nothing else asks - a preference, never a conflict.
Two uses asking two types are `NK1200`, naming both, with the annotation to
write.

### D25 — Where no use asks, what it is given decides, and every value it is given must fit.

The first type that holds all of its values - its own and every one assigned
to it - `i32`, else `i64` (D21 over every value): `let mut n = 1` then
`n = 3000000000` is an `i64`. A value the decided type does not hold is
`NK1116` at that value, with a note that the type came from the uses.

### D26 — A name is where the widening stops.

What an operation over a name comes to is held to the name's type and never
decides it. `let a = 2000000000` then `let c = a + a` is refused where nothing
asks (*"this comes to 4000000000, which does not fit in an `i32`"*, the way
out `let a: i64`), and is an `i64` where a use asks for one.

### D27 — The decided type is written into the generated `let`.

`let i: i64 = 0;`, so the language below infers nothing this compiler
decided; a literal that would get an `i64` suffix carries the decided type's.
A number no use asked for is written bare.

### D28 — One constant fold, and the lookup is what separates its callers.

`crate::fold` holds the arithmetic - in an `i128`, every step checked, over a
literal, an immutable `let` whose value folded, `+ - * / %` and a negation -
and what a name is worth is a parameter. The checker passes its scope; the
emitter, which has none, passes `nothing_is_known`, and gets exactly D22's
subset.

**Refused at compile time**

### D29 — A constant that does not fit the type beside it is a compile error, not an abort.

`let x: i32 = 3000000000` is `NK1116`, at an annotated `let`, a `return`
against a declared result, an argument whose parameter says what it takes,
and where an operand's declaration pins the type (`let b = a + 1`). A fold
that stops - a `mut` local, a parameter, a `for` binding, a cast - claims
nothing, and an expression that does not fold is never refused.

### D30 — A constant operation that overflows is refused where it stands.

In an `f"…"` hole, a condition, a list, a receiver - once, at the innermost
operation that overflows. An operation over an open number is measured once
that number's type is decided.

### D31 — A division whose divisor is a constant zero is refused.

`NK1118`, by the fold D29 uses. Every other division by zero stays where Part
III A.2 has it: unrecoverable at run time, naming the Nikaia line. A divisor
the fold cannot evaluate is one nothing is claimed about.

### D32 — An integer widens where no value can be lost, between types already decided.

*Added October 6, 2026 (#439).*

```nika
fn area(x: i32, y: i32) -> i64 {
    x * y                       // computed in i64
}

let n: u64 = xs.len()           // a length is never negative
let total = count + offset      // u32 + i64 is an i64
if small < big { … }            // u64 against i64, compared as numbers
```

**1. The common type.** Two integer types have a common type when one type
holds every value of both:

| | `u8` | `u32` | `u64` | `i32` | `i64` |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `u8` | `u8` | `u32` | `u64` | `i32` | `i64` |
| `u32` | | `u32` | `u64` | `i64` | `i64` |
| `u64` | | | `u64` | none | none |
| `i32` | | | | `i32` | `i64` |
| `i64` | | | | | `i64` |

A **typed slot** - a `let` with an annotation, an argument for a parameter of
a stated type, a `return` or a body's last expression, a field in a struct
literal, an assignment, an element of a list whose element type is stated -
takes a value of a narrower type that its type holds. An **operator** whose
two sides are two integer types computes in their common type, and a **list
literal** whose elements are two integer types holds their common type,
whichever comes first. Where there is none, `NK1199` and `NK1154` stand.

**2. A comparison** of two integer types compares the numbers, for every
pair, `u64` against `i64` included.

**3. Inference first, widening after.** A number without an annotation
(D23-D25) and a generic parameter are typed by their uses, each use asking
for exactly its type, as before. Widening is a check between two types already
decided and never one of a use's answers: `let n = 5` handed to an `i64` and
to a `u32` is `NK1200`, and `pick(a, b)` for `fn pick[T](a: T, b: T)` over an
`i32` and an `i64` is refused with `a as i64` as the help.

**4. A slot's type reaches through `+`, `-`, `*`, `/`, `%` and a negation.**
`let t: i64 = x * y` over two `i32` computes in `i64`: each operand is widened
before the operation. It does not reach into what a name was given, into a
call's arguments, a method's receiver or an index, and it stops at the
operators whose result depends on the width - `&`, `|`, `^`, `!`, `<<`, `>>` -
and at the `wrapping_`, `saturating_` and `truncating_` names. There, a computation in a narrower type is refused
(`NK1215`), the help naming both readings: `(a as i64) << 3` and
`(a << 3) as i64`.

**5. A value shown non-negative goes into an unsigned type without `as`.**
`let n: u64 = xs.len()` and, after `if k >= 0`, `let n: u64 = k` are taken
where the proof says `k >= 0` (ADR-306 D12 and D16; a callee's postcondition,
ADR-269 D17). Where it does not, the slot is `NK1103`, `NK1102` or its
neighbour, with `as u64` and `assert k >= 0` as the help.

**Why a lost value and not a mix.** Every refusal D3 made for a mix that loses
nothing was answered with an `as` that could not fail; it marked no place a
value might not fit, which is what D3 asked of it, and taught that `as` is
noise. Java, Kotlin and C# widen at the same places; C widens too, but to a
type that does not hold both (`u32 + i32` is a `u32` there), which is the
mistake D3 was written against and the common-type table rules out.

**Why inference does not widen.** With widening among a use's answers, `let n
= 5` handed to an `i64` and a `u32` has two types that work and no rule that
picks one, and a generic `T` over an `i32` and an `i64` has two as well. C#
picks the wider one for a generic; Swift admits no implicit widening at all,
in part because its inference is already costly with literals and overloads.
Between two types already decided the common type is unique, so keeping
widening out of inference keeps both.

**Why the slot's type reaches the operands.** Overflow aborts (D5), so `+`,
`-`, `*`, `/` and `%` in a narrow type either give the number the wide
computation gives or stop the program; computing wider changes no value a
program prints and only removes a stop. That is untrue of the bit operators:
`!a` for `a: u32 = 0` is 4294967295 as a `u32` and -1 as an `i64`, and
`x << 31` for `x: i32 = 1` is -2147483648 and 2147483648. So those stop the
slot's type, and an expression of them is refused rather than read either
way. Computing the narrow type and widening the result (the rule for a name)
was the other choice for arithmetic: it is the `long t = x * y;` mistake C is
known for, kept as an abort.

**Why a proof may admit a value.** The proof a build uses is the committed
`nikaia.proofs` entry, replayed from its certificate (ADR-270 D4, D21), so the
answer does not depend on the machine or on the search; a change that removes
the fact is a refusal with a help, never a wrong value. Facts about `std`
calls are their postconditions and D12's length bound, so nothing is added to
the ledger.

**Rejected.** A ledger column *never negative* for `std` results: a second
place for what a postcondition already says, and blind to `if k >= 0`.
Refusing a narrow computation in a wide slot: safe, but `let p = x * y` then
`let t: i64 = p` is allowed, and the rule would forbid the spelling that
means what the annotation says. Computing a whole expression in its widest
operand's type wherever it stands: one `x * y` would compute in three types
in three places. Converting a finished list (`Vec[u32]` into `Vec[i64]`): a
new allocation and a copy, and no longer the same list.

**What it costs.** A reader meets an expression whose type is the slot's,
not its operands': `x * y` as an `i64` and, moved into its own `let`, as an
`i32` that may stop. A computation into a wide slot handles half as many
elements per vector register (not measured). No mainstream language passes a
slot's type to its operands.

### D33 — `f32` is a type of the language, beside `f64`.

Half the size per value is what a picture, a model's weights, a sensor's
samples and most wire formats are made of, and every language this one is
measured against offers it (C, Rust, Go, Swift, Java, C#). It follows the rules
already set for numbers, so it adds no rule of its own:

* A float literal is an `f64`, unless its use asks for an `f32`
  (`let w: f32 = 0.5`), as an integer literal takes the type its use asks for.
* An `f32` and an `f64` do not mix without `as`.
* `f32 as f64` always fits.
* **`f64 as f32` is written only where it is shown to fit.** A constant beyond
  the `f32` range is refused where it stands (`NK1116`, as D29 for integers).
  A value the prover shows to be within the `f32` range, or infinite, or not a
  number, converts, rounding to the nearest `f32`. Any other is refused with
  `NK1241`, and the program says what it wants by name:
  * `x.checked_f32()` is an `f32?`, `null` where a finite value is beyond the
    range, and the program handles it (`?? …`);
  * `x.rounding_f32()` is the backend's conversion: the nearest `f32`, and an
    infinity where a finite value is beyond the range.

  Losing digits is not a failure: every `f64` within the range has a nearest
  `f32`. Only leaving the range is.

This is D12's rule for every narrowing conversion. The prover reasons about
integers and not yet about floats (ADR-270 D11), so until it does, a
non-constant `f64 as f32` is `NK1241` and a program writes one of the two
names.

*Decided October 8, 2026 (#470, #552).*

### D34 — The elements of a list written in number literals are one open number.

`[12, 14, 13]` is a `Vec[T]` whose `T` is decided as D23-D25 decide a `let`'s:
the uses ask - a parameter `Vec[u8]`, an annotated `let`, an element read into
a typed place (`let x: u8 = xs[0]`), a `push` of a typed value, an element in
a typed operation - and two uses asking two types are `NK1200`. Where no use
asks, the first type that holds every element, and every value written into
the list, is the element type: `i32`, else `i64` (D21, D25). D26 holds for an
element as for a name: `xs[0] + xs[1]` over two `2000000000`s is `NK1116`
where nothing asks for an `i64`.

**Why.** A list of literals is the same question as a `let` of one, one level
down, as [ADR-135](adr-135.md) D2 already answers it for `[]`. A fixed
`Vec[i64]` would refuse `total([1, 2, 3])` against `fn total(xs: Vec[u8])`, and
a list left untyped stops at run time where the same sum over a name is refused
while building.

*Decided October 8, 2026 (#513).*

### D35 — Text becomes a number by a function per type, and the name carries the type.

`text::parse_i32`, `parse_i64`, `parse_u8`, `parse_u32`, `parse_u64`,
`parse_f32` and `parse_f64` each hand back a `T?`: the number the whole text
writes, or `null` where it writes none or one the type does not hold. An
integer is an optional sign and decimal digits (an unsigned type takes no
`-`); a float is an optional sign, digits, an optional `.` and digits, and an
optional exponent (`e` or `E`), or one of `inf`, `-inf` and `nan`, which a
float holds and a data file writes. Nothing else: no space, no `_`. A program that has to say why a text is not a number reads it with a
grammar (`dec[T](p)`, Part II 10.8).

**Why.** The name carries the type, as `checked_i32` and `truncating_i32` do,
so no signature has to take its type from the place its result goes, and no
conversion follows the parse: `text::parse_i32(s) ?? 1000` instead of an
`i64` narrowed by `checked_i32` (D12). Java, C# and Go name the type the same
way; Rust's and Swift's generic `parse` would be the one function in `std`
whose result is typed by its use. Rust's `str::parse` is not offered
([ADR-286](adr-286.md) D36).

*Decided October 8, 2026 (#504).*

## 5. Consequences

* **Part I 2.2** lists five integer types and the float, the overflow rule
  and its named exceptions, the bit operators, the four spellings, `as` and
  its checks, and the compile-time refusals; **Part I 2.4** says what a use is
  and what a number takes where none asks; **Part III A.2** lists the overflow
  and the conversion that does not fit among the unrecoverable errors; Part
  III's table carries `NK1116`, `NK1118`, `NK1122`, `NK1197`, `NK1198`,
  `NK1199`, `NK1200` and `NK1215`.
* No integer arrangement reaches `rustc`'s overflow lint, its *literal out of
  range*, its *type annotations needed* or its *mismatched types*: each is
  answered in this language's words first.
* **What it costs.** Five integer types, and a beginner meets an unsigned one the first time a file is read.
  A checked conversion where Rust would truncate. One list per open number,
  read once per function body. The generated Cargo project carries the
  overflow setting, and a project rebuilt with other settings computes other
  numbers.
* Nothing is added to the cache key: the check is not a switch.

## 6. What this does not decide

* **Whether the default integer should be `i64` outright**, as Go's and
  Swift's is. A length and an index already are one (D1); it would cost Part I
  2.4's `i32` sentence and four bytes per unannotated number. D21 is what an
  `i64` default would also say about a literal too large for it.
* **Whether a program may ever name a machine-width type**, and which further
  `std` entries join D15's list; an entry that cannot be described without one
  is the argument for reopening.
* **A type suffix** (`1u8`), a separator in a `char` escape or a string, and a
  hexadecimal float.
