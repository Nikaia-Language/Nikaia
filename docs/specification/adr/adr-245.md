## 1. Context

There is no `nikaia test`. Part III 14 describes one — `test` blocks, an `assert`
statement, fuzzing, `bench` — and none of it is built. Programs in this tree are
tested from Rust, by running them and comparing what they print
(`crates/nikaia/tests/examples.rs`).

**What that costs was measured on 2026-09-27.** Rewriting the comments of the 22
programs in `examples/`, every claim a comment made was checked by running it.
About fifteen were false or stale: an expected output that was not the output,
a unit of time that was wrong, a run instruction that built nothing, a
compiler refusal that no longer happens. None was caught by a test, because the
only thing tested was each program's final output.

**Part III 14.2 would make `assert` the one run-time check a build option turns
off.** Everywhere else the language says the opposite: an overflow, an index out
of bounds and a conversion that does not fit are unrecoverable *at every build*,
and *the check does not depend on a build option* (Part I 2.2, Part III A.2).
Other languages keep `assert` with their other checks — Zig's `assert` and its
overflow checks are both on in `Debug` and `ReleaseSafe` and both off in
`ReleaseFast`; Rust's `assert!` is on in every profile. Nikaia has no build that
trades safety for speed, so by that reasoning `assert` is always on.

**But "always checked at run time" is the wrong thing to fix in place.** The
compiler already proves some claims before a program runs — a constant that does
not fit (`NK1116`), a division by a constant zero (`NK1118`) — and refuses the
program instead of letting it fail. An `assert` is the same kind of statement
written by a person. If its meaning is fixed today as *a check at run time*, a
compiler that later proves it cannot remove the check without changing what the
language says, and a condition written today that reads a file or changes a
value can never be proved at all. Both have to be settled before the first
`assert` is written, because afterwards they break programs.

## 2. Decisions

### D1 — A test is a `test "name" { … }` block in the package it tests.

```nika
test "a blank line is counted" {
    let (lines, blank) = count("a\n\nb\n")
    assert(lines == 3)
    assert(blank == 1; message: "an empty line is blank")
}
```

* A `test` block stands where a `fn` may, in any file of the package, and sees
  what the package sees, private names included.
* It is compiled only by `nikaia test`; `nikaia build` and `nikaia run` leave it
  out.
* Its body may pause and may fail. An error that leaves the body fails the
  test and is printed in its long form (`error.full()`: the site and the chain).
* A test fails on an error that leaves it, a false `assert`, or a `panic`. A
  failing test does not stop the others: each test runs in a process of its own,
  because a panic at `user_parallelism = no` ends the process (Part III A.2).

`test` becomes a reserved word, for this construct. Measured: no name in the
84 `.nika` files of this tree is `test`.

### D2 — `assert` is a prelude function, and the compiler knows it.

```nika
assert(cond)
assert(cond; message: "what should have held")
```

It is a function in the sense of the language — the subject before the `;`, an
option after it — so it costs no reserved word. It is on the prelude's list
already (ADR-154 D1). The compiler recognises the call, for D3 to D6, and for
its message: a false `assert` names its line, its condition as written, and the
value of each operand of the comparison, because only the compiler knows what
they were called:

```text
assertion failed at src/tally.nika:4
    assert(blank == 1; message: "an empty line is blank")
    blank is 2
```

A false `assert` is unrecoverable, as a `panic` is (Part III A.2).

### D3 — The condition of an `assert` is pure.

The condition may not pause, may not fail, and may not change anything: it is
`sync`, it does not `throw`, and it touches no place and calls nothing that
does. A condition that does is refused where it is written.

This is the rule that keeps D4 possible. A condition that reads a file, or
advances an iterator, has no value a compiler could prove before the program
runs — and a condition with an effect would make the program behave differently
depending on whether the check is performed. Refused from the first `assert`
on, nothing written today stands in the way of a prover later.

### D4 — An `assert` is a claim, and the compiler decides how it is held.

*An `assert` claims that its condition holds whenever it is reached.* For each
one the compiler does one of three things:

| the compiler | then |
| :--- | :--- |
| **proves** the claim | the check is not emitted |
| **refutes** it, with an input that reaches it false | D5 |
| does neither | the condition is checked at run time, and a false one is D2's failure |

**No build option chooses among the three.** Part III 14.2's *removed in a
release build* is displaced: debug and release programs hold the same claims.
Today the compiler proves nothing, so every `assert` is checked at run time.
A later compiler that proves more removes checks and changes nothing a correct
program does — which is why D3 comes first.

### D5 — A refutation needs a counterexample, and it is a warning until decided otherwise.

A claim is refuted only with **concrete values** that reach the `assert` with the
condition false, and the message shows them:

```text
warning: this assert can be false
  --> src/math.nika:7:5
   7 |     assert(b != 0)
     = `divide` is called with `b = 0` at src/main.nika:12
```

It is a **warning**, not a refusal. A compiler that proves more would otherwise
refuse, in its next version, a program the previous one accepted — the same
fault ADR-244 removed for `sync`. Whether a refutation becomes a refusal is a
later decision, made when there is a prover to measure.

### D6 — `nikaia --asserts` reports each claim.

Beside `--sharing`, `--tethers` and `--overlaps`: every `assert` in the program,
and for each whether it was proved, refuted (with D5's values) or left to run
time. Today every row says *run time*; the report exists so that a prover's
progress is visible and a reader can ask why a check is still emitted.

### D7 — `nikaia test` runs at the project's setting; both settings on request.

Each test runs under the `user_parallelism` the project names.
`nikaia test --both-settings` runs each test at `no` and at `yes`, and a test
whose outcome differs between them fails with both outcomes shown. The meaning
of a program is the same at both settings (Part I 1.2); a difference is a
compiler fault, and this is how a project asks for it to be looked for.

### D8 — An output test is three files and no code.

In a package's `tests/` directory, `NAME.stdout` makes `NAME` a test of the
package's program:

| file | is |
| :--- | :--- |
| `NAME.stdout` | required: what the program must print, compared byte for byte |
| `NAME.stdin` | optional: what it is given on standard input (empty otherwise) |
| `NAME.args` | optional: its arguments, one per line |

The program must also end successfully. This is what `examples.rs` does for the
programs in `examples/` today, written as data instead of Rust, and it is what an
expected output shown in a comment can be pinned with.

## 3. Not covered

**Preconditions and postconditions.** A claim on a function's signature —
`requires b != 0` — is where a prover pays most: every call is a place to prove
it, and across a package it would be a promise in the ledger as `sync` is
(ADR-244). It needs syntax and its own record; D3 to D6 are written so that it
can reuse them.

**The implicit checks.** An overflow, an index out of bounds and a division by
zero are claims of the same kind that nobody wrote. Whether D4 and D6 apply to
them — a proved index check not emitted, and listed — is a later decision; D4's
table is written so that the answer can be *yes* without a new rule.

**An assert only for development.** A condition too expensive to check in
production wants a second name (Rust's `debug_assert!`), not a build option on
this one. Added when a program needs it.

**Fuzzing and `bench`** (Part III 14.3, 14.4) are unchanged by this record.

## 4. Considered and rejected

**`assert` as a statement, as Part III 14.1 wrote it.** A reserved word for a
construct a function expresses as well; ADR-117 took four such words out.

**Removed in release builds, as Part III 14.2 wrote it.** The one run-time check
a build option would switch off, against Part I 2.2 — and a meaning (*checked in
debug*) a prover could not later improve on without changing it.

**Checked at run time, always, and nothing more.** Consistent with overflow
today, but it fixes the meaning at the implementation of the day. D4 says the
same thing for today's compiler and leaves the proof possible.

**Every test at both settings by default.** It doubles every run to look for a
compiler fault; that search belongs to the compiler's own test suite and to
whoever asks for it (D7).

## 5. Consequences

* `nikaia test` exists as a command; Part III 13.2 already lists it.
* Part III 14.1 and 14.2 contradict D2 and D4 until they are rewritten with the
  build ([`open-work.md`](../../open-work.md) §3).
* `open-work.md` §2.41's last open name, `assert`, is answered; the work to

* The first programs to carry tests should be the ones in `examples/`, whose
  expected outputs are in their comments today (D8).
