## 1. Question

**What does a type parameter mean, what may a bound on it say, and who answers
for the bound — in one file and across a package?**

Part I 4.6 and 4.7 printed generics and traits before either compiled. The
`[T]` was read by the parser, erased by the checker and dropped by the emitter,
so `fn hand[T]` reached `rustc` as a type nobody declared. `trait Summarize`
was a parse error at the keyword, so a bound had nothing to name. And once a
bound existed it did one of its two jobs: it put a method in reach of the body,
while nothing asked *which types may stand here* — so `tell(rock)` where `Rock`
implements nothing, and a call into a package's generic function, were both
answered by the backend about a file nobody wrote (Part III C.1). Each step is
the same question asked one place further out: the body, the declaration, the
call, the package.

## 2. How others do it

Measured against the one language this lowers to; no other was surveyed.

| Language / tool | Its answer | What it costs there | Source |
| :--- | :--- | :--- | :--- |
| Rust | `<T: Trait>`, monomorphised; a body may use only what a bound declares, a caller must satisfy the bound | no dispatch at run time; one body per instantiation at compile time | measured |
| Rust, the parameter alone | `fn shout<T>(x: T) -> String { x.to_uppercase() }` | refused: *no method named `to_uppercase` found for type parameter `T`* | measured |
| Rust, two bounds with one method | the call is ambiguous and needs a disambiguation | a syntax Nikaia cannot write | §6 |

What does not transfer: Rust has `dyn`, `where` clauses and default bodies,
and Nikaia has none of the three; a trait here names a bound and nothing else.

**The number that decided it:** `rustc` compiles 60 generic functions at 8
instantiations 11 % faster than the same 480 written out, and the generated
generic runs as fast as its concrete twins - the cost to watch is the
instantiation count, not the feature.

## 3. Options, weighed

| Option | Lost because |
| :--- | :--- |
| Keep [ADR-024](adr-024.md) D4's erasure in the body as well as at the call | `T` became `?`, `?` fits everything, so a body that misuses its parameter checks clean and fails below — C.1 |
| Emit the `<T>` and nothing else | turns *every generic fails* into *every generic whose body uses its parameter fails*: the same class one size smaller |
| Infer `T` from its uses | a constraint solver, with pathological inputs; a parameter that is **written** leaves nothing on the right-hand side to solve for, which is what keeps the cost flat |
| `impl[T] Stack[T]`, a second list | a spelling Part I does not have, bought to avoid a rule that reads the list already written |
| A trait method as an `Item::Fn` with an empty or optional body | *declares this* and *does nothing* become one shape, and an absent body could be emitted by accident |
| A bound as a licence that the member exists | arity, argument and result types, `sync` and `throws` would go unchecked; one lookup answers all of them |
| `use http` bringing `Handler` in | breaks [ADR-286](adr-286.md)'s *every name on a line says where it comes from*; a path in the bound makes the exception unnecessary |
| One ledger listing a trait's implementors completely | an `impl` may be written in the trait's package, the type's, or a consumer's; a list read as complete turns absence into an answer ([ADR-010](adr-010.md) D1) |
| Who implements what, in the checker's per-file walk | one file sees one file, so a two-file project that builds and runs would be refused — C.4, the most expensive failure |
| The bound in a ledger key of its own | a second key that must agree with the `signature` is a second source of truth for one fact |
| The bound recorded and read as the package spells it | the consumer's trait map holds `handler::Handler`; a bare `Handler` finds no trait and the refusal never lands |

The weighing in every row is the same one: a correct program refused (C.4) is
the worse mistake, and a wrong one passed to the backend (C.1) is the one to
close — so each refusal is placed where the compiler has the answer, and withheld
where it does not.

## 4. Decision

### D1 — Inside its own body a type parameter is a type; at a call site it is a variable.

In the body `T` is a type and is compared as one: the caller picked `T`, so a
body that puts an `i64` where `T` is wanted is wrong. At a call `T` is a
variable, bound from what the caller passes and substituted away, or `?` where
nothing bound it; it never survives into a comparison, so no caller is told
that `i64` is not `T` — [ADR-024](adr-024.md) D4's reason, kept exactly where it
applies. `Self` stays erased: no call site binds it.

### D2 — A variable binds from the arguments and from a struct literal's fields, and is written, never inferred.

`hand(n)` with `n: i64` is an `i64`; `Pair { first: n, second: n }` is a
`Pair[i64]`, and a value's own type arguments bind its declaration's parameters
when a field is read back. One structural walk, the one
[ADR-288](adr-288.md) uses for a receiver: no queue, no fixpoint, no occurs
check, because a type parameter is declared and never solved for. A mismatch
binds nothing.

### D3 — The emitter writes the parameters, on a `fn`, a `struct` and the `impl` over it.

`fn hand[T]` is `fn hand<T>`, `struct Pair[T]` is `struct Pair<T>`,
`impl Pair[T]` is `impl<T> Pair<T>`; an input lifetime stands first,
`struct Row<'a, T>`.

### D4 — An `impl`'s parameters come from the slots it already writes; there is no `impl[T]`.

`impl Stack[T]` declares `T` and `impl Stack[i64]` applies `i64`: a bare name
that is neither a Part I 2.2 type nor one this file declares stands for a type.
The rule lives in one function that the ledger, the checker and the emitter all
call.

### D5 — `NK1126`: a member reached on a type parameter that no bound of it declares.

Fields and methods both. The message says *no bound*, not *no such method*: the
method may exist on every type a caller passes, and what is missing is the
sentence that says so. It is asked after the bounds (D8), so it fires only where
none of them declares the member.

### D6 — A trait declares signatures, and the syntax tree says so.

`trait Summarize { fn summary(ref self) -> String }` is an item whose methods
have **no** body — not an empty one and not an optional one — and the emitter
writes it with a writer for declarations rather than by omitting a definition's
parts. `trait` is a reserved word.

### D7 — A bound is written `[T: Summarize]`, and several are `[T: A + B]`.

Inside the brackets Part I 4.6 already puts the parameter; `+` joins a list.
They reach the generated file as `<T: Summarize>`, in source order.

### D8 — A bound is looked up in the ledger, under the trait's name, before anything is refused, and it answers the whole call.

A trait's methods are recorded as `Summarize::summary`, the key shape an
`impl`'s methods get, because a bound and a receiver ask one question: *what
does a value of this thing have*. A member reached on a type parameter is asked
of its bounds as receivers, and the trait's entry answers arity (`NK1101`),
argument types (`NK1102`), the result type, `sync`, `throws` and the binding of
the signature's variables. A name that is not a trait in the ledger names none.

### D9 — A trait's method is recorded with the words it was declared with.

A declaration has no body to infer from, so what it says is what it is: `sync`
where the word stands, and without it a method that **may pause**, as a
function type reads ([ADR-288](adr-288.md) D24). A call through a bound pauses
where the declaration allows it.

### D10 — A bound takes a path, as every position that names a type does.

`fn dispatch[H: http::Handler](r: Router[H])` and `[T: A + http::B]`. The
grammar's rule for a type name is the rule for a bound's trait name.

### D11 — `use` is unchanged: no name comes in, for a trait as for anything else.

### D12 — The ledger has a `trait` table, and a trait's methods are the ordinary `fn` entries beside it.

```toml
[trait."Handler"]
pub = true

[fn."Handler::handle"]
signature = "(ref self, request: Request) -> Response"
sync = true
```

The table carries the trait's name and nothing else — no `fields`, and no list
of methods, which would be a second source of truth for the `fn` entries the
`impl` owes (`NK1130`). The table is what a bound and an `impl … for` must name,
and a trait is never the type of a value.

### D13 — Each `impl` is an entry in the ledger of the package that wrote it, and whether a type implements a trait is the union over every ledger the program reads plus its own.

```toml
[impl."Handler for Static"]
```

An `impl` may stand in the trait's package, the type's, or a consumer's, so no
ledger can list implementors completely and none claims to. An `impl` no read
ledger wrote does not exist for this program.

### D14 — A call through a bound resolves to the implementing type's own entry.

There is no `dyn`, so at every instantiation the concrete type is known: its own
`sync` and `throws` are what that call has, and the trait's declaration is the
ceiling an `impl` may not exceed, checked where the `impl` is written
(`NK1129`, `NK1130`). The body is checked against the trait's entry (D8), which
is the right answer for its signature.

### D15 — The ledger records who implements what, merged across units, under both spellings.

The claim *`Dog` answers for `Speaks`* is made in one place, the `impl` head, and
it is recorded in the ledger rather than found by the checker's walk, because an
`impl` may stand in another file from the `fn` that asks. Absorbing a module
records it under the package's spelling and the qualified one; an extra
spelling can only make the check fail open. Across a package it travels as
D13's `impl` table.

### D16 — A call whose type does not answer for the bound is refused here (`NK1164`).

At the call the binding of D2 is asked the second question, at the free-call and
the method-call site alike. Two sentences, because there are two readers: a
concrete type is told *write `impl Speaks for Rock { … }`, or pass a type that
already has one*; a parameter of the caller's own, which no `impl` can be written
for, is told *add it to the bound: `[V: … + Speaks]`* (Part III C.2).

### D17 — The refusal fails open where this compiler could not have the answer.

* **A trait this program has not read** — one the compiler reads rather than one
  a `.nika` file wrote ([ADR-023](adr-023.md) D3), or one no ledger in reach
  describes. A trait read from a dependency's ledger is checked.
* **An argument this compiler could not type**, which binds nothing.
* **A parameter that carries the bound**, which answers for it: that caller did
  not pick the type either (D1, at one remove).

### D18 — A bound reaches a caller inside the `signature`, where the declaration writes it.

```toml
[fn."dispatch"]
pub = true
signature = "[H: Handler](h: H) -> String"
```

The type parameters are declared in brackets before the parameters, as the
source declares them — `[T](x: T) -> T` for one with no bound — with several
traits `+`-joined and several parameters `,`-separated. One string and not a
second key: the signature already carries the parameter, and the bound is the
rest of that sentence. A signature with no brackets parses as it always has. The ledger's hash covers it, so adding or removing a bound
changes the file a consumer compiles against ([ADR-100](adr-100.md)).

### D19 — The bound arrives in the declaring package's namespace and is read in the consumer's.

A package writes its own names bare and a consumer writes the path
([ADR-286](adr-286.md) D1), so the trait name is qualified on the way in: every
prefix of the entry's own key is tried, and the first spelling this program's
trait map knows wins. Only a spelling the program has; where none matches, the
name stands as written and D17 applies. It is D15's *under both spellings*,
asked from the reading side.

## 5. Consequences

* Part I 4.6's and 4.7's programs compile and run: declare a trait, bound a
  parameter by it, call the method through the bound — and Part I 4.7's prints
  `User: Ada`.
* A bound is worth something at both ends: it says what a body may do with its
  parameter, and what a caller may hand in. A body that calls `say` on its `T`
  is a body whose callers have all been asked, in one file, across files, and
  across a package (`NK1164` naming `handler::Handler` and offering
  `impl handler::Handler for Bare { … }`).
* A generic call is typed rather than opaque: `let wrong: String = hand(n)` is
  `NK1103` naming `i64`.
* The ledger gains a `trait` table, an `impl` table and a bound inside the
  `signature` (Part III 13.5). A package can publish a trait and a consumer can
  constrain by it; a library author writes nothing new.
* The cost accepted: every bound is answered from a table a package must write,
  and where the table is missing the check is silent rather than wrong.

## 6. What this does not decide

* **A bound on an `impl`'s own parameter.** `impl Stack[T]` has nowhere for a
  `: Summarize` to stand (D4).
* **Two bounds that declare the same method.** `[T: A + B]` takes whichever
  bound declares it first; Rust calls the call ambiguous.
* **A trait as a type, a default body, a `where` clause.** None has a spelling.
* **Generic enums** (`enum Maybe[T]`), **variance**, and **lifetimes on
  parameters**.
* **What a literal binds.** `hand(7)` is `?`, because a literal carries no type
  on purpose; [ADR-285](adr-285.md)'s question.
* **Coherence** — two packages each writing `impl A for T` — is not decided
  here.
* **A shape bound's travel.** `[T: Struct]` ([ADR-304](adr-304.md) D2) is
  answered by a declaration and records the same way.
* **Which of a trait's methods a bound reaches** beyond its `fn` entries is
  [ADR-304](adr-304.md)'s ground.
