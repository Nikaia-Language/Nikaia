## 1. Context

### 1.1 Two things called "type"

The compiler holds two different things that are both called a type.

* **What the program wrote**, `ast::Type`: the `Vec[Row]` in a declaration,
  with the span it was written at. It has been declared in Nikaia since
  ADR-252 D1, in `tools/ast.nika`, like the rest of the tree.
* **What the checker concluded**, `contracts::ty::Ty`, in `contracts/ty.rs`
  (1 925 lines). It is the written type with three additions:
  * `Unknown`, which means *no claim*. It is compatible with everything, so an
    error is reported only where both sides are known and disagree.
  * `Var` (`$V`, ADR-030), a name in a library's signature that the receiver
    binds at a call.
  * The shapes only a ledger writes: `Fn` with `sync` and `throws`, `Seq`
    with what one step may do and what the whole is (ADR-105, ADR-212), and
    `Pointed` (ADR-147).

  It has no spans, because it is also what the **ledger** records. A ledger
  is a file (ADR-100), so a `Ty` has a **text form**: `Ty::parse` reads it,
  and `Display` writes it. Two types are the same when they are written the
  same, and nothing is interned.

The ledger's records are declared around it in `contracts/mod.rs`. They are
`FnContract`, `TypeContract`, `Signature`, `FieldContract`, `VariantContract`,
`ConfigContract`, `Ledger`, and the small enums `Sync`, `Lock`, `Crosses`,
`Threads` and `Provenance`.

### 1.2 How this became the blocker

ADR-250's rule is that a module moves when everything it reads is Nikaia or
plain data. The tree moved, so `fold`, `trust` and the rest of the first ring
could move after it (ADR-252, 0.0.273–0.0.281; the self-hosted share went
from 2.4 % to 3.8 %).

Every module of the **next** ring reads `Ty` or a ledger record:

* `sync` asks whether a callee is `sync`.
* `throws` asks what a callee may fail with.
* `keeps` asks what a parameter lends.
* The checker itself uses `Ty` on 633 lines of `check/mod.rs`.

So nothing more moves until these types are Nikaia, or until each module's
adapter flattens them into plain data. The second path is option (2) of the
open decision. It builds an adapter per module that is deleted again once the
types move, and the owner declined it.

### 1.3 What other compilers do

| compiler | the checker's type | across a unit boundary |
| :--- | :--- | :--- |
| `rustc` | `hir::Ty` for what was written; `ty::Ty<'tcx>`, **interned** in an arena, compared by pointer | `.rmeta`, a binary encoding of the interned types |
| Go | `go/ast` for what was written; `go/types`, plain heap objects, compared by structure with identity rules (`types.Identical`) | export data, a binary encoding |
| TypeScript | one `Type` object per type, created through caches so each is created once, with flags for the kind | `.d.ts`, a **text** form, re-read by the same parser |
| Swift | canonical types, **interned** in the `ASTContext` | `.swiftinterface`, a text form |
| Zig | `InternPool`: every type **and every comptime value** is a `u32` index into one pool | the pool is what incremental compilation keeps between updates |

Nikaia is closest to TypeScript today. Types are plain trees and the boundary
is text. Go and TypeScript are also the two that moved (or are moving) their
compiler to another language. Go 1.5 did it by mechanical translation, so the
shape of the types did not change during the move. The move and the redesign
were kept apart.

### 1.4 Why Zig interns, and why that may not be this compiler's answer

Zig's `InternPool` was not a micro-optimisation. It followed from four
properties of Zig, each stated in its design talks and in the self-hosted
compiler's history:

1. **The front end is the product.** Zig has its own back ends. The
   self-hosted x86-64 back end exists so that a debug build does not wait on
   LLVM. When nothing slow follows the front end, the front end's memory
   traffic is the build time, and data-oriented design is about memory
   traffic: fewer bytes, fewer pointers, more that fits in cache.
2. **Types are comptime values.** In Zig a function can return a type, and a
   type is compared, hashed and stored like any other comptime value. One
   pool for both, with equality as an integer comparison, is the natural
   representation of a language where the two are the same thing.
3. **Incremental compilation patches the binary in place.** An index that
   stays the same across updates is what lets a later update find what an
   earlier one decided. A pointer does not survive that; an index does.
4. **The workload is large.** Zig's own benchmark is the Zig compiler and its
   standard library, several hundred thousand lines, and semantic analysis is
   being made to run on several threads, which the pool was sharded for.

For each of the four, Nikaia's situation today is different. Each difference
could close, so each is a condition to watch, not a permanent answer:

1. **`rustc` follows the front end.** `docs/subprocess-cost.md` measured the
   whole `rustc` compile of `json.rs` at 1.72 billion instructions. If the
   front end is a few percent of a build, halving it is invisible to the
   person waiting. *This changes if Nikaia gets a back end of its own.*
2. **A type is not a value here.** ADR-088 D2 reaches a type's shape as
   members through a bound, with no `@typeInfo` and no function that returns a
   type. *This changes if build-time evaluation ever computes types.*
3. **Incrementality is per unit, and the boundary is text** (ADR-100). A
   ledger is re-read, not patched, so a stable index buys nothing across
   units. *This changes with an incremental mode inside a unit.*
4. **The workload is small.** The largest Nikaia unit is 1 197 lines. The
   whole corpus is about 6 200 lines. The compiler itself is 74 489 lines of
   Rust, and it is the program this road ends with. *This changes as
   self-hosting proceeds. The measurement has to say how the cost grows with
   size, not only what it is today.*

If the measurement comes out differently from Zig's answer, this is why. If
it comes out the same, Zig's reasons were not the only ones.

## 2. Decisions

### D1 — The ledger's types move whole, as the tree did

`Ty`, `Shape`, the ledger records of §1.1 and their small enums are declared
in Nikaia. They go in a tool module beside `ast.nika`, lowered by `nikaia
lower-std` and re-exported from `contracts`, so every reader keeps its path.
This is ADR-252 D1's route, used a second time.

### D2 — Four steps, each one shippable

* **(a)** This measurement (§3–§4), which decides the shape (D3).
* **(b)** The declarations move in that shape. The algorithms stay Rust and
  read them through the re-export.
* **(c)** The text form (parse and print of a signature) moves next to
  `ledger.nika`, which already reads the file's lines.
* **(d)** The algorithms (`fits`, `bind`, `substitute`, `qualify`, …) move,
  and with them the next ring.

**The shape is decided before (b) and not during it.** Interning later would
touch the checker's 633 lines a second time. Deciding first is what keeps the
move and the redesign apart, which is the lesson of Go 1.5 in §1.3.

### D3 — The rule the measurement is read against, written before it ran

Interning (a `u32` handle into a pool, as Zig and `rustc` do) is chosen
**only if both** of these hold on the corpus's largest programs:

1. **What interning removes is worth removing.** The instructions spent
   cloning, dropping and comparing `Ty` are at least **15 %** of the front
   end's instructions, net of what interning would add (a hash and a lookup
   for every type built).
2. **The front end is what the person waits for.** The front end is at least
   **10 %** of an end-to-end debug build of the same program.

It is also chosen if the measured growth with program size carries (1) past
15 % at the size of the compiler itself, 75 000 lines, even though it holds
today at neither.

Otherwise `Ty` moves as it is, a plain tree with a text form (D1), and §4
records the numbers that would reopen this decision.

### D4 — The prediction, written and committed before the measurement

These numbers are this record's guess, committed in a separate commit before
the first measurement ran, so that the result cannot be shaped to fit them.

* **P1.** The front end is **under 5 %** of an end-to-end debug build of
  `json`, the largest example (by instructions).
* **P2.** Cloning, dropping and comparing `Ty`, counted inclusively and
  including the allocations under them, is **3–12 %** of the front end's
  instructions on the larger programs. Best guess: about **6 %**.
* **P3.** On programs under 100 lines, the fixed cost of every run (reading
  `std.contracts`, 2 997 lines, and the sysroot) is **at least 40 %** of the
  front end.
* **P4.** Clones outnumber `==` comparisons by **at least five to one**, and
  `fits` is called more often than `==`. Interning's cheap equality therefore
  removes little: `fits` has `Unknown`'s rules and stays a walk either way.
* **P5.** Per program there are **fewer than 1 000 distinct** `Ty` values,
  and at least **20 times** as many are built or cloned. So interning would
  save memory, but the memory is small either way.
* **P6.** The `Ty` share is **roughly flat** with program size. It does not
  grow, because the checker's work per line does not depend on how many
  lines came before.
* **P7.** Therefore D3's rule answers **move as values**, and the conditions
  of §1.4 are what would reopen it.

The weakest of these is P6. The corpus spans only 15 to 1 197 lines, and a
size effect that starts later would not show in it.

### D5 — The method, and what could make it wrong

**The corpus.** Every `.nika` file in `examples/`, `tests/samples/`,
`benches/` and `crates/nikaia/tests/fixtures/`, each lowered on its own. Then
`nikaia lower-std`, which checks the eleven tool modules and `text.nika`.
`tests/errors/` is left out, because a program refused early measures the
refusal.

**The build.** The release profile with line tables
(`CARGO_PROFILE_RELEASE_DEBUG=1`), because that is the compiler people run.

**Two instruments, never mixed.**

* **Costs** come from `valgrind --tool=callgrind` on the **unmodified**
  compiler: instructions per function, inclusive. The count is the same on
  every run, so two compilers can be compared, which a timing on a shared
  virtual machine cannot do.
* **Counts** (clones, drops, `==`, `fits`, distinct values) come from a
  separate census build whose `Clone`, `PartialEq` and `Drop` for `Ty` are
  written out with a counter. That build's timings are never quoted.

The known sources of error, and what is done about each:

| # | error | direction | correction |
| :--- | :--- | :--- | :--- |
| E1 | **No real users' programs.** The corpus is examples, tests and the compiler's own tools, written by the people who wrote the compiler, and skewed toward what the compiler already does well. | unknown | Reported per program, never only as a total. Growth is fitted across sizes, and the rule (D3) is applied at an extrapolated size, not only a measured one. Where this changes the answer, the record says so; the conclusion is stated with the size range it was measured on. |
| E2 | **The lowering cache.** A second run reuses the lowering and measures nothing. | lower | `--no-cache` on every run. |
| E3 | **Fixed cost hides the per-line cost.** On small programs the run is mostly reading `std.contracts`. | lower | An empty program is measured, and each program is reported as a total and as the part above that baseline. |
| E4 | **Wall-clock on a shared machine is noise.** | either | Decisions rest on instruction counts. Wall-clock is reported only as a median of repeated runs, with its spread, to say what the counts feel like. |
| E5 | **Instructions are not time.** Zig's argument (§1.4) is cache misses, which an instruction count does not see: a pointer-chasing clone costs more than its instructions. | lower | Callgrind's cache simulation (`--cache-sim=yes`) is run too, and misses under the `Ty` functions are reported beside their instructions. |
| E6 | **Inlining hides clones.** A derived `clone` or `drop` the optimiser inlines into its caller is counted as the caller's. | lower | The census build puts `#[inline(never)]` on the written-out functions. Its total instructions are compared with the unmodified build's, and the difference bounds what inlining hid. |
| E7 | **What interning removes is less than what `Ty` costs.** Building a type still happens: it becomes a hash and a lookup. | higher | The number of types built is counted (census) and charged at a hash's cost, and the net is what D3 reads. |
| E8 | **The counting build is slower and different.** | either | Counts only, never costs, from that build (above). |
| E9 | **The test suite's own programs are not in the corpus.** About 1 800 tests write a program inline in Rust. | unknown | Acknowledged. They are small (mostly under 20 lines), so they would add programs rather than size, and E3's baseline would dominate them. |
| E10 | **One run of a deterministic count can still depend on the environment** (hash seeds, the path length, the sysroot's location). | small | Two runs of the same program are compared; a difference over 0.5 % is reported. |
