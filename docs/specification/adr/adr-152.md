# ADR-152: A Fixed-Size Array Is `Array[T, N]`

**Status:** Accepted · **Built:** yes, except the C field — see §5
**Date:** September 19, 2026
**Target Version:** Nikaia 0.0.31
**Related:** [ADR-284](adr-284.md) (a C value struct's `[f64; 3]` field),
[ADR-135](adr-135.md) §4 (a container that does not allocate) and D2 (a
literal takes its type from its use), [ADR-119](adr-119.md) (the bare-metal
target and its allocation profile), [ADR-293](adr-293.md) (an index out of
range aborts), [ADR-287](adr-287.md) (`comptime`), Part I 4.5 and 4.6

## 1. Context

Two records point here. [ADR-284](adr-284.md) leaves a C value struct's
`[f64; 3]` field undecided, and [ADR-135](adr-135.md) §4 leaves *a container
that does not allocate* — which the bare-metal target's `startup` profile
([ADR-119](adr-119.md)) will ask for on its first day, since a `Vec` needs an
allocator and that profile has none.

The question is the spelling and the literal. Rust's `[T; N]` is a **new type
form**; this language's type grammar already writes every parameterised type
with brackets — `Vec[T]`, `Shared[T]`, `HashMap[K, V]`.

## 2. Decisions

### D1 — `Array[T, N]`, in the bracket generic the type language already has.

```nika
struct Vector3 { parts: Array[f64, 3] }

let origin: Array[f64, 3] = [0.0, 0.0, 0.0]
```

`N` is a `comptime` integer ([ADR-287](adr-287.md)) — a literal, or a constant
that folds. No new type form, no second way of writing a parameter, and the
thing a reader already knows about `Vec[T]` transfers.

### D2 — It is a value, and it copies as its elements do.

An `Array[T, N]` is `N` elements inline: in a struct it is part of the struct,
as an argument it is passed as a value, and nothing is allocated. That is what
makes it the answer to both of the records above — the C field is laid out the
way C lays it out, and the profile with no allocator has a container.

### D3 — It is indexed as a list is, and an index out of range aborts.

`xs[i]` hands back a `T` — an index is the program's own arithmetic and a wrong
one is a bug ([ADR-293](adr-293.md), Part III A.2) — and `len()` is the `N`
it was declared with, known while the program is built.

### D4 — A literal takes the array type where the use asks for one.

```nika
let origin: Array[f64, 3] = [0.0, 0.0, 0.0]
```

Which is [ADR-135](adr-135.md) D2's rule for the **empty** list extended to a
full one: the literal takes the type its use gives it, and a use that asks for
`Array[f64, 3]` gets an array rather than a `Vec`. A literal with no use to
constrain it is a `Vec`, which is what that record already decided.

A literal whose length does not match `N` is refused naming both numbers,
because the length is part of the type.

## 3. Consequences

* Both open doors close with one type, and neither record needed its own.
* The bare-metal target has a container the day its profile lands.
* **What it costs:** one type in the ledger's type language with an integer
  argument — which is the part that is new, since every parameter so far has
  been a type — the literal's fit, and the length refusal.

## 4. What this does not decide

* **A slice of an array**, `&xs[1..3]`, which is the range and the view
  question together and which no program here has asked.
* **An integer as a parameter of anything else.** `Array` needs one; whether
  the type language gains them generally is a question with one program behind
  it, and this record answers only its own.
* **A default value for an unwritten element.** A literal writes every
  element, and `Array[T, N]` with no literal has no value.

## 5. What is built

Steps 1, 2 and 3. Step 4 waits, because [ADR-284](adr-284.md) is unbuilt —
`extern "C" struct` is still a parse error, so there is no C field to put one
in. `Array[T, N]` in an *ordinary* struct's field is built and tested.

**The integer argument is a `Ty` and not a second kind of argument.** The type
language gained `Ty::Count(i64)` and the AST's `Type` a `count`, so `Array` is
an ordinary `Named` with two arguments and everything that already walked a
type's arguments walks this one — `erase`, `parameterise`, `substitute`, the
crossing analysis, the ledger's render and parse. A second list beside `args`
would have had to be threaded through every one of them for one type's sake.

**It is compatible with nothing but itself**, which is the whole of D4's *the
length is part of the type*: `Array[f64, 3]` against `Array[f64, 4]` is the
ordinary argument-by-argument comparison, and no rule was written for it.

**D2 turned out to be three predicates already in the tree.** *It copies as its
elements do* is what `moves`, `moves_away` and `copies` each ask, one per
caller, and an array's answer is its elements' — so `Array[i64, 3]` is passed by
value the way a tuple of three `i64` is, and `Array[String, 3]` is lent the way
one of three `String` is. Without that the compiler wrote the `&` of
[ADR-094](adr-094.md) D1 around an array of numbers, which compiles and is not
what D2 says.

**The literal carries a position, and it is the only expression that does.**
Whether `[0.0, 0.0, 0.0]` is `vec![…]` or `[…]` is decided by its *use*, the use
is a type and the emitter has none ([ADR-288](adr-288.md)), so the answer is
handed over like every other one — but a statement's byte is not enough here,
because one statement may hold a list and an array both. So `list_lit` is an
`@=` rule and `Expr::ListLit` keeps the byte its `[` stands at.

**The use answers, and the element question stays with the use.** A literal
standing where an `Array[T, N]` is wanted comes back as the array of what its
elements *agreed* on rather than as the one that was asked for — so `[1, 2]`
where an `Array[&str, 2]` is wanted is refused by the `let`, the argument or the
field in that position's own words, under the code that position always used.
One message, and no code of its own for a mismatch that is not new. `NK1157` is
only the **length**, and it names both numbers because what a reader has to do
about it is count.

**Four positions write a use**: an annotated `let`, a call argument, a declared
result and a struct literal's field. A literal in any other position is a `Vec`,
which is what D4 says a literal with no use to constrain it is — and a `Vec` is
not silently accepted where an array is wanted, it is the ordinary mismatch.

**And the answer descends with the literal.** The first reading of *the use*
read the type it was given whole, which refused `let grid: Vec[Array[f64, 2]] =
[[1.0, 2.0], [3.0, 4.0]]` — a correct program, which is Part III C.4's class and
the one thing this may not do. So a `Vec[T]` is walked *through* where an array
is what it holds, and an array's own elements are walked the same way:
`Array[Array[i64, 2], 2]` lowers both levels. Every element is walked and not
only the first, because each one's length is its own refusal and each one's byte
is its own line for the emitter.

`len()` needs nothing: `[T; N]::len` is a constant below and the emitter's
existing `is_length` already writes the `as i64`. Indexing needs nothing either
— `nikaia_std::index::at` is written around every index already, and Rust's own
bounds check is D3's abort.
