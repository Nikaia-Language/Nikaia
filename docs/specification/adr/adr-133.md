# ADR-133: An Argument List of Options Alone Writes No `;` — the Leading Semicolon Is Gone, and It Is Not Optional

**Status:** Accepted · **Built:** yes — see §5
**Date:** September 19, 2026
**Target Version:** Nikaia 0.0.10
**Related:** [ADR-296](adr-296.md) D5 (the typed spread after the `;`), [ADR-108](adr-108.md) (a required argument is positional), [ADR-140](adr-140.md) D1 (the named struct literal goes, which is what unblocked the call half), Part I 5.1 (the subject ; config protocol)

## 1. Context

Part I 5.1 separates a call's **subjects** (positional, before the `;`) from
its **options** (named, after it), and a function whose only parameters are
options was called `query.execute(; target_age: min_age)`: a semicolon with
nothing before it, a shape no reader has seen in any language. The
specification itself wrote the call both ways — 17.1 has
`io::read_to_string(trusted: false)` — which said what the eye already knew.

The `;` earns its place where it separates two zones. Where there is only one
zone it separates nothing. The question was whether removing it costs the
parser anything, because an option is `name: value` and a subject is an
expression, and the two would now meet in one list.

## 2. Decisions

### D1 — A call whose arguments are all options writes them without a `;`, and so does a signature whose parameters are all options.

```nika
fn read_to_string(path: &str; trusted: bool = false) -> String   // two zones: `;`
fn execute(target_age: i64 = 0) -> Vec[User]                      // one zone: none

io::read_to_string("in.txt"; trusted: true)     // two zones: `;`
query.execute(target_age: min_age)              // one zone: none
```

The rule is what it always was — a subject is positional, an option is named,
an option has a default ([ADR-108](adr-108.md) and Part I 5.1) — and the `;`
stands **between** the two zones. Where one zone is empty there is nothing to
stand between, and the semicolon is not written.

### D2 — The leading `;` is refused, so there is one spelling.

`f(; opt: 1)` and `fn f(; opt: i32 = 1)` are parse errors whose message says
*an argument list with no subjects writes its options without the `;`:
`f(opt: 1)`*. Two accepted spellings would be worse than either alone: the
old one would keep appearing in code that reads the old pages, and a reader
would wonder what the difference is. There is none, so there is one form.

A mixed call keeps its `;` and keeps it required: `request(url, timeout: 60)`
stays refused as it is today, because the `;` is what makes *positional
before, named after* visible without counting parameters.

### D3 — It costs the parser one alternative, tried first.

Nothing in expression position begins with a name followed by a colon — a
struct literal begins `Name {`, a path `name::`, a call `name(`, and there is
no type ascription — so `name:` at the head of an argument list is options
and nothing else. The argument-list rule gains one alternative before the
present one: *a list of options*, tried first, which succeeds or fails on
the second token. The signature rule gains the same: *a list of parameters
with defaults*, tried first. The typed spread `...args: Self::dsl` of
[ADR-296](adr-296.md) D5 keeps its `;`, because it stands after a subject in
every driver that has one and is a zone of its own.

No AST changes: the call already carries subjects and options apart, and
the emitter and the checks read those. The number the record was written to
check: the tree writes the leading form in **two** places, both in the
specification's prose, and no example or test does.

## 3. Consequences

* A call with only options reads as a call with named arguments does in every
  language: `execute(target_age: 30)`.
* Part III 17.1 is right as written.
* One spelling per shape; the message names it.
* **What it costs:** two alternatives in the parser, and the message.

## 4. What this does not decide

* **Named subjects** (`request(url: "…")`) or **positional options**: the
  zones stay what they are.
* **Dropping the `;` in a mixed call** in favour of *named after positional*
  by convention; the `;` is what the language chose to make the rule visible,
  and this record does not reopen it.

## 5. What is built

**Both halves**, and the call half took a second record rather than more work.

**The signature half, and D3's premise had to be corrected to say which half
that is.** `fn execute(target_age: i64 = 0)` parses — the options-only list is one
alternative in `fn_params_body`, tried before the positional one and decided on
the token after the type, because it insists on the `= value` that makes a
parameter an option. A mixed signature keeps its `;` and keeps it required, and
`fn execute(; target_age: i64 = 0)` is refused with D2's message.

*Its own rule and not `config_param` reused*, which is a small thing with a sharp
reason: `config_param` ends in a `fail` for a missing default — the right message
**after** a `;`, where a parameter can only be an option, and the wrong one before
one, where `name: T` is an ordinary subject. A `fail` outranks the alternatives at
its position, so reusing it would have put *a configuration parameter needs a
default* on every plain signature that failed for some later reason.

**The call half was blocked, and D3 was why.** *Nothing in expression position
begins with a name followed by a colon — a struct literal begins `Name {`* left
out the other struct literal: Kap 4.2's `Stats(min: first, max: first)`, which is
`execute(target_age: 30)` spelled identically. The parser tried the literal first,
so D1's call form was read as a struct literal, and whether this language lets two
constructs share a spelling was a question rather than work.

**[ADR-140](adr-140.md) D1 answered it by removing one of the two constructs**,
and [ADR-286](adr-286.md) answered the clause it left over — *a rule for a name
that is both a type and a function* — by refusing the second declaration.
The named literal is gone; `Name { … }` is the struct literal and
`name(field: value)` is a call with options. So the parser's own rule is enough
after all and D3's premise is true as written — *since* that record and not
before it. What tells a mistake apart is `NK1146`, in the checker where the
receiver's type is: a call carrying options whose callee **declares a type** is
the old spelling, and the message names the braces.

**The leading `;` is refused at a call too**, with D2's message, and that closes
the asymmetry the build had been in: one spelling per shape, in a signature and
at a call.

**A driver's deferred parameters write no `;` either.** D3 says the typed spread
of [ADR-296](adr-296.md) D5 *keeps its `;`, because it stands after a subject in
every driver that has one* — which is true of the **signature**,
`pub fn execute(&self; ...args: Self::dsl)`, and not of the call: a receiver
stands outside the parentheses, so `query.execute(; target_age: 30)` has an empty
zone in front of the separator exactly as any other options-only call does. It is
`query.execute(target_age: 30)` now, which is what Part II 10.5 already wrote.

**Three defects the record was written to name, and all three were older than
it.**

*A call whose arguments are all options lowered to invalid Rust.*
`execute(; target_age: 30)` came out as `execute(, 30)`: the comma the emitter
writes *between* arguments, written before the first one because such a call has
nothing in front of it. `rustc` answered about a file nobody wrote, which is
[Part III C.1](../30-nikaia-tooling.md)'s class, for the **only** spelling such a
call had. Nothing in the corpus declares a function whose parameters are all
options, which is why it stood.

*A struct literal naming nothing this compiler declares said nothing at all.*
The arm that checks a literal's fields `continue`d over a type with none, so
`execute(target_age: 30)` lowered verbatim and came back as *cannot find struct
`execute`* — C.1 again, and the very hole `NK1135`
([ADR-096](adr-096.md)) was built to close for a written annotation. That is the
silence that let the collision go unnoticed through two records, and it is
`NK1135` now for the brace form — the only form that can still make the claim,
since `Widgit(size: 3)` is a **call** to a name nothing describes and silence is
the correct answer to one (C.4), exactly as `Widgit(3)` beside it has always got.

*And a method call's options were **dropped**.* `q.execute(target_age: 30)` came
out as `q.execute()`, because the emitter fills options from the callee's
contract and finding a *method's* entry means resolving the receiver, which it
cannot do ([ADR-288](adr-288.md)). `rustc` answered about the arity of a file
nobody wrote — C.1 a third time, and reachable by the `;` form just as well, so
older than the spelling that makes it easy to hit. The checker records the
declaration's option order now (`method_options`), which is the hand-over
`lent_args` and `nullable_args` already use, and the emitter writes the same fill
it writes for a call by name. **Part III 15.1's `script.exec(msg: message)` is
the block that proves it**: it lowers, and the specification's lowering floor
went back up from 47 to 48 with it.

*Thirteen tests* in `crates/nikaia/tests/options_only.rs`.
