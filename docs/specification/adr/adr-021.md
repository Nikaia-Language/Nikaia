# ADR-021: The Build Cache Is Ours, and the Lockfile Is Its Key

**Status:** Accepted
**Related:** [ADR-002](adr-002.md) D3 (the germ of this),
[ADR-003](adr-003.md) D2 (the orchestrator owns caching),
[ADR-001](adr-001.md) D1 (the toolchain D2 records),
[ADR-005](adr-005.md) D3 and D8 (the ledger D10 keeps separate),
[ADR-020](adr-020.md) (the ledger as its own file)

## 1. Context

The specification promised fast builds in three places and never said how.
`nikaia.lock` was a "deterministic cache key" for compile-time I/O; the ledger
was said to double as an incremental cache key; the orchestrator was where
"hash-based incremental compilation checks" happened. Three descriptions of
caching, no statement of what is hashed, what invalidates what, or where
anything is stored.

A cache key is the one thing that cannot be widened later without invalidating
everything built under it, and both ways of getting a key wrong are silent.

An external compilation cache is the obvious alternative, and it is not taken —
not because such caches work badly: they cache the wrong
layer. They memoise `rustc` invocations, while the expensive repeated work in a
Nikaia build is macro evaluation, grammar expansion and lowering — all of which
happen *before* `rustc` is reached, and none of which `rustc` ever sees.

## 2. Decisions

### D1 — There is no external compilation cache. Caching is the orchestrator's job.

No second caching system to configure and keep in step.
[ADR-003](adr-003.md) D2 already makes the orchestrator the owner; this makes
that ownership exclusive.

Cargo's own fingerprinting continues to cover the *Rust* workspace and is not
replaced or wrapped.

### D2 — One committed file records everything that determines a build.

`nikaia.lock` holds, per entry: the SHA256 of every external file read at
compile time, the SHA256 of every `.nika` source that took part, resolved
dependency versions, the **exact toolchain used**, and the **compiler's own
identity** (D3).

Splitting the record — assets here, toolchain there — produces a lockfile that
cannot answer the only question a lockfile exists for: *does this build the same
thing for you as for me?* Leave out an asset or the toolchain and the answer is
no, and the file does not know it.

### D3 — The compiler's own identity is part of the key.

Stated separately because it is the most dangerous omission available. The
emitter is a pure function from
source to Rust — which is what makes caching sound at all — but it is a function
*we edit*. Same input, same toolchain, changed emitter, different output.
Without it the cache serves artifacts from the previous emitter and the build is
silently stale. The failure lands only on compiler developers, which is
precisely why it would survive undetected.

**"Version" has to mean a fingerprint, not a version string.** The obvious
reading is `CARGO_PKG_VERSION`, and it is wrong: it stays `0.1.0` across every
edit to the emitter, so the key would sit still exactly while the thing it
identifies moved. What goes in is a SHA256 over the sources that decide the
output — the compiler's own `src/`, and the `std` ledger it bakes in. A version
string is a *claim* about the compiler; a fingerprint is a *measurement* of it,
which is the same distinction D4 draws between a manifest and a lock.

### D4 — Declaration and record are different files.

`nikaia.toml` declares what the project requires; `nikaia.lock` records what was
resolved and used. A constraint and a measurement can coexist; two constraints
cannot — which is what resolves the drift that would otherwise appear between
`rust-toolchain.toml` and the lock.

The `toolchain` field in the *ledger* is not part of that drift. Per D10 the
ledger travels with a published package while the lock does not, so it arrives
downstream alone and must describe itself; otherwise a consumer cannot tell a
contract diff caused by a compiler upgrade from one caused by their own code.
Duplication a file needs in order to be readable on its own is not drift.

### D5 — Build-time choices enter the key but are never written to the lockfile.

*Changed by [ADR-292](adr-292.md) D7: there is no `ordering` switch, so it is not a dimension; the two build switches that remain are.*

The two build switches, opt-level and backend are decisions made at invocation
time, not facts about the inputs. Hashed into the key, never persisted — a lockfile that
records them is rewritten whenever a developer switches either, producing a
committed diff carrying no information and conflicts between developers who
build differently.

Both **must** be in the key. Either setting lowers the same source to different
Rust, so a key without them hands back one build's artifact for the
other — and the test that exists to catch exactly that divergence would compare
an artifact against itself and pass trivially. **A cache is allowed to make a
test faster. It is never allowed to make a test vacuous.**

### D6 — One key per translation unit, never one key over the file.

The key for a unit is the hash of *that unit's* inputs, not the hash of
`nikaia.lock` as a whole. Hashing the whole file is the easy implementation and
destroys the property the cache exists for: one changed asset would invalidate
every unit. Smart invalidation is not a later optimisation — it is a consequence
of choosing the granularity correctly the first time.

### D7 — Every dimension of the key is enumerated explicitly.

A key can be wrong in two directions, and both are silent:

* **Too much** — absolute paths, mtimes, ambient environment, a build timestamp.
  The key varies when nothing meaningful changed and the cache never hits. Looks
  like a cache that is merely useless.
* **Too little** — D3's compiler identity being the standing example. The key
  fails to vary when something meaningful did change. Looks like a
  miscompilation.

So the key is assembled from an explicit, reviewable list. Nothing is captured
incidentally, and nothing that determines the output is left to be remembered.

For a git dependency, hash **content**, not the revision: Cargo fingerprints
such a dependency on its commit, so local edits to the checkout are silently
inert. A bug to learn from, not to reproduce.

### D8 — Artifacts live in a content-addressed store outside the repository.

`target/nikaia/cache/`, addressed by the D6 key, git-ignored. The lockfile
records inputs; the store holds outputs. Because the key is derivable from the
lockfile plus the D5 choices, the store needs **no index of its own** — and the
absence of a second bookkeeping structure is the point, since an index that can
disagree with the lockfile is a cache that can be wrong.

The precondition, determinism, already holds: it is why `--explain` rebuilds the
source map from source rather than storing it ([ADR-300](adr-300.md) D2).

### D9 — Cranelift is a supported option for development builds, not the default.

Measured on this workspace, Cranelift is fully compatible and buys about one
second on an incremental rebuild and nothing on a full build: at `opt-level = 0`
the cost is the dependency graph and the proc macros, not codegen. Defaulting to
it would oblige every contributor and CI job to install a toolchain component
these numbers cannot justify.

It is not switchable from this repository: the switch is `[profile.dev]
codegen-backend`, which Cargo has not stabilised, so turning it on costs a
nightly toolchain Nikaia does not use ([ADR-001](adr-001.md) D1). Revisit when a
single crate becomes large enough for codegen to dominate its rebuild.

A backend nothing implements is refused with an error naming this decision,
never accepted and quietly replaced by the default. The message offers no
remedy, because there is none: a refusal that named something to install would
send the reader after a build that does not exist.

### D10 — The contract ledger stays its own file.

`nikaia.contracts` does not merge into `nikaia.lock`. Two properties make that
impossible rather than merely inadvisable:

* **The ledger is distributed; a lockfile is not.** Published packages ship
  their ledger so downstream builds get stable contracts. A lockfile is the
  opposite by definition — a library's is ignored by its consumers. One file
  would have to be both shipped and not shipped.
* **`--locked` would mean two contradictory things.** For the ledger it means
  *regenerate and compare byte for byte*, sound because the ledger is a pure
  function of (source tree, toolchain). For a lockfile it means the reverse,
  *do not re-resolve*, and it must: resolved dependency versions are not a
  function of the source tree at all. That is the entire reason lockfiles exist.

**The shared phrase "cache key" is retired here, because it names two different
mechanisms:**

| | consulted | question it answers |
| :--- | :--- | :--- |
| `nikaia.lock` | **before** any work | *Do I need to start at all?* — a skip decision |
| `nikaia.contracts` | **after** inference | *Which callers must be re-checked?* — a blast radius |

The lock can be read and answered without compiling anything. The ledger cannot:
it is compared against contracts that exist only once inference has run. They
are complementary stages of one build, not two implementations of one idea.

### D11 — Caching is on by default, and that decides where the files go.

Reusing an unchanged lowering is the difference in feel between a Nikaia build
and a Rust one, and a default nobody types is not that difference. `--no-cache`
is the way out, kept for debugging the emitter.

Being the default turns *where files go* into a requirement: nothing may be
written into a directory the user did not ask us to write into.

* **In a project** — `nikaia.lock` at the root, committed; the store in
  `target/nikaia/cache/`. A unit is named by its path *below the root*, never
  absolutely, since D7's first failure direction is a key that moves with the
  checkout.
* **Outside one** — a one-off transformation, where a committed lockfile would
  have nothing to be committed to. The input record moves beside the store in
  the user's cache directory and the source tree is untouched. Entries are still
  shared across projects: the key is content-addressed and holds no path, so two
  identical sources hit the same entry.

### D12 — A cache failure degrades the build; it never fails it.

A read-only checkout, a full disk, a CI sandbox, a corrupt lockfile: each must
cost the *next* build its speed and leave *this* one working. **A cache that
turns a succeeding build into a failing one has taken something the user had,
and no amount of speed pays for that.**

A store that cannot be opened is reported on stderr and the build proceeds; a
lookup that cannot read is a miss rather than an error. The library still
returns `Result` — it should be able to say what went wrong — and the *caller*
decides the answer is not fatal.

### D12.5 — Coexisting is bounded: the oldest trees are collected.

D7 says dimensions **coexist; they do not share**, and the compiled-`std` tree is
where that costs real disk: it is a whole Cargo target directory, and every new
toolchain, target or codegen table starts another one. Unbounded, that reached
gigabytes and failed builds for want of disk: **a cache with no eviction is a
disk leak** — coexisting is right, coexisting *forever* is the defect.

The newest three are kept and idle ones below that are removed. Three because
switching target or codegen table back and forth is a normal thing to do, and
evicting on every switch turns a cache into a tax. "Idle" is an age floor of an
hour on top of the count, because the tree a *concurrent* build is writing into
must never be the one that goes — and the build marks its own tree in use before
sweeping, so it can never collect itself.

**A program leaves the tree with its project.** Every project builds its program
in the shared tree, under a crate name carrying the project's tag, and the
binaries are tens of megabytes each. A build records which directory its tag
belongs to and removes the artifacts of every tag whose directory is gone: a
project that no longer exists is not building, so nothing is taken from a build in
flight. Rejected: one tree per project, which is the per-project `std` this tree
exists to avoid.

Ordered by a marker file this writes, not by the directory's own timestamp: Cargo
writes into subdirectories, so a tree used every day can carry the mtime of the day
it was made. And a sweep that fails is D12's rule again — a fuller disk, never a
failed build.

### D13 — A hit skips the checks too, and what that costs to be allowed.

A hit serves the whole build: nothing is parsed, `sync`-checked, lowered or
inferred. Sound for exactly one reason — **only a build that passed every check
is ever recorded.** A failing check returns before anything reaches the store,
so an entry's existence *is* the statement that this input passed. Skipping the
check on a hit is reading its memoised result.

The price is D7 applied strictly: every input those checks consult must be a
dimension. If a future check reads something not on that list — an environment
variable, a file found at run time — it becomes a dimension in the same commit
that adds the check, or the cache starts approving inputs nobody checked.

Two things a hit does **not** skip:

* **`--locked`.** Whether the *committed* ledger still matches is the user's
  question about the working tree, not the compiler's about the source. A cached
  build has as much to answer for there as a fresh one.
* **Producing the outputs — all of them.** A build makes the emitted Rust *and*
  the ledger, so both live in one envelope under one key. Separate keys would
  allow a half-hit with nothing to notice it. An envelope lacking an artifact
  the current build needs is a miss, which makes adding an output a safe change
  rather than a silent gap.

## 3. Consequences

**Bought:** one answer to "what determines this build", in one reviewable file;
invalidation proportional to the change; and a cache over macro evaluation and
lowering — the work that is actually repeated — rather than only the `rustc`
call at the end.

**Paid:** disk, twice over. Dimensions coexist rather than share, so each
combination of build-time choices occupies its own entries. That is the correct
trade and it is stated rather than discovered: the cache is larger so that it is
never wrong and never thrashes. D12.5 bounds the compiled-`std` trees.

**Not decided:** the lockfile's concrete syntax, the hash framing, how the store
under `target/nikaia/cache/` is collected. Those follow the implementation. The one structural question
decided rather than deferred is D10, because deferring it would have left the
orchestrator free to merge two mechanisms whose distribution and `--locked`
semantics contradict.

## 4. Measurements

This workspace, `dev` profile.

**Cargo keys its cache per dimension, and dimensions never evict one another** —
the property D7 protects. Steady state costs nothing; a first `cargo clippy`
after a `cargo build` rebuilds 56 crates not as waste but as a parallel artifact
set. Dimensions **coexist**; they do not **share**.

**Cranelift** builds the whole workspace, passes the test suite and produces
identical output, at 25 s against 26 s cold and 1 s against 2 s incremental (D9).

## 5. Resolved dependency versions

`orchestrator::cache` holds the key, the store and the lockfile; every dimension
of D7's list is named in `Key::build` and nowhere else.

D2's resolved dependency versions come from Cargo: a project build generates a
`Cargo.toml` ([ADR-002](adr-002.md) D1) and Cargo resolves a `Cargo.lock` beside
it under `target/`. Without carrying them across, `nikaia.lock` would answer
*does this build the same thing for you as for me?* only about the Nikaia half.

* **Recorded** — `[dependencies]` in `nikaia.lock`, the whole resolved graph
  rather than the lines the author wrote, one entry per name holding a list of
  versions. The whole graph because a transitive crate that resolved
  differently on two machines is a different build; a list because two majors
  of one crate in one graph is ordinary, and a record that keeps one of them is
  not the whole answer. Read out of Cargo's answer rather than computed, which
  is D4's distinction in the small: `nikaia.toml` declares `version = "1.5"`
  and the lock records the `1.13.1` that turned into.
* **Not in the key**, deliberately. Stage 0 lowers name for name, so a
  dependency bump changes the machine code Cargo produces and never the Rust
  this compiler emits — and the envelope a key holds is exactly that Rust and
  the ledger (D13). Hashing the versions would invalidate every unit's lowering
  for a change that cannot alter one, which is D7's **too much** direction, on
  the half Cargo's own fingerprinting already covers (D1). D13's obligation is
  met the other way round as well: no check the cache lets a hit skip consults
  a resolved version, so this is a dimension that must *not* be added rather
  than one that is owed.

Written after `cargo` returns, because that is when the versions exist, and
only for a build that succeeded. A failure to write it warns and leaves the
build alone (D12), and an unchanged record is not rewritten, so a committed
file does not turn up modified after a build that changed nothing about it.

What `--locked` would mean for the lock is fixed by D10 — *do not re-resolve* —
and it is not passed to Cargo; the flag is the ledger's ([ADR-005](adr-005.md) D8).
