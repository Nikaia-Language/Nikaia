# ADR-016: The UTF-8 Check Is Divided, Not Skipped

**Status:** Accepted · **Built:** yes
**Closes:** "UTF-8 validation is serial", [ADR-015](adr-015.md) §3
**Related:** [ADR-283](adr-283.md) (`&` is a view marker — which is why D1 is
not optional), [ADR-296](adr-296.md) D19 (nothing but the
driver), [ADR-296](adr-296.md) D10 (chunk count does not change results)

## 1. Context

Two numbers did not sit comfortably together: at `user_parallelism = yes` the compiler parses
8 million rows in 0.19 s, and `fs::map` validates the file as UTF-8 first,
serially, at a rate that would cost ~7.6 s on a 13 GB input. The reconciliation
is only that these are two file sizes — at 105 MB the check is ~60 ms and is
*inside* the 0.19 s, about a third of it.

Two fair questions follow. Why is the check there at all, and why is it that
slow?

## 2. Decisions

### D1 — The check stays, because it is what makes a view a `&str`.

`fs::map` hands the parser a `&str` over the mapped pages, and every slice the
grammar cuts out of it is a `&str` into those same pages. Removing the check
does not make the program slightly less careful; it makes it
`from_utf8_unchecked` over bytes nobody controls, and every view after it
undefined behaviour in code the user wrote safely.

Not an argument from principle. Built with the check removed, the flagship
prints

```text
{Hamburg=12.0/12.0/12.0, \xffBad=3.0/3.0/3.0}
```

for a file with one stray byte — a station name that is a `&str`, is not UTF-8,
and is formatted without complaint on the far side of a `Deref` that promises
otherwise. The check is load-bearing.

What may eventually skip it is an assertion the *user* makes, in the shape the
language already has three times over (`@frame(…, unchecked)`,
`fs::map(…; trusted: false)`, `dsl backend::x86`) — a hatch the source opens and
the ledger records, never a default the runtime picks. §4 says why that is not
worth building yet.

### D2 — The check is chunked at character boundaries, and reports the earliest failure.

`fs::map` cuts the mapping into one piece per core and validates in parallel. A
cut walks forward off a continuation byte, at most three times, so every piece
begins where a character begins: no sequence is split, and no piece can accept a
truncation the piece before it left behind. A failing piece contributes
`chunk_start + valid_up_to`, and the answer is the **minimum** — so a rejected
file names the same byte however many cores looked at it, which is
[ADR-296](adr-296.md) D10's promise applied to validation.

Below 1 MiB it runs in one piece: waking the pool costs more than the check.

Tests hold it to the serial validator as the oracle: a multi-byte input over the
threshold; a corruption at every cut ±8 bytes and at a stride coprime with the
character width, each compared to the serial verdict *and offset*; one break per
chunk, to check that the first is reported; and the small-input path.

### D3 — `user_parallelism` does not reach into `std`, and does not here either.

The obvious objection: `user_parallelism = no` means `Parallelism::Off`, so should
`fs::map` validate on one core there? No — and it could not, because
[ADR-296](adr-296.md) D19 says nothing but the DSL driver reads the switch.

What the switch governs is the *fold*: whether the input is cut into pieces
whose results are merged. The UTF-8 check has no result to merge. It returns the
same verdict and the same offset on one core and on sixty-four (D2), so how many
cores ran it is not observable in the program — it is a library function doing
the fastest correct thing.

**The switch bounds the user's code, not every function a program calls**
([ADR-037](adr-037.md) D2).

## 3. The measurement

8 million rows (105 MB, ~1.5 % of bytes multi-byte), 4 cores, best of five.
`no check` is the same program with validation deleted — the floor, not a
candidate.

| | `user_parallelism = no` | `user_parallelism = yes` |
| :--- | ---: | ---: |
| serial check | 0.57 s | 0.19 s |
| **chunked check** | **0.52 s** | **0.14 s** |
| no check at all | 0.51 s | 0.13 s |

The check alone: **63.7 ms serial (1.7 GB/s) → 16.5 ms on four chunks
(6.6 GB/s)**, a clean 3.9×. Projected to 13 GB: ~7.6 s → ~2.0 s, and it now
divides by the core count like everything else.

**What is left to gain by removing it entirely is 10 ms** — 2 % sequential, 7 %
parallel — against the output in D1. That is the answer to "why not switch it
off": after dividing it, there is almost nothing left to switch off.

Instructions per row are **unchanged at 659**: chunking moves work between
cores, it does not remove any. Deleting the check gives 629, so the check is
30 Ir/row — **4.5 % of the instructions and 11 % of the time.** That gap is the
whole story: it is not arithmetic, it is a second pass over 105 MB of memory,
and the parse then walks the same bytes again.

**Why 1.7 GB/s and not 10.** Measured against an ASCII-only twin of the same
file — every `ü`, `ã`, `Ü` folded to its ASCII letter, same length, same rows:

| input | validation rate |
| :--- | ---: |
| ASCII only | **10.3 GB/s** |
| the real file (1.5 % multi-byte) | **1.7 GB/s** |

The standard validator has an ASCII fast path over machine words, and a single
non-ASCII byte drops it to the per-character path. Station names like
`São Paulo`, `Zürich`, `Ürümqi` put a multi-byte character roughly every
68 bytes, often enough that the fast path never gets going. So the rate this
started from was never "the cost of validating UTF-8"; it was the cost of *this*
validator on data that keeps interrupting it.

## 4. Rejected and deferred

* **Switch the check off by default** — 10 ms against the `\xff` above (D1).
* **A SIMD validator** — it would plausibly beat the chunked check on one core,
  but it is a new dependency in `std` for 10 ms of a 140 ms program, where the
  chunked check gets 3.9× with fifteen lines and no new trust. Reconsider when
  the check is again the largest thing left. (It would help more than the table
  suggests, for the reason in §3.)
* **An assertion that skips the check**, as a sibling of `trusted: false` —
  [ADR-010](adr-010.md)'s hatch is about *hashing*, not encoding, and the two
  must not share a keyword: one says "I accept a slower hash", the other says "I
  accept undefined behaviour if I am wrong".
* **Fuse the check into the piece — right, and deferred.** Where the pieces run
  in parallel the
  driver already cuts the input and hands each piece to a thread. Validating a
  piece on the thread about to parse it would be parallel *and* cache-hot: one
  traversal instead of two, which is exactly where the
  11 %-of-time-for-4.5 %-of-instructions gap lives. It needs the parser backend
  to take bytes and produce text, which is a language-level decision about what
  a view *is*, not a change to one file.

## 5. What is still not true

* **The check is a separate pass.** §4's last item is the fix, and it is not
  built.
* **A 13 GB run has never been made.** Every figure here is measured at 105 MB
  and projected; the projection assumes the rate holds, and page-fault behaviour
  at 13 GB is not something a 105 MB file can tell you.
