# ADR-121: The Ring's Park Hears the Bell, So Every Worker Operation Can Wake the Executor

**Status:** Accepted · **Built:** yes, except `io::lines` — see §5
**Date:** September 16, 2026
**Target Version:** Nikaia 0.0.8
**Related:** [ADR-038](adr-038.md) D3 and D4 (I/O split by kind; the runtime
runs before the first statement), [ADR-055](adr-055.md) D3 (the executor is
ours and drives the I/O that is already there), [ADR-019](adr-019.md)
(standard input), Part III 13.3b (`io-method`)

## 1. Context

The runtime finishes an operation in one of two ways. On a machine with a
completion queue the kernel does the read and the ring reports it; where the
queue is missing or forbidden, a worker thread does it and rings a **bell** —
a count the executor's park hook watches. The two paths were built for the
same operations and differ in one thing: while the executor parks on the
ring, it waits on the ring's own count of outstanding jobs, and a worker's
reply is not one of them. So a worker's reply cannot wake a ring park, and
no future may be fed from the worker path: `block_on` spins where `main` is
alone and panics otherwise, with its own message about a waker nobody
arranged. A test in `crates/nikaia-std/src/rt/mod.rs` holds this and goes
red the day it stops being true.

Two things rest on it. Standard input is a worker operation, which is why
`io::read`, `io::read_to_string` and `io::lines` are `async fn` whose bodies
block the thread they always did. And `rt::io::wait`, the readiness half of
the runtime built for sockets, can be blocked on and not awaited — which is
the piece an HTTP server needs first.

The entry that proposed wiring standard input to readiness would not have
worked: the defect is the park, not the input.

## 2. Decisions

### D1 — The ring carries an eventfd, always armed, and the bell writes to it.

Where the executor parks on the ring, one file descriptor is registered on
the ring with a read always in flight. `ring_the_bell` writes to it. A
worker's reply therefore completes a ring job, the park returns, and the
executor runs whatever the worker's reply made ready. The two paths stop
differing in what they can feed: **every** worker operation is awaitable —
standard input, socket readiness, and whatever a later operation carries.

### D2 — The bell's completion is not mistaken for an operation's.

The eventfd read carries its own user data, is answered by re-arming it, and
is never handed to a future as a result. The count of outstanding *jobs* the
park consults excludes it, so a park with only the bell armed still sleeps.

### D3 — A hang is the failure this may not have, so it is a panic and a test.

The worst failure a runtime can have is a park nobody wakes. `park`'s own
`false` is already a loud panic rather than a wait; this keeps that standard.
The test that today asserts a worker reply does **not** wake a ring park is
inverted and kept: a worker reply wakes a ring park, and a future fed from a
worker completes under `block_on` with other tasks alive.

### D4 — Standard input stays on the worker path, and becomes awaitable through it.

No second read shape for standard input, no ring path for a stream that has
no size to `stat`. `io::read`, `io::read_to_string` and `io::lines` suspend
because the path they were always on can now wake the executor. The same is
true of `rt::io::wait`, which is what the server's socket layer awaits.

## 3. Consequences

* Standard input suspends, which closes the entry [#267](https://github.com/Nikaia-Language/Nikaia/issues/267) carried as
  *standard input is `async` and does not suspend*.
* `rt::io::wait` is awaitable, which is the first thing the HTTP server's
  socket layer needs.
* **What it costs:** one file descriptor and one always-armed submission per
  ring, and the care D2 describes. Nothing in the language.
* **Where the ring is absent** — the fallback path, `wasm32` — nothing
  changes: the park there already watches the bell.

## 4. What this does not decide

* The socket layer itself, and the server on it ([ADR-038](adr-038.md) §4.5).
* Whether standard input should ever go to the ring on Linux for throughput;
  nothing measured asks for it.

## 5. What is built

**D1, D2, D3, and D4 except one entry.** The ring carries an `eventfd` with a
poll always armed and its own user data (`u64::MAX`, a number no slot index can
wear); `ring_the_bell` writes to it as well as bumping the count the fallback
park watches; the bell's completion is answered by draining the descriptor and
arming the next poll and is not counted among the ring's outstanding jobs, so a
park with only the bell armed still sleeps. `rt::io::wait` has a future beside it
(`rt::io::waiting`), and `io::read` and `io::read_to_string` are the reads they
always were, performed on an I/O worker and awaited.

**A poll and not a read**, which the record did not say and which is what keeps
`uring`'s soundness rule out of the bell entirely: `IORING_OP_POLL_ADD` hands the
kernel a descriptor and no buffer, so there is nothing to keep alive and nothing
to move. The eight bytes are taken afterwards by an ordinary non-blocking read on
a descriptor the poll has just called readable.

**Three things the building found that the decision had not named.**

*The descriptor lives beside the lock and not inside it.* The thread that parks
is inside `io_uring_enter` **holding the ring's lock**, and the thread that rings
is an I/O worker: a worker that had to take that lock to ring could not ring at
all, because it would be waiting for the very thread it is trying to wake. So
the runtime keeps the number and hands it to the write. Per runtime and not per
process, which one hang taught: a test that builds a second `Runtime` gets a
second ring with a bell of its own, and publishing that one as *the* bell left
the process's own park deaf.

*The bell coalesces, so the park needs the count as well.* One descriptor serves
every worker, and a ring another thread's reap has already drained leaves nothing
on this ring to wait for. The park therefore checks the fallback's own generation
— read before the poll that found nothing to do — **inside the ring's lock**,
which is the whole of why a wake cannot be lost: draining needs that lock, and
`ring_the_bell` bumps the count before it writes, so anything that could already
have been drained shows up here as a count that has moved.

*A bounded park has to be bounded on this path too*, which is D3 read strictly.
Before D1 the ring park answered *nothing to wait for* about a worker operation
and `exec::block_on` said so loudly; after D1 it waits for one, and a bell that
is not heard would be a hang where there had been a panic. So a park with a limit
uses `IORING_ENTER_EXT_ARG`, whose bound the kernel keeps for one
`io_uring_enter` — no timeout submission to cancel, no timespec the kernel holds
past the call — and `ETIME`, a kernel too old for `EXT_ARG`, and a refused
submission are all *nothing moved*, which is what a caller with a deadline asked
to be told.

**And `Op::Readiness` carries a duplicate of the descriptor** rather than its
number. While the only surface was `io::wait` the caller was blocked for the
whole of the wait and its borrow was the guarantee; a future may be dropped while
the operation is in flight, so the borrow is not there to be had. A `dup` shares
the file description, which is what readiness is about, and costs one syscall.

**What is left is `io::lines`**, and the reason is the language rather than the
runtime. A step of it is an `Iterator::next`, and a suspension point inside one
is `while let Some(x) = s.next().await` in the language below — a `Stream` trait
Rust has not stabilised and a `for` over a stream this language has not decided.
[#182](https://github.com/Nikaia-Language/Nikaia/issues/182) carries that as the half it always called the larger one.

*One of the three needs a generous bound, and what it is generous about is not the
mechanism.* `io_workers` is **one** by default and the harness runs the suite in
parallel, so every in-process readiness wait queues behind the others on one
thread and a wait ahead holds it for as long as its own timeout. A hang is
unbounded, so a minute tells the two apart; ten seconds went red under a loaded
whole-workspace run and green on its own. **And its waiting task is a worker
operation rather than a `Slot`**, which the first version got wrong: a `Slot`
filled from an ordinary thread is outside the runtime's accounting, so
`pending()` can be zero while a task waits for one — and `exec::block_on` then
panics about a waker nobody arranged, correctly, because nothing it can see will
move.

*The tests, and each one was watched go red with the bell unwired:*
`a_worker_operation_wakes_the_park_on_either_path` (the inverted one — it
asserted the defect and now asserts the fix),
`a_future_fed_from_a_worker_finishes_under_block_on`, and
`standard_input_is_read_on_a_worker_and_awaited`. The last two bound themselves,
one by driving `block_on` on a thread it joins with a deadline and the other by a
watchdog in the child process, because D3's *a hang is the failure this may not
have* applies to the test that reports it.

**Found at 0.0.259, and fixed: an answer reaped by another thread.** The ring
is one per process, and a poll or a park on any thread takes every completion
off its queue - so a read's answer is often reaped by a thread that is not
waiting for it. D3's ordering (the count read before the poll, asked first in
the park) only covers what moves the count, and a ring completion did not: the
reader's park waited for a completion that had already come. Where the read
needed another turn, which only its own poll submits, that wait lasted as long
as any other operation was outstanding, with the ring's lock held and every
thread behind it - the arm64 CI job hung six hours in
`fs::many_threads_reading_and_writing_at_once_each_get_their_own_answer`, and
`a_future_fed_from_a_worker_finishes_under_block_on` beside it failed waiting
for the lock. `file_ring::Ring::answered` counts operation completions reaped;
`rt::with_ring` moves the generation when a call reaped any, while the ring is
still held, so a park after it returns.
`an_answer_another_thread_reaps_moves_the_generation` fails without it.
