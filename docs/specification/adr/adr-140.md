# ADR-140: Five Places Where One Thing Had Two Spellings, and Which One Stays

**Status:** Accepted · **Built:** yes — see §5
**Date:** September 19, 2026
**Target Version:** Nikaia 0.0.18
**Related:** [ADR-133](adr-133.md) (an options-only argument list), [ADR-286](adr-286.md) (`use` brings nothing in), [ADR-296](adr-296.md) D24 (a grammar is entered by a call), [ADR-281](adr-281.md) D2 (a hull you can observe, you write), Part I 4.2, 7.1 and 9.1, `docs/language-review.md` §3.3

## 1. Context

`language-review.md` §3.3 found five places where the language says one thing
two ways. None of them is a bug and each of them is a reader stopping to ask
which they are looking at:

* `Stats(min: first, max: first)` and `Reading { name, temp }` both build a
  struct — and `Stats(first)` calls the anonymous constructor, so `Foo(x: 1)`
  goes round the constructor's invariants and `Foo(1)` goes through them,
  told apart by a colon;
* a type is constructed by an **anonymous constructor** in this language's own
  code and by `Type::new()` in `std`;
* a path is written `Op::Times` and `Json.value(input)`;
* `throws` and `sync` stand on either side of `->` and the parser takes both;
* `use` brings **no** name in for a package and brings `HashMap` in for
  `std`.

A sixth was on that list and is answered: the options-only argument list is
[ADR-133](adr-133.md).

**Five picks in one record, and each migration its own entry.** They are one
question — *does this language say one thing one way* — and answering them
apart would let the corpus be migrated five times for one property. What is
separate is the **work**: [#265](https://github.com/Nikaia-Language/Nikaia/issues/265) carries one entry per pick,
because each is a rewrite somebody has to read.

## 2. Decisions

### D1 — The struct literal is the brace form, and `Name(field: value)` goes.

```nika
let r = Reading { name: "a", temp: 1.0 }
let s = Stats { min: first, max: first }
let t = Summary(first)          // still the anonymous constructor
```

`Name { … }` cannot be mistaken for a call, and the shorthand field already
lives there. `Name(a, b)` stays what it is: a call, of the anonymous
constructor or of anything else.

**One thing D1 does not decide, and the build picked it in silence.** A name that
is both a **type** and a **function** — which the grammar allows and nothing in
the corpus writes — resolves to the type here, so `Foo(n: 1)` is `NK1146` and
the function is uncallable through the only spelling
[ADR-133](adr-133.md) D1 gives it, with a help that sends the reader to a line
building the struct. That record's own open question had named the shape and
this one did not take it; [ADR-286](adr-286.md) does — a name denotes one thing,
so the case that made this help wrong cannot be declared.

**This also answers a question the build found.** `execute(target_age: 30)`
— [ADR-133](adr-133.md) D1's options-only call — is the same five tokens as
`Stats(min: first)`, so that record's call half was blocked on which construct
owned the spelling. With the named literal gone, `name(field: value)` is a call
with options and nothing else, and ADR-133 D1 is unblocked without the
resolution its own open question was about.

### D2 — A type is constructed by its anonymous constructor, and `new` leaves `std`'s own types.

`Vec()`, `String()`, `HashMap()` where `Vec::new()`, `String::new()` and
`HashMap::new()` stand today. The anonymous constructor is what a `.nika` file
writes (`pub fn(first: i32)`, Part I 4.2) and `new` is Rust's convention
reaching through a hand-written ledger.

**One convention, and it is this language's own.** `1brc.nika` passes
`Summary::new` as a value although `Summary` declares an anonymous constructor
and no `new` — a program written against the convention it could see.

### D3 — A path is `::`, everywhere.

`Json::value(input)` and `T::fields` where the dot stands today
([ADR-296](adr-296.md) D24, Part II 10.3). A grammar's name is a name and a
rule of it is reached the way every other qualified name is reached.

**The dot is for a value's members**, and keeping it for a namespace was the
one place this language asked a reader to tell two things apart by what the
left side happens to be.

### D4 — `throws` and `sync` stand **after** the result type.

`fn f() -> String throws` and `fn f() -> String sync throws`. The form before
the arrow stops parsing, and `sync` stands before `throws` — one slot, in the
order [ADR-277](adr-277.md) D6 gives a function type.

**After reads best and is what every example writes** — and it is the order
[ADR-277](adr-277.md) D6 already fixed for a function *type*, where the
trailing words are greedy. One order in a declaration and in a type.

**A declaration with no result type writes the word where it always did.**
`fn tick() sync { … }` has no arrow for the word to be before or after, so
nothing about it changes; what goes is a promise standing *in front of* a `->`.

**The one shape this takes away**, and it is a shape nothing can write.
[ADR-277](adr-277.md) D6's greedy rule means the trailing words on
`fn make() -> fn(i64) -> i64 sync` belong to the **result type**, and that
record's note pointed at the pre-arrow form as the way to mean the function's
own promise instead. A function type in a result is `NK1142` until D5's boxed
lowering exists, so no program is waiting on the distinction — and D5 is the
record that owes it a spelling the day it lands.

### D5 — `use` brings nothing in, for `std` as for a package.

`use std::collections` then `collections::HashMap`, or the prelude's `HashMap`
where the prelude has it. [ADR-286](adr-286.md)'s rule is the language's and
`std` is the one place it is not followed.

**`Vec`, `String` and `HashMap` need no `use` at all**, which is the prelude
and is unchanged: what goes is `use` *acting differently* depending on what
follows it.

## 3. Consequences

* Five fewer places a reader stops to ask which of two things they are looking
  at, which is what `language-review.md` §3.3 counted.
* [ADR-133](adr-133.md)'s call half is unblocked by D1, and
  `docs/open-decisions.md`'s entry about the collision goes with it.
* **What it costs:** five migrations. Each is mechanical, each touches
  `examples/`, `std` and the specification's pages, and each is its own entry
  in [#265](https://github.com/Nikaia-Language/Nikaia/issues/265) so that no two of them are in flight at once.

## 4. What this does not decide

* **Whether the anonymous constructor's syntax is right** — `pub fn(first:
  i32)` — which D2 keeps as it is.
* **The prelude's contents.** D5 is about `use` and not about what needs none.
* **A shorthand field in a call**, which the brace form has and a call does
  not.

## 5. What is built

**D1, and [ADR-133](adr-133.md)'s call half on top of it.** `ctor_lit` is out of
the grammar — both the expression rule and the head one, where it sat for
[ADR-301](adr-301.md) D4's brace reasons — so `Name(field: value)` is a **call**
wherever it stands, and `Name { … }` is the literal.

**What tells a mistake apart is the checker and not the parser**, which is the
whole shape of this decision: a call carrying options whose callee
`declares_a_type` is the old spelling, and `NK1146` names the braces with the
fields the line already has. It is asked before the call is resolved, because
resolution would otherwise answer about the **anonymous constructor** — the
silent lowering was `Stats::new()` with the fields dropped, which is
[Part III C.1](../30-nikaia-tooling.md)'s class.

**And a name nothing declares moved rather than lost its message.**
`Widgit(size: 3)` was `NK1135`, *nothing declares a struct called `Widgit`*; it
is a call to a name nothing describes now, and silence is the correct answer to
one — `Widgit(3)` beside it has always got the same, because this build cannot
see whether a dependency declares it and refusing a correct program is what
Part III C.4 forbids. The **brace** form still carries the claim, which is where
it belongs.

*The migration was eight sites in `examples/`, thirty-four in the tests and six
on the pages* — the number D3's own paragraph asked for and the reason this was
a change rather than a project.

**D4 too**, and it was one rule and seventeen sites. `promise_before_the_arrow`
refuses a `sync` or a `throws` standing in front of a `->`, with a message that
names the order — **the cut sits after the arrow and not after the word**, which
is what leaves `fn tick() sync { … }` alone: the word alone is not the old form,
a word followed by an arrow is. Nothing in `examples/` wrote it at all; the
sites were fifteen in `errors_lowering.rs`, one in `returns.rs`, one in
`function_types.rs` and two on Part I 7.1.

*And `sync` now stands before `throws`, which the record did not say and one
slot decides.* `fn f() throws sync { … }` used to parse — `throws` took the slot
before the arrow and `sync` the one after it, so the pair was legal only because
there were two. D4 leaves one, and the order in it is
[ADR-277](adr-277.md) D6's and this record's own example: `sync throws`. Refused
with a sentence rather than with *expected `{`*, because the form was legal a
version ago. Nothing in the tree wrote it but one line of a test.

*And the test that guarded ADR-277 D6's greedy rule was asking the ledger and
could not have answered.* `sync` is **inferred** from the body, and an empty body
pauses at nothing — so `ledger.functions["make"].sync` said *sync* whichever of
the two the trailing word attached to, and the assertion held for the wrong
reason. It reads the **AST** now: the declaration's `is_sync` is false and the
result type's is true.

**D3 too, and it is the checker's refusal and not the parser's.** A grammar is
entered through a path now — `Json::value(input)` — in the checker, in the
emitter and in the ledger, where the key was already `Grammar::rule`. The dot is
`NK1147`, and it has to be asked where the grammars are known: `Json.value(x)`
and `text.value(x)` are the same five tokens, and a grammar name is not a value
the parser can tell from one. Raised only where the receiver **is** a grammar of
this file and the name **is** one of its rules, so the message carries the whole
rewrite and a method on a value that happens to share a spelling is untouched.

*Nine sites in `examples/`*, five in the tests, and Part II 10.2, 10.6 and 11.
`T::fields` on 10.3 is the same decision on a page whose construct is itself
unbuilt, so there the spelling is all there was to fix.

*The one thing that had to be found by running the corpus*: `uses_driver` — the
walk that decides whether the emitted file imports `ParseContext` and
`Parallelism` — read the **method** shape, so a parallel entry lowered to a
`parse_…_pieces` call with both names undeclared. `rustc` about a file nobody
wrote ([Part III C.1](../30-nikaia-tooling.md)), and no test of the spelling
would have caught it: what caught it was *every runnable example prints what it
promises*.

*And it took a `rustc` message back that the dot had been hiding.* Part II 10.3's
`describe[T: Struct]` was refused as `NK1117` — *nothing declares `T`* — because
`T.fields` read `T` as a **value**. As a path there is nothing for that refusal
to fire on, and the block reached the backend, which answered *cannot find trait
`Struct` in this scope* about a file nobody wrote
([Part III C.1](../30-nikaia-tooling.md)). A **bound** naming a trait nothing
declares is `NK1135` now — the same claim one position over, against the traits
either ledger records ([ADR-295](adr-295.md)) and this unit's own — so the block
is refused in this compiler's words. Part II 10.2's `parse_input` moved the
other way and is a program now, so the specification's lowering floor is 49.

*And it made a silence visible that had been failing open.* The analyses answer
nothing about a method whose receiver they cannot resolve, so a grammar entry
used to contribute nothing to its caller's `sync`, `keeps`, `touches` and
`locks` — a promise **kept** on doubt, which is
[ADR-010](adr-010.md) D1's polarity backwards. As a call by name it reads the
entry's contract instead, and that contract carries none of those columns
because nothing derives them: `examples/inventory`'s `read` lost
`sync = "inferred"`, `keeps` and `touches`, and its lowering became `async`.
Every example still runs, at both settings, so what this costs is information
and not correctness — and the derivation a `pub` rule's action blocks would
allow is [#141](https://github.com/Nikaia-Language/Nikaia/issues/141). Probing that entry found the other half:
**an action that pauses lowers to `.await` inside a synchronous parser**, which
the backend refuses, and whether an action may pause at all is a question this
record does not answer — `docs/open-decisions.md` §1.

**D2, and the ledger's keys did not move after all** — which is this record's
own §5 step corrected. It said *`std.contracts`'s entries renamed to `Vec()`,
`String()` and `HashMap()`*, and that would have been a second spelling in the
one place there must not be one: `Type::new` is the name the **lowering**
writes, and the lowering is name for name ([ADR-296](adr-296.md) D17). What moved
instead is the **resolution**: the `{name}::new` fallback that a `.nika` file's
own types have always had now reaches the library too, where it stopped at this
unit. `Vec()` is one rule with `Stats(first)` rather than a special case.

*And the written `Type::new` is `NK1149`*, in `std` as in a `.nika` file, which
is what makes it one convention rather than two. Asked of the **name** and not
of the position, so the value form goes with it — `par_fold(M, Summary::new, …)`
is how `1brc.nika` wrote it, and `par_fold(M, Summary, …)` is what it says now,
with the emitter putting the key back on the Rust side. A **qualified** name is
left alone (`http::Server::new()` names a package this build cannot see), which
is `NK1135`'s convention one refusal over.

*One thing had to be corrected rather than added.* The anonymous-constructor
rule handed back `Ty::named(ty)` — *the type it is on, whatever its declaration
says about `Self`* — which is right for a `.nika` type, and wrong for
`Vec::new`, whose entry declares `-> Vec[?]`: `let xs = Vec()` came out as a
plain `Vec` and `NK1106` refused it against every `Vec[T]` it was given to. The
declared result is used where it names something, and `Self` and the absence of
a claim keep the old rule. **The rule was right for the one case it had.**

*And the `sync` walk needed the same reach.* `contracts::sync` looked the
library up by the written name only, so a `sync` function that built a
`HashMap()` was refused against a callee nothing described — `NK2202` on nine
programs. One loop over the two spellings.

*A name this unit does not declare is left alone*, which is
[Part III C.4](../30-nikaia-tooling.md)'s rule and is what lets a `.nika` file
name a **Rust-side** item at all: `crates/nikaia/tests/fixtures/measurements.nika`
says so in its own header, and keeps writing `Summary::new` because that is a
Rust name and not a type of the program. The same shape appears in a *slice* of
a real program — `grammar_lowering.rs` extracts `1brc.nika`'s grammar without its
`struct Summary` — and the test now pins both halves: the slice writes `Summary`
and the whole file writes `Summary::new`.

*And the map is built through the path rule and not by writing `::new`*, which
is where one name below depends on more than the name: at the default provenance
a map is the **trusted** one, and `new` exists only for the default hasher
([ADR-010](adr-010.md) D5). One arm written the short way took that back for
every `HashMap()` in a trusted program.

*Twenty-one sites in `.nika` files and sixty-four in the tests*, and the tests
were the careful half: a test file writes `Vec::new()` in **Rust** as often as in
a fixture, so what is migrated is what is not followed by a `;` and not inside a
`.contains(` about the emitted Rust. `measure.rs` is entirely the second kind
and is untouched.

**D5, and it turned out that the compiler already did nothing.**
`use std::collections::HashMap` was a **no-op**: the module layer skipped every
`std` import, the checker never looked at one, and the emitter wrote it back as
a comment. `HashMap` worked with no `use` at all, because it is a name this
compiler already knows. So what this record removes is not behaviour — it is a
line that *reads* like an import and is not one.

`NK1156` refuses it, and the question it asks is **does the name have a
receiver**. A module and a type read the same way in a ledger key —
`fs::read_to_string` and `HashMap::len` are both `X::y` — so what tells them
apart is the `self`: a type's entries are called on a value and a module's are
not, and the method has to be one of *this* name rather than of something
inside it, or `fs::Mapped::deref` would make `fs` a type. `use std::fs` is a
module and stands; `use std::db::postgres` and `use std::backend::x86` name
modules nothing describes yet and stand too, because refusing on a surface that
does not exist is [Part III C.4](../30-nikaia-tooling.md)'s correct program
refused.

*The migration was two `.nika` files, three tests and three pages.*
