# ADR-002: A Toolchain That Wraps Cargo, and Metaprogramming Without Proc-Macros

**Status:** Accepted · **Built:** D1, for a Rust dependency (§5);
D3 as [ADR-021](adr-021.md)'s key and store; D4 (§5); not D2
**Supersedes in part:** [ADR-014](adr-014.md) D1's *when* — `std`'s Nikaia half
is lowered at release time, not when the crate is built (D4)
**Superseded in part by:** [ADR-021](adr-021.md) D9 — D3's Cranelift claim.
**Related:** [ADR-021](adr-021.md) (works out D3, and whose key D4 extends),
[ADR-026](adr-026.md) (works out D2), [ADR-296](adr-296.md) (the multi-language
goal), [ADR-014](adr-014.md) D1 (the `.nika` half of `std` D4 pre-lowers),
[ADR-037](adr-037.md) D3 (the `Shared` that would break D4's constraint),
[ADR-005](adr-005.md) D8 (why the ledger travels with the compiler)

## 1. Context

Nikaia is one language on a toolchain meant to host several. Two things had to
be true before any of them: a Nikaia project must consume crates.io without
reinventing dependency resolution, and compile-time metaprogramming must not
cost what Rust's proc-macros cost — a separate dynamic library compiled before
the program that uses it.

## 2. Decisions

### D1 — One CLI wraps and instruments Cargo.

`nikaia.toml` is translated to a compliant `Cargo.toml`, native Rust
dependencies passing through unchanged. Compilation is intercepted with
`RUSTC_WORKSPACE_WRAPPER`: Rust crates go to the native `rustc`, `.nika` files
to the Nikaia pipeline. The build switches of [ADR-037](adr-037.md) set
`opt-level` and the panic strategy from there.

Dependency resolution and linking are solved problems, and a language that
cannot reach crates.io starts with no ecosystem.

### D2 — Compile-time code runs in an interpreter, not as a compiled plugin.

Quasi-quoting, `dsl … { … }` validation and reading a file at build time are
evaluated by an AST walker in the compiler's own process.

A proc-macro is a crate that must be built, linked and loaded before the crate
that uses it, which is where Rust's build latency comes from. An interpreter has
none of that, and the compiler already holds the AST.

What a build may read, and what may run while it reads, is [ADR-026](adr-026.md)
— still open.

### D3 — A build that reads the world needs a deterministic key over what it read.

Every external file a compile-time evaluation touches is recorded by content
hash in a lockfile, and an unchanged hash skips the evaluation.

[ADR-021](adr-021.md) is this decision worked out: what is hashed, what
invalidates what, and where artifacts live. Where the two differ, ADR-021 wins.

### D4 — A project reaches `std` through a sysroot: sources, pre-lowered, compiled into a keyed rlib cache.

`nikaia-std` is not published, so D1's "Cargo resolves it" does not apply to it
and never will until a registry is decided. What replaces the path to a checkout
is a **sysroot**: a directory that travels with the compiler and holds `std`'s
*sources*, with the Nikaia half already lowered to `.rs` and the `.nika` kept
beside it. `NIKAIA_SYSROOT` names one; the default is the checkout the compiler
was built from.

**What decided it is a measurement of the thing it replaces.** A Nikaia
hello-world's generated lockfile held **97 packages, and 58 of them existed only
to *build* `nikaia-std`** — `clap`, `anstream`, `toml`, `sha2`, `orchestrator`
and `nikaia` itself among them. The cause is
[ADR-014](adr-014.md) D1: `std` lowered its own `.nika` files in a build script,
so it had the compiler as a **build-dependency**, so Cargo compiled the compiler
library *again, inside the project's `target/`*, while the installed compiler was
running and doing that very lowering. A duplicate build, per project, for ever,
and 29 s cold for a program that prints one line.

Three decisions follow, and each is the one the numbers force rather than the one
that sounds most careful.

**`std` ships as sources, with the `.nika` half pre-lowered, and the `.nika`
kept.** A binary install compiles the `.rs` and needs no compiler to do it, which
is what makes the 58 packages go. A from-source install may re-lower, by
invoking the installed `nikaia` **binary** (`nikaia lower-std`) and never by
linking the compiler as a library — that linkage is the defect, not an
implementation detail of it. One artifact serves both installation styles, which
is the point: the alternative is two release pipelines that can disagree.

**Built locally into an rlib cache, not shipped pre-built per platform.** The
two measurements that settle this are about what actually dominates. The Rust
toolchain an installation needs is **602 MiB** ([ADR-001](adr-001.md) D1),
against **1.9 MB** for `nikaia-std`'s rlib — so installation *size* cannot decide
this question, because `std` is two and a half orders of magnitude below what
already dominates. And building the compiler from source is **40 s / 209 MB**, so
a from-source install is cheap and shipping pre-built artifacts per platform buys
little while costing a matrix.

The cache is keyed with the key [ADR-021](adr-021.md) already has — the
compiler's own fingerprint (D3) and the toolchain — plus the **target** and the
**codegen flags**. `Key::sysroot` is the one place those dimensions are named,
beside `Key::build`, for D7's reason. The codegen flags are in because
**hardware optimisation is the one axis where `std` matters more than the
compiler**: `std`'s code runs inside every user program, where the compiler's own
speed only costs build time. So `-C target-cpu=native` has to be a *dimension* —
a second entry that coexists — rather than a reason to rebuild the first one,
which is [ADR-021](adr-021.md) §4's "dimensions coexist; they do not share"
applied one layer up.

ADR-021 D7's "not too much, not too little" governs the rest of the list, and it
is what keeps three plausible dimensions **out**. `user_parallelism` is out
because the switch reaches `std` as a *runtime value* — `UserCode::Sequential` or
`::Concurrent` handed to `rt::start` in the `fn main` the emitter writes — and
never as a `cfg` or a feature. Verified, and it still holds: `nikaia-std`
declares no features and the only `cfg` in it is `target_os`. So there is one
compiled `std` per machine, not one per build switch. `ordering` and the lowering
backend are out because they decide what a `.nika` file lowers to and `std`'s
Rust is not lowered by a project's build at all. And the **content hash of the
`std` tree** is out, which is the one that looks like an omission: what the key
names is a *directory*, and inside it Cargo's own fingerprinting already decides
what is stale (ADR-021 D1). Hashing the tree as well would start a fresh
directory for every edit to `crates/nikaia-std/src/fs.rs` and rebuild everything
under it — 38 units, 16 s — to guard against a staleness that cannot occur,
which is D7's "too much" direction exactly.

**`NIKAIA_SYSROOT` replaces `NIKAIA_STD_PATH`.** The old name said *crate
directory*, and a crate directory can answer only one of the questions this
mechanism has to answer.

#### The constraint this creates, stated rather than discovered

`std`'s Nikaia half is lowered **at one setting of the build switches** —
`Build::default()`, which is `target = x86_64-linux`, `user_parallelism = no` —
whatever the consuming program is built at. That was already true when a build
script did it, hardcoded, and **nobody decided it**. Moving the lowering to
release time turns the hardcoding from an accident into a promise, so it is
stated as a constraint:

> `std`'s Nikaia half is lowered once, at one setting. This is sound only while
> nothing switch-sensitive appears in it.

`Shared` is exactly what would break it. [ADR-037](adr-037.md) D3 makes it `Rc`
at `user_parallelism = no` and `Arc` at `yes`, so a `Shared` in a `.nika` file
here would be lowered to `Rc` and then linked into a program built at `yes` — a
`std` that cannot cross a thread inside a program that may. That question is
still open (D3 says so in as many words, and ADR-005 §5.3 records what depends on
it), and until it is answered this constraint is what stands in for an answer.

It is **checked**, not merely written down: every `.nika` file in `std` is lowered
at both settings and the bytes have to agree, so the day something
switch-sensitive arrives it is a red build instead of a miscompilation.

#### Committed, not generated by a release step

The pre-lowered `.rs` is **committed**, beside the `.nika`. Both ways are
defensible and both cost something — committing puts a generated file in a
reviewer's diffs; generating adds a release step that must not be forgotten — and
what breaks the tie is a constraint this record does not get to trade away:
**`cargo test --workspace` must work from a fresh checkout with no extra steps.**
At that moment a generated `.rs` does not exist, and the only mechanism that
could produce it in time is the build-dependency on the compiler this decision
removes. Committing is therefore not the more convenient option; it is the only
one compatible with the in-tree flow.

The cost is paid the way a generated file's cost is always paid, by making the
file unable to lie: a test regenerates it with the compiler and fails if the
committed bytes differ, naming the command that fixes it. That is the same
standard [ADR-005](adr-005.md) D8 sets for the ledger — `git diff --exit-code`
rather than a comparer that can itself be wrong.

#### Where the ledger lives

`std.contracts` stays **inside the compiler**, baked in with `include_str!`, and
the compiler answers from that copy and never from the sysroot.
[ADR-005](adr-005.md) D8 makes ledger stability across toolchain versions
explicitly *not* required, so a `std` that could be paired with a different
compiler would let the ledger describe a compiler that is not there. The file in
the sysroot is the source it was built from — a reviewer reads it there — and a
test requires the two to be equal, so they cannot drift.

## 3. Consequences

Rust's own guarantees are inherited rather than rebuilt — the borrow checker
verifies the lowered program, which is what lets Nikaia promise memory and
thread safety without implementing either.

The price is that a target language has to fit Rust's ownership model. A language
that assumes pervasive garbage collection does not.

## 5. What is built

**D1, for a project with Rust dependencies.** `nikaia build` and `nikaia run`
take a directory, walk to the nearest `nikaia.toml` — the walk the build cache
already does, not a second one — and translate it into a `Cargo.toml` under
`target/nikaia/build/`. `[package]` becomes Cargo's, a `type = "rust"`
dependency passes through with only that marker removed, and the
`[build.<target>]` table of the machine this build chose becomes
`[profile.dev]`'s `opt-level` and `lto`. The panic strategy is written there too
and is not a choice: `unwind` where the machine unwinds, `abort` where it traps
([ADR-037](adr-037.md) D1). Cargo then resolves, fetches and links, which is the
half of this record the toolchain deliberately does not implement.

**The interception is `RUSTC_WORKSPACE_WRAPPER`, and that is the load-bearing
word.** Cargo applies it to workspace members only, so a crate from crates.io is
compiled by the real `rustc` with nothing in between. The generated manifest
names `src/main.nika` as the crate root — Cargo does not require `.rs` there —
so Cargo hands the wrapper a `rustc` command line with a `.nika` file in it, the
wrapper lowers the program, substitutes the emitted Rust and runs the real
`rustc`. A command line without a `.nika` file in it, including Cargo's own
`rustc -vV` probes, is passed through untouched.

**Verified by asking what Cargo asked for, not by looking at what came out.**
A dependency passed *through* the wrapper and one that never reached it produce
the same rlib, so the claim is invisible in the artifacts. `NIKAIA_WRAPPER_TRACE`
names a file the wrapper appends one line to per invocation, and the test over a
project depending on `regex` asserts that exactly one crate in the build was
lowered, that it was the project's own, and that nothing in the trace mentions
`regex` — while Cargo's lockfile for the generated package shows `regex` was
resolved from crates.io and linked.

**Two things building it settled, both about Cargo's freshness rather than about
this record.** A generated file rewritten with identical bytes is newer than the
fingerprint Cargo wrote, so the package is dirty on every build, for ever: the
emitted Rust is written only when it changed. And the dependency file `rustc`
emits names the *generated* Rust, which Cargo believes — so an edited `.nika`
source would leave the package fresh and the binary stale. Every source that
took part goes back into that file after `rustc` succeeds. Neither was
predicted; both were measured by building twice and editing once.

**Not built: a Nikaia dependency.** Part III 13.3 shows `http-server = "1.2"`
beside the Rust crate, and nothing anywhere decides what resolving it would
mean — no registry, no name space, no distribution format. It is refused with
that reason rather than handed to Cargo, which would look for it on crates.io
and fail somewhere that explains nothing.

**Not built: D2.** Compile-time evaluation waits on
[ADR-026](adr-026.md), which is still open. Nothing reports a compile-time asset
yet, which is why the cache's asset dimension travels through the key carrying
nothing (D3, [ADR-021](adr-021.md) D7).

**What the generated manifest is not in:** the build cache's key. `opt-level`,
`lto` and a dependency version change the *machine code* and not the lowering —
Stage 0 emits name for name, and the envelope the cache holds is the emitted Rust
and the ledger. Cargo's own fingerprinting covers that half and is not wrapped
([ADR-021](adr-021.md) D1).

**The resolved versions are recorded, and that closes what this section
previously listed as owed.** Cargo's `Cargo.lock` for the generated package has
them and `nikaia.lock` did not, so the one file that is supposed to answer "does
this build the same thing for you as for me?" answered it only about the Nikaia
half. It carries `[dependencies]` now — the whole resolved graph, read out of
Cargo's answer after `cargo` returns, because the toolchain still does not
resolve anything itself. Recorded and **not** keyed, for the reason the
paragraph above gives: [ADR-021](adr-021.md) §5 works it out.

**D4, and what it did to the numbers.** `crates/nikaia/src/sysroot.rs` resolves
the sysroot and names the compiled-`std` cache; `Key::sysroot` in
`orchestrator::cache` holds its dimensions beside `Key::build`'s;
`crates/nikaia-std/build.rs` is gone, with the `[build-dependencies]` that were
the defect. Measured the same way before and after, on a hello-world:

| | packages resolved | of those, only to build `std` | cold build | units compiled |
| :--- | ---: | ---: | ---: | ---: |
| before | 103 | 58 | 25.8 s | 79 |
| after | 46 | 1 | 16.0 s | 38 |

The 97 / 58 / 29 s that decided this were measured earlier on another machine;
103 / 58 / 25.8 s is the same defect re-measured where the fix was built, and the
58 is identical. The **1** that remains is `version_check`, an honest build
script of a crate `std` itself depends on — nothing of the compiler is left, and
`nikaia`, `clap` and `sha2` are asserted absent by a test rather than by reading
a lockfile once. `docs/history/std-sysroot.md` has the method and the machine.

**The rlib cache hits, and that is asserted by mtime.** A second project on the
same machine builds in **1.65 s** and compiles exactly one crate, its own; with
the cache switched off (`CARGO_TARGET_DIR` set, which is the way out) it pays
16.0 s again. The test does not read a build log for an absent "Compiling" line,
which would only say Cargo was quiet — it takes the rlib's modification time
before and after and requires it not to have moved.

**A second record's *reason* went with it, and its mechanism stays.**
[ADR-014](adr-014.md) D4 makes the tests read which rlibs belong together out of
crate metadata, because "the build-dependency graph builds the parser backend a
second time under cargo's build-override profile, so a deps directory holds two
`winnow` rlibs that do not link together". That build-dependency graph is what
this decision removes, so the coin toss it described cannot happen here any more.
D4 is not withdrawn: reading the set out of metadata is right whatever put two
rlibs in a directory, and a test that anchors on `nikaia_std` is one that cannot
be wrong for a reason nobody thought of. The reason is simply no longer the only
one it has.

**Two prices, named.** The compiled `std` lives in the user's cache directory and
not under `target/`, because "shared between projects" is the whole of what it is
for — so `rm -rf target` no longer gives a cold build, and
[ADR-021](adr-021.md) §3's owed eviction policy now has a second store to cover.
And two builds sharing one entry serialise on Cargo's lock on that directory,
where two projects with their own `target/` did not.

**Not built: a sysroot that is not a checkout.** The layout is decided — a
directory with `nikaia-std/` in it, which is why `crates/` *is* a sysroot and the
in-tree flow needs no special case — and `NIKAIA_SYSROOT` reaches it. What does
not exist is the release step that *produces* one: `nikaia-std/Cargo.toml` still
spells its shared dependencies `{ workspace = true }`, so a copy of that directory
outside this workspace does not resolve. Packaging has to inline them, and nothing
here decides what else an installed layout carries.
