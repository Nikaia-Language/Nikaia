# ADR-042: A View Keeps the Type It Is a View Of, and a Transparent Container Is Seen Through

**Status:** Accepted · **Built:** D1, D2 — see §4
**Related:** [ADR-024](adr-024.md) (the type checker says only what is written
down — D1 is that discipline failing in one direction, not an exception to it),
[ADR-288](adr-288.md) (a signature naming its receiver's type arguments, which
is what makes D2 answer with what *this* container holds),
[ADR-288](adr-288.md) D11 (why D2 takes one step and not a chain),
[ADR-040](adr-040.md) D1 (the rule that needed this before it could be written).

## 1. Context

Two defects in one place, found while asking a question about something else:
whether a shared value can be lent out without unwrapping it. The answer turned
out to depend on a rule the language does not have, and the rule is not about
sharing.

**`&` on a generic type answered nothing.** `view_of` produced a type only where
the type had no arguments, so `&Vec[i64]`, `&HashMap[&str, Stats]` and — the day
it exists — `&Shared[Connection]` all came out as "nothing is known". The checker
then said nothing, the program was emitted, and a mismatch was reported by
**`rustc`, about the generated file**:

```
error: mismatched types
     = expected reference `&str`
   found reference `&Vec<i64>`
warning: … `#[warn(unused_variables)]` …
```

That is the one thing Part III C.1 forbids. It is also not a gap in what the
checker *knows* — the type was right there — but a step that threw it away.

**And a transparent container was refused.** Part III says of `fs::Mapped` that
*"a parser cannot tell the difference"*, and `std`'s ledger spells it out:
`fs::Mapped::deref` has `signature = "(&Mapped) -> &str"`. Nothing consulted that
entry, so a function taking a text view refused a mapped file — the opposite of
what the specification promises about the type, and by this compiler's own
`NK1102` rather than by rustc.

The two defects point in opposite directions, which is why neither was found by
the other: one let too much through, the other too little.

## 2. Decisions

### D1 — A view keeps the type it is a view of, arguments and all.

`&Vec[i64]` is a view of a `Vec[i64]`. Three cases and nothing else:

* a view of a view is the view — `&&str` is not a type this language has;
* `&String` is `&str`, the one rewrite, because a text view is spelled `&str` and
  `&String` is not a type a signature may ask for;
* anything else named keeps its name **and its arguments**.

A tuple and a lambda answer nothing, deliberately: a tuple of views is not a view
of a tuple, and nothing writes down what a view of a lambda would be.

### D2 — A type whose ledger records a `deref` is seen through, once, and only to rescue a comparison that has already failed.

A container that records `Type::deref` is one a caller is not meant to notice. So
where a found type does not fit what is wanted, and the ledger says the found type
derefs, the question is asked again of what the deref gives.

**Only as a rescue.** It runs *after* a direct comparison has failed, so seeing
through a container can turn a refusal into an acceptance and can never turn an
acceptance into a refusal. That is what makes it safe to add to a checker whose
whole discipline is to say nothing where it knows nothing
([ADR-024](adr-024.md)): this says *more* only where it was already about to
refuse.

**One step.** A container inside a container is two questions and nothing in the
language has asked the second. [ADR-288](adr-288.md) D11's rule — an entry exists
because a program asked for it — applies to a step of this walk exactly as it
applies to an entry.

The receiver's own arguments bind the signature's variables as they do for any
other method ([ADR-288](adr-288.md)), so an entry written `(&Shared[$T]) -> &$T`
answers with what *this* container holds rather than with a variable. That is what
makes D2 enough for a generic container and not only for `Mapped`.

## 3. Consequences

**A program refused by rustc is now refused by Nikaia.** The probe that found
this — a text view handed a `&Vec[i64]` — is `NK1102` with this compiler's words
and a help line, where it used to be rustc's words about a file nobody wrote.

**And a promise the specification already made is now kept.** A function taking a
text view accepts a mapped file.

**This is what [ADR-040](adr-040.md) D1 was resting on.** That record says a
handle on a shared value is duplicated where it is handed on; lending one out
instead is the case where nothing is handed on at all, and before D1 and D2 there
was no rule under which `serve(&db)` meant anything. A separate correction to
ADR-040 draws that line.

**The door this opens and does not walk through.** `Shared[T]` and `SharedMut[T]`
will be seen through by D2 the moment they have a `deref` entry, with no further
decision — which is what makes the shared case a consequence of this record
rather than a special case beside it.

**One thing found on the way, since fixed.** `check/mod.rs` carried a doc comment
for a method-on-a-type lookup that documented no function — the item below it was
`arguments_given`, with its own doc — so the thing the comment was about, and
which D2 uses, had none. It sits on `method` now.

## 4. What is built

**Both decisions, with five tests.** D1 is `view_of` in `check`; D2 is
`fits_through_deref` beside it, consulted at the two places a found type is
compared against a wanted one — the shared `expect` helper, which covers `let`,
`return`, an assignment and a struct field, and the positional argument check
that raises `NK1102`.

**D2 is used by a shared value now.** `std`'s ledger carries
`Shared::deref` as `(&Shared[$T]) -> &$T`, so `serve(&db)` reaches the inner value
with nothing new — the `$T` bound from the receiver is what §2 said would make
this enough for a generic container and not only for `Mapped`, and that is what
happened. `fs::Mapped` still exercises it too.

What is **not** built is the `SharedMut[T]` half, because that type is not one the
compiler knows ([ADR-281](adr-281.md)).
