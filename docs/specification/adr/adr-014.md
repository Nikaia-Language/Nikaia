# ADR-014: `std` in Nikaia, a Real Mapping, and a Parallel Driver

**Status:** Accepted · **Built:** yes
**Closes:** the two items [ADR-013](adr-013.md) §4 named — `fs::map` reading
rather than mapping, and the pieces running in sequence
**Superseded in part by:** [ADR-015](adr-015.md), which re-measures D3 after
removing the backend's eager error bookkeeping; [ADR-002](adr-002.md) D4, which
moves D1's lowering from the crate's build script to release time — *parts of
`std` are `.nika`, compiled by Stage 0* stands; *when the crate is built* does
not
**Related:** [ADR-001](adr-001.md) D4 (Stage 0 is a transpiler — which is what
makes D1 possible at all), [ADR-296](adr-296.md) D11 and D15

## 1. Context

Two things the flagship still did not do were dependency decisions rather than
compiler ones, and both are closed here.

The third question was asked directly: *can more of Nikaia be written in
Nikaia?* The answer is yes, in a bounded way, and the way matters more than the
amount.

## 2. Decisions

### D1 — Parts of `nikaia-std` are `.nika` files, compiled by Stage 0 when the crate is built.

A build script runs every `src/*.nika` through the compiler library and writes
the Rust to `OUT_DIR`; `lib.rs` includes it as a module of the same name. The
first such file is one function:

```nika
pub fn digit_value(c: char) -> i32 {
    return c as i32 - 48
}
```

The point is not its size. It is the first code the project itself runs on that
the Nikaia compiler produced, and it establishes the mechanism by which the
share grows: **what a `.nika` file in `std` may contain is exactly what Stage 0
can lower, and each construct the compiler learns is a function that can move.**

`list.rs` (a trait with a generic method) moves when traits and generics are
lowered; `cli.rs` when `std::env` is reachable. `fs.rs` does not move: it is
`unsafe` around a memory mapping, and that is the layer a self-hosted language
still writes in the host.

**The compiler is a build dependency, as a library.** `nikaia-std` builds
against the `nikaia` library rather than its binary: nothing about turning
`digit_value` into Rust needs a CLI. That dependency is what
[ADR-002](adr-002.md) D4 later removes altogether, by lowering `std`'s Nikaia
half at release time and committing the `.rs`.

### D2 — `fs::map` is a memory mapping.

Read-only, validated as UTF-8 once when the map is made; after that a view of
the text is a view of the pages, and the `unsafe` that says so is a comment
pointing at the validation. A zero-length file cannot be mapped and is an empty
input rather than an error.

[ADR-296](adr-296.md) D15's allowance — leave a large read-only mapping to the OS
at process exit — is not taken yet; the mapping is released on drop.

### D3 — The parallel driver runs the pieces in parallel.

The backend's `rayon` feature is enabled on the **workspace** dependency rather
than on `nikaia-std` alone, for a build reason rather than a semantic one: cargo
would otherwise hold two differently-featured copies of the crate, and the tests
that compile emitted programs against the deps directory would have to know
which one the runtime meant.

Measured on 8 million lines, 4 cores: wall time divides by the cores while user
time is unchanged, which is what a frame plus a monoid buys and what nothing in
the program says how to do. *(The absolute figures here were dominated by error
bookkeeping the backend did on a succeeding parse; [ADR-015](adr-015.md) D3
removes it and re-measures. The ratio, which is this decision's point, is
unchanged.)*

Output is identical byte for byte at either setting — [ADR-296](adr-296.md) D10's
whole claim, measured rather than asserted.

### D4 — Tests read which rlibs belong together from crate metadata, not timestamps.

A consequence of D1 worth recording. The build-dependency graph builds the
parser backend a second time under cargo's build-override profile, so a deps
directory holds two `winnow` rlibs that do not link together, and "the newest
file" is a coin toss.

An rlib's dependencies can be read out as `name-hash`, the hash being the one in
the file name. The tests anchor on `nikaia_std`, read the parser backend from it
and `winnow` from that, and hand `rustc` one consistent set. This is why
`nikaia-std` declares the parser backend as a dependency: the runtime and the
parser it runs on are one dependency, and the chain needs somewhere to start.

## 3. Consequences

The flagship does everything its comments claim. A test still checks it on the
real file; the timing is not a test, because a test that asserts a speed-up
fails on a loaded CI runner. The *identical output* at either setting is asserted;
the speed-up is measured.

## 4. What is still not true

* **`sync` is unchecked.** The parallel section contains no pause because its
  author put none there, not because the compiler looked.
  *(Closed by [ADR-288](adr-288.md).)*
* **The pool is the backend's global one.** [ADR-296](adr-296.md) D11 keeps the
  cut and merge public for a pool of Nikaia's own; that is the
  runtime-integration line of the roadmap.
* **One Nikaia file in `std`.** The mechanism is the point; the share is one
  function, and D1 says which file moves when.
* **The compiler is not written in Nikaia.** This is self-hosting's first line,
  not its last: a `.nika` file the toolchain depends on. The distance from here
  to "the compiler compiles itself" is the whole language, and no part of it is
  made shorter by pretending otherwise.
