# ADR-235: `par_iter()` Walks a List on Every Core, and Its Lambda Neither Pauses Nor Writes What Is Shared

**Status:** Accepted · **Built:** yes, in 0.0.221
**Date:** September 27, 2026
**Target Version:** Nikaia 0.0.221
**Answers:** [#185](https://github.com/Nikaia-Language/Nikaia/issues/185), *`par_iter` has no entry to demand `sync`
of* — step 4 of [ADR-105](adr-105.md)
**Refines:** [ADR-105](adr-105.md) D3 (a `Par[T]` has `Seq[T]`'s surface, and
its lambda must be `sync`)
**Related:** Part II 12.6, [ADR-037](adr-037.md) D7 (which count a `Shared`
gets), [ADR-061](adr-061.md) (`user_parallelism`), [ADR-296](adr-296.md) D35
(`NK2209`)

## 1. Context

Part II 12.6 promises a data-parallel walk:

```nika
let bright = pixels.par_iter()
    .map fn(pixel) { pixel.brightness * 1.5 }
    .filter fn(value) { value > 0.5 }
    .collect()
```

The type language had `Par[T]` since ADR-105, and a `Par` falls back to
`Seq`'s entries, but nothing produced one: `par_iter` had no entry, so the
receiver was unknown, the lambda was not asked anything, and the lowering
refused a pausing one with a message about a compiler limit. ADR-105 said the
entry was *one line the day something asks for it*. Something did.

## 2. Decisions

### D1 — `Vec::par_iter` is a `Par[ref T]`, and it means the same at both settings.

`Vec::par_iter(ref Vec[$T]) -> Par[ref $T] sync ends sized`. Everything `Seq`
has, a `Par` has — `map`, `filter`, `collect`, `count`, `nth`, `join`, `rev`,
`take`, `skip`, `step_by`, `zip`, and `for_each`, which is new to `Seq` too —
and a `for` over one works out every element and then runs the loop's body in
the list's order.

* At `user_parallelism = yes` it is `nikaia_std::par::iter(&xs)`, a wrapper
  over rayon whose surface is exactly `Seq`'s. `collect` keeps the list's
  order; the walks rayon has only for a walk of known length go through a list,
  so they work after a `filter` too. A `map` or a `filter` allocates nothing
  it would not have.
* At `no` it is the list's own `iter()`: nothing runs at once, and nothing
  here is used.

A value a parallel lambda captures crosses threads, so a `SharedMut` it
changes through `update` keeps its atomic count — the sharing analysis
(ADR-037 D7) treats a lambda handed to any walk chained onto a `par_iter()`,
or onto a name bound to one, as it treats a `spawn` body.

### D2 — The lambda may not pause (`NK2209`) or change a name outside it (`NK2107`).

Both are asked at **both** settings, so a program never means something
different at the two.

* **A pause** — a call that can pause, or a `for` over a sequence whose step
  does — is `NK2209`, the code Part III already gave *a par_iter lambda*
  beside a grammar's action: a core that waits holds its share of the work.
* **A write to a name bound outside the lambda** — an assignment, or a method
  that changes what it is called on — is `NK2107`: every core would write it at
  once. The way out is a `map` and a `collect`, or a `SharedMut` changed
  through `update`, which the message names. A name the lambda binds itself is
  its own.

### D3 — `join` over a walk that does not pause.

Found while building D1: `Seq::join` over a `map` or a `chars()` had no
counterpart below — the language below's `join` is a slice's — and reached
`rustc`. `nikaia_std::seq::Join`, in the prelude under no name, is it.

## 3. Consequences

[#185](https://github.com/Nikaia-Language/Nikaia/issues/185) is closed and deleted. A lambda that pauses reaches the
lowering's refusal now only where the checker could not resolve what it is
handed to. Programs that compiled before compile to the same Rust.

## 4. What is built

All of it, in 0.0.221: the two entries in `std.contracts`,
`crates/nikaia-std/src/par.rs`, `Join` in `seq.rs`; the checker's

`crates/nikaia/tests/parallel_walks.rs`, run at both settings.
