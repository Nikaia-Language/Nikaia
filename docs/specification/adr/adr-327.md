# ADR-327: Shared State After a Panic Is Never Read Half-Changed — Rebuilt Where It Says How — and Every Task and Shared Value Has a Memory Budget in Memory Nikaia Allocates Itself

**Status:** Accepted. D1-D3 are rules; D4-D8 are the direction, with what is still to be measured in §6.
**Date:** October 6, 2026 (#121)
**Answers:** what a panic in one task ([ADR-326](adr-326.md) D4) leaves to the
others, and whether one task can exhaust the memory of all
**Related:**
[ADR-326](adr-326.md) (a panic ends its task);
[ADR-321](adr-321.md) D10 (a counting allocator bounds the build-time run);
Part I 6.2-6.3 (`Shared`, `SharedMut`, the four doors), Part II 12.8 (supervision), Part III 15.2 (crossing into Rust)

## 1. Question

**When a task dies while it changes a value other tasks share, what do they
see; and can one task's memory end everyone else's?**

A panic between two changes in an `update` door leaves a value half-changed.
Part III A.2 promises it is poisoned *so no other thread reads state a
half-finished task left behind*; the lock in `std` takes the guard without
looking at the poison. And a task that reads a large upload into a `String`
grows until the process has no memory left.

## 2. How others do it

| | A lock held by a dying task | Memory of one unit of work |
| :--- | :--- | :--- |
| Erlang/Elixir | nothing is shared; the owner's restart starts its state anew | a heap per process; `max_heap_size` ends that process, unset by default; a full machine ends the VM |
| Rust `std` | poisoned; a program usually `unwrap`s, so every later use panics | the global allocator; failure ends the process |
| tokio, parking_lot | not poisoned; the half-changed value is read | as Rust |
| Haskell STM, Clojure refs | changes go to a copy, committed at the end | - |
| Zig | - | every allocation takes an allocator and can fail; `FixedBufferAllocator` returns `OutOfMemory` |

From memory, not checked against a version.

## 3. Options, weighed

| Option | Why it lost |
| :--- | :--- |
| Read through the poison | a wrong value nobody is told about |
| A poisoned value stays poisoned | every task that needs it dies; the server runs and does nothing |
| Every change to a copy, committed at the end | pays on every change, not on the crash; for a large value, a copy per `update` |
| A budget in Rust's global allocator | an allocator may not panic and a refusal ends the process, so the limit could only be soft |
| One account per allocation, recorded beside it | a few bytes and a count on every allocation; a block per account says the same by address |
| Collections that are Rust's own, as today | their memory is the global allocator's, so no budget is hard |

## 4. Decision

### D1 — A poisoned value is never read.

A value behind a lock a panicking task held is poisoned; no door opens it as if
nothing happened.

### D2 — Without a way to rebuild it, a door to a poisoned value panics, in the task that opens it.

By [ADR-326](adr-326.md) D4 that ends that task only.

### D3 — A shared value that says how to build it is rebuilt.

*Made precise by [ADR-328](adr-328.md) D9: the policy, a door during a delay, and giving up.*

```nika
let cache = SharedMut::supervised(fn { Cache::load() })
```

The holders keep the same handle; the runtime calls the function again, puts
its result in place of the poisoned content and lifts the poison. How often is
bounded as a supervisor's restarts are (Part II 12.8). The content starts
anew: what must survive a crash belongs in a store with transactions.

### D4 — Nikaia allocates its own memory: `std`'s collections take it from an allocator Nikaia controls, and every such allocation can fail.

`List`, `String` and `Map` stand on collections with an allocator of their own
(`allocator-api2`, `hashbrown`), not on Rust's `Vec` and `String`.

### D5 — Every task, and every shared value, allocates from a block of its own, and the block is its budget.

What a task allocates is the task's; what is allocated inside a door of a
`SharedMut` or in the construction of a `Shared` is that value's. `Shared` is
written in the source (Part I 6.2), so which account pays is known where the
code stands.

### D6 — A full block is a panic in the task, or a poisoned shared value.

A task whose block is full panics where it allocated - outside the allocator,
so it unwinds - and ends ([ADR-326](adr-326.md) D4); its memory goes with it. A
shared value whose block is full is poisoned, and rebuilt where it says how
(D3).

### D7 — How large a block is, an exchangeable strategy decides.

As admission is ([ADR-326](adr-326.md) D2): `std` provides one that derives
budgets from the memory there is and the tasks running; a package may provide
another. No number is configured.

### D8 — Toward Rust, a view crosses free; an owned `Vec` or `String` is an explicit copy.

`&[T]` and `&str` cross without a copy, as a `String` crosses to `&str` today
(Part III 15.2). A Rust API that owns its `Vec<T>` or `String` gets a copy the
program writes; the copy leaves the block and the budget. Memory a Rust crate or
a C library allocates for itself is the global allocator's and no task's
budget.

## 5. Consequences

* A crash never leaves a half-changed value to be read; a cache that broke, or
  outgrew its budget, starts again instead of ending the process.
* One request's memory ends that request.
* **What it costs:** `std`'s collections change their ground; crossing into a
  Rust API that owns its collection becomes a copy; the content of a rebuilt
  value is lost; a full machine still ends the process, as it ends the BEAM.

## 6. What this does not decide

* **The cost** of a block per task and of fallible collections, measured.
* **A `Vec` a Rust crate hands back**: copied into the block, or kept as a
  foreign buffer the program views.
* **Freeing a task's block whole** when the task ends, which needs every value
  to have left it.
* **A value built outside a door and stored into a shared one**, which the
  task's block still pays for.
* **Whether `update` may run on a copy** for small values, so that nothing is
  ever poisoned.
