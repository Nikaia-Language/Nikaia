## 1. Question

**What executes the code a `comptime` calls, and what bounds it?**

A `comptime` initialiser that calls a function runs that function while the
program is built. Until now an interpreter inside the compiler did it, and
nothing stopped a body that did not end.

An interpreter is a second implementation of the language. It computed
`sq(100000)` with `fn sq(x: i32) -> i32` as `10000000000`, where the program
stops on the overflow; it cannot run a `std` function written in Rust, such as
`5.seconds()`; and it is slow enough that `fib(30)` takes the build minutes. A
build without a step budget hangs without a word, and *a budget added later
refuses only programs that already hang* is not so: it also refuses slow ones
that end.

## 2. How others do it

| Language | Build-time code runs | Bounded by |
| :--- | :--- | :--- |
| Rust `const` | rustc's own interpreter (Miri's core); no heap values | a lint after a large number of steps, an error by default |
| Rust `build.rs`, proc-macros | compiled for the host and run, with the dependencies | nothing; full privileges |
| Zig `comptime` | the compiler's interpreter | backward branches, 1000 by default, raised with `@setEvalBranchQuota` |
| C++ `constexpr` | the compiler's interpreter | steps (`-fconstexpr-steps`), loop iterations, operations |
| Nikaia grammars ([ADR-177](adr-177.md)) | the generated parser, compiled and run | — |

What transfers: Rust's build scripts show that compiling for the host against
the dependencies works at scale; Zig and C++ show that a deterministic count is
how a build-time evaluator is bounded. What does not: their interpreters, for
[ADR-177](adr-177.md) D1's reason.

## 3. Options, weighed

| Option | Why it lost |
| :--- | :--- |
| Keep the interpreter and teach it the language's types | a second implementation that every feature must be built into twice and kept equal |
| Interpret small cases, compile large ones | two implementations, and a size threshold that decides which answer a program gets |
| Emit Rust `const fn` and let rustc's const evaluation compute it | no heap: a table built from a file, the main use, cannot be a value there |
| Link the build-time program statically | measured: about 1 050 million instructions to compile and link a call into `std`, nearly all of it the linker merging `std`'s dependencies and their debug information; 338 million with the debug information stripped |
| Load the build-time code into the compiler's own process, using the `std` the compiler contains | the compiler holds only the part of `std` it calls, its symbols are not exported, and it is built with its own profile; a `std` shipped as a dynamic library with the compiler ties it to one set of build options and one platform's rules for shared libraries |
| A persistent host process that loads `std` once | saves only the start of one program per package and build (about 36 million instructions measured); not worth its machinery yet |
| A time limit | not deterministic: the same build would pass on one machine and fail on a slower one ([ADR-005](adr-005.md) D8) |

## 4. Decision

### D1 — A `comptime` whose initialiser calls a function is compiled to Rust and run; it is never interpreted.

The calls are lowered as the program is, built for the machine that builds and
run there; the program's answer is the value. One implementation of the
language computes both the build-time and the run-time answer, so an overflow,
a narrowing or a `std` function behaves at build time exactly as it does when
the program runs: `comptime C = sq(100000)` stops the build at the
multiplication, in the program's words.

An initialiser of literals alone — `4 * 1024` — is folded by the checker, which
computes it anyway ([ADR-285](adr-285.md) D22), and is not compiled.

### D2 — What a build-time body may call is unchanged, and now includes `std`'s Rust half and the Nikaia dependencies.

[ADR-287](adr-287.md) D13-D14 still decide it from the ledger: `sync`, and a
touch set that is empty or the build's parameters. A function that passes may
run whether this program, `std` or a Nikaia dependency declares it (D8):
`5.seconds()` runs from `std`'s Rust half. A function the ledger does not
describe touches everything and is refused (`NK1152`). A Rust crate's never
runs (D9).

### D3 — The dependencies are built first, and the build-time code links against them dynamically.

Cargo builds the package's dependencies as it does for the program. Beside the
package the compiler generates one crate that names `std` and every Nikaia
dependency build-time code may reach and builds it as a dynamic library, from the same compiled
dependencies: a crate type of its own changes nothing the dependencies are
built with, so they are reused and not built again. The build-time code links
against that one library and reaches the dependencies through it.

Measured on a call into `std`: about 132 million instructions to compile and
link, and 36 million to start and run, against 1 050 million for a static link.
The library is rebuilt when a dependency changes, not when a `comptime` does.
The shipped program stays statically linked.

Where the target is not the machine that builds, the dependencies build-time
code reaches are built a second time, for that machine, as Cargo builds a build
script's.

### D4 — One crate holds every `comptime` of a package, and its results are cached.

The package's build-time code is one crate, compiled by `rustc` directly and run
once; Cargo starts only for the dependencies. Its results are kept under a key
of the code that produced them — each initialiser and everything it calls — the
toolchain and the build's parameters ([ADR-287](adr-287.md) D15), so an
unchanged `comptime` is neither compiled nor run again.

### D5 — The build-time run goes beside the rest of the build.

No type waits for a build-time value ([ADR-287](adr-287.md) D21): the run starts
once the ledger has decided what may run, and only the check that a value fits
and the writing of the values wait for it.

### D6 — A result reaches the compiler as data and crosses as [ADR-311](adr-311.md) says.

The build-time program writes each value in an encoding the compiler reads back,
as a grammar run's does ([ADR-177](adr-177.md) D4); the crossing to the program
is unchanged. A value the crossing cannot write is still refused by what it is
(`NK1167`).

### D7 — There is a step budget, and it is counted, not timed.

The compiled build-time code counts each turn of a loop and each call; past the
budget the run stops, and the build is refused with `NK1152`, naming the
`comptime` and the call path it was in. The count is the same on every machine,
so a build that passes passes everywhere. The call depth stays bounded as well.

### D8 — A Nikaia dependency's functions run at build time only on entries this build derived from their sources.

A consumer believes a dependency's shipped ledger while its sources hash as
recorded ([ADR-100](adr-100.md) D3). That guards against a **stale** ledger, not
a **false** one: a package can ship honest hashes beside an entry that says
`touches = []` for a function that writes a file. At run time such an entry
misleads the checker; at build time it would let the package's code read and
write on the building machine. So before a dependency's function runs at build
time, this build derives that package's ledger from its sources, keyed by
their hashes and done once per version, and D2's rule reads the derived
entries. Where they disagree with the shipped ones, the build is refused
(`NK1152`), naming the package and both answers. A package that ships no
sources has nothing to derive from, and none of its functions runs at build
time.

### D9 — At build time only Nikaia code runs, and `std`'s Rust half.

What this compiler can vouch for is what it derives: `sync` and `touches` of
Nikaia code, its own and, by D8, a dependency's. A Rust body gives it nothing to
derive from — Rust reaches the system through `unsafe` and calls no signature
shows — and a description's columns are a person's judgement
([ADR-290](adr-290.md) D5), made for ordering statements at run time. A claim
does not become a proof by being written twice. So a Rust crate's function
never runs at build time, described or not, and neither does a Nikaia function
whose calls reach one: the call is refused (`NK1152`), naming the Rust
function and the path to it. `std`'s Rust half is the exception: it is this
project's own code, reviewed and shipped with the compiler
([ADR-020](adr-020.md) D5).

**Rejected:** believing the description's `touches`, which runs a stranger's
native code on a judgement made for another purpose; and a second, explicit
per-function claim in the description, which is the same judgement written
again.

## 5. Consequences

* `comptime` and the program cannot disagree: there is one implementation.
* Build-time code is as fast as the program, and as capable as its Nikaia code
  and `std`: a Rust crate stays out of it.
* What runs at build time is native code. What keeps it from reading or
  writing is no longer an interpreter that has nothing to reach a file with,
  but D2's rule, read off entries this build derived (D8), and no Rust but
  `std`'s runs (D9).
* **What it costs.** A dynamic library per package, rebuilt when a dependency
  changes; about 170 million instructions per package and build in which a
  `comptime` changed; a second build of the dependencies when cross-compiling;
  and the interpreter's call-evaluating part goes, with its tests.

## 6. What this does not decide

* **A Rust dependency's `build.rs` and procedural macros.** Cargo runs them
  natively, with full privileges, while it builds the dependencies, whatever a
  `comptime` does; D8 and D9 do not reach them.

* **The budget's default and how a program raises it** — what a program writes
  where it needs more, and where it writes it.
* **Memory** ([ADR-287](adr-287.md) D17): a build-time run is still unbounded
  in what it allocates.
* **Windows**: dynamic linking of Rust libraries there was not measured.
* **A grammar run** ([ADR-177](adr-177.md)) joining this crate rather than its
  own project.
