## 1. Question

**How does a program talk to a SQL database so that a mistake in a query is
found while the program is built, and the rows it gets back have fields?**

Two halves:

* **Where the SQL is checked, and by whom.** The compiler knows no SQL and must
  not learn one - there are a dozen dialects, and a company's own database is a
  thirteenth. What it knows is the `dsl` protocol of Part II 10.5: cut the
  block out at `eod`, hand the bytes to a grammar, take what the grammar
  declares. The protocol alone has no **schema** and no **result**.
* **Where the connection goes when a checked statement runs.** A statement is
  checked against one schema while the program is built; a connection is a
  runtime value. Unless something makes the two agree, a statement checked
  against one database can run on another, and its typed row describes columns
  that database does not have - found at runtime, which is what the first half
  promises does not happen.

## 2. How others do it

* **LINQ to objects** - `where`, `select`, `orderBy` over a collection in
  memory - is `filter`, `map` and `fold` over a `Vec` and a `Seq` here, with
  lambdas; nothing is missing but a keyword spelling.
* **LINQ to SQL** keeps `u.age > 18` as an expression tree, and a provider
  translates it to SQL at runtime. An expression the provider cannot translate
  fails at runtime, the SQL it emits is nobody's, and an N+1 query is
  invisible in the source.
* **An ORM** maps rows onto declared classes and generates the SQL; the same
  three costs, and a second model of the schema to keep in step.
* **Part II 10.5** already wrote the SQL as SQL, in the dialect the database
  runs, inside `dsl mysql { … } eod`, parsed while the program is built, with
  every `:hole` a typed named parameter - but a column the table lacks is
  found only by the database.

## 3. Options, weighed

| Question | Option | Verdict |
| :--- | :--- | :--- |
| Who checks the SQL | the compiler, with a built-in dialect | **rejected** - a dozen dialects, and a vendor's own would need a compiler change |
| | the driver's grammar, run by the compiler as every grammar is | **chosen** (D1) |
| Queries from code | expression capture and a provider (LINQ to SQL) | **rejected** - fails at runtime, SQL nobody wrote; [ADR-304](adr-304.md) closed without it (D5) |
| | an ORM | **rejected** - the row type is the mapping (D5) |
| Where the dialect lives | in `std` | **rejected** - nothing a second party needs |
| | in a driver package; `std::db` only the protocol two drivers share | **chosen** (D4) |
| Where the connection goes | the statement's subject, `by_age.execute(db; …)` | **chosen** by the owner (D7) |
| | a method of the connection | not chosen |
| | a build-time argument of the block | not chosen - a connection is a runtime value |
| Statement and connection agree | by a check at runtime | **rejected** - the error the build promised to find |
| | by the connection's type carrying its schema | **chosen** by the owner (D9-D11) |

## 4. Decision

### D1 — The dialect is a grammar in a driver package, and the compiler runs it as it runs every grammar.

`dsl sqlite { … } eod` names the grammar of the `sqlite` package, `dsl
postgres` the grammar of another, and a vendor's database is a package its
vendor writes without a change here. The compiler parses the rest of the file
in parallel, hands the slice to the grammar at build time, and builds the
statement's types from what the grammar declares. Nothing SQL-shaped is in the
compiler, and nothing will be.

### D2 — A grammar declares a result column with `meta::column(name, type)`, and the compiler derives the row type.

Beside `meta::capture` (*this variable, here, at build time*) and
`meta::parameter` (*a named argument at runtime*), the third and last
intrinsic:

| intrinsic | when it resolves | what the compiler builds from it |
| :--- | :--- | :--- |
| `meta::column(name, type)` | build time, declared by the grammar | the statement's **row type**: one field per declared column, named and typed |

A statement's value is a prepared statement whose `execute` takes a
connection as its subject (D7) and the parameters by name, and returns
`Seq[Row]` ([ADR-105](adr-105.md)), where `Row` is a struct the compiler wrote
from the columns: `SELECT name, email FROM users` gives `name: String` and
`email: String?` where the schema says the column is nullable, and `u.emial`
is `NK1117`. `SELECT *` declares every column, in the schema's order. A
computed column without a name (`count(*)`) is a build error from the grammar
asking for `AS`. The row type is not a struct the program can declare a second
time, and it needs no `use`.

### D3 — The schema is a build-time input of the block, and the driver's grammar reads it.

*Changed by [ADR-287](adr-287.md) D20: the schema is bound as `comptime APP = asset(…)`; there is no `comptime` expression.*

```nika
comptime APP = asset("schema.sql")                // ADR-310: read while the program is built

let db = sqlite::open("app.db"; schema: APP)       // D9

let by_age = dsl sqlite(schema: APP) {
    SELECT name, email FROM users WHERE age >= :min_age
} eod

for u in by_age.execute(db; min_age: 18) { println(u.email ?? "-") }
```

A `dsl` block may take **build-time arguments**, named, in parentheses after
the grammar's name - options only, so no `;` ([ADR-133](adr-133.md)). Each
resolves at build time to a `comptime` value of the surrounding scope:
`meta::capture`'s meaning given an explicit place. The grammar declares which
arguments it takes and their types; a block that leaves one out or passes one
it does not know is refused at the block, in the grammar's words.

The `sqlite` grammar parses `schema` with the driver's own DDL grammar (tables,
columns, types, nullability) and checks the statement against it: a table or
column the schema lacks is a build error **at the query**, a hole compared with
a column of another type is one, and the declared columns carry the schema's
types. A live database is never opened while the program is built
([ADR-287](adr-287.md)), which is why the schema is a file in the repository.
Whether the database opened at runtime still matches that file is the driver's
to verify at `open`, throwing a named error there rather than failing on the
first query.

### D4 — `std::db` is the protocol and nothing more; every dialect lives in a driver package.

`std::db` holds what two drivers must agree on without depending on one
another: the `Connection` and `Transaction` traits, the `Statement` protocol the
compiler's prepared statement speaks, and the values a row may carry - the
language's numbers, `bool`, `String`, `Bytes`, and `T?` for `NULL`. No grammar,
no SQL, no dialect, no binding to a database library. A driver package brings
the dialect grammar, the DDL grammar, the connection, and the target adapter
(the runtime's I/O thread on native, a Web Worker on the web). `http` left
`std` because nothing in `std` depended on it ([ADR-289](adr-289.md)); `db`'s
protocol stays because a **second party** - two drivers and every program that
changes drivers - depends on it.

### D5 — No expression capture, and no ORM.

No expression is captured as a tree and no provider translates one; a query in
memory is the `Seq` combinators. The row type **is** the mapping: a program
that wants a `User` writes `User { name: u.name, … }` or `with`, and a
migration is a SQL file the DDL grammar can read. Dynamic SQL is not refused: a
driver offers `raw(text)`, which returns untyped rows and is `Untrusted` on the
way in.

### D6 — The sentence for the reader who asked for LINQ.

*Nikaia does not translate your code into SQL. You write the SQL your database
runs, and your database driver checks it while the program is built - the
syntax, every parameter, every column against your schema - and the compiler
turns the result into a type, so a misspelled column is a compile error and a
row has fields. What LINQ promised, without the provider; and a vendor adds its
database by writing a package.*

### D7 — The connection is the statement's subject.

`by_age.execute(db; min_age: 18)`: the statement is the receiver, the
connection stands before the `;` and the parameters after it, as Part I 5.1's
*Subject `;` Config* reads anywhere else. A statement is not tied to a
connection for its life, so one prepared statement serves every connection of
a pool.

### D8 — `std::db` declares the `Connection` trait, and the compiler writes the conversion.

The trait has one method: run this text with these named `db::Value`s, and
hand back rows of `db::Value`. A driver implements it. The **compiler** turns a
row of values into the row type it derived (D2), in the one place that derived
it, so a driver never names a per-statement type and the conversion cannot
disagree with the row type. A driver does not write `execute(self;
...args: Self::dsl)` for a checked statement; the typed spread of
[ADR-296](adr-296.md) D5 stays for every other DSL a library drives.

### D9 — A connection's type carries the schema it was opened for.

A driver's `open` takes the schema - `sqlite::open("app.db"; schema: APP)` -
the same build-time value a statement's block names (D3), and the connection
it hands back is typed by that schema. D3's check at `open` that the database
matches the file is then part of the type.

### D10 — A statement handed a connection of another schema is refused while the program is built.

`by_age` was checked against a schema and `db` is typed by one; where they are
not the same schema, `by_age.execute(db; …)` is refused at the call, naming
both. Swapping two connections in a program with two databases fails the
build.

### D11 — The same schema is the same build-time value.

Two blocks that name `APP` are checked against one schema; a block that names
`APP` and a connection opened with `reporting` are two, even where the two
files say the same thing - the fail-closed reading ([ADR-010](adr-010.md) D1).
A program that means one database names one schema.

## 5. Consequences

* The compiler stays dialect-free, and a vendor's database is a package.
* A query's mistakes - a column, a parameter, the wrong database - are found
  before it runs.
* A row has fields, so `u.email` is checked, completed and documented.
* `std::db` is a page of traits and stays one; its first trait is
  `Connection` (D8), declared where the checker reads it, since an `impl` of an
  undeclared trait is a refusal.
* **What it costs:** one intrinsic and the derived row type in the compiler;
  build-time arguments on a `dsl` block; `std::db`'s traits; a connection type
  that carries a schema; and per driver a dialect grammar, a DDL grammar and a
  connection.
* **Costs if wrong:** a database type no `db::Value` carries grows the
  `Connection` trait by a method - an addition, not a break.

## 6. What this does not decide

* **Mapping a row into a declared struct** in one step (`SELECT … INTO User`);
  a literal or `with` until that is not enough.
* **Migrations tooling** - ordering, applying, recording; the DDL grammar reads
  them, and what runs them is a driver's or a tool's.
* **Which SQLite binding** the `sqlite` driver stands on - the driver's record,
  by [ADR-303](adr-303.md)'s standard.
* **Schema drift at runtime** beyond the driver's check at `open`.
* **How the schema is spelled in a written type**, for a program that writes a
  connection's type; it is inferred from `open`, and its spelling is not decided
  here.
* **The code of D10's refusal**, assigned when it is built, in Part III C.3.
* **How `app` itself is written at file level** - a top-level `let` is not an
  item; see `open-decisions.md`, *How a schema is bound while the program is
  built*.
