# ADR-303: The Runtime Is Nikaia's Own — It Starts Before `main`, Is Tuned When the Program Starts, Completes Files and Registers Every Readiness Wait; the HTTP Server Is Ours and TLS Is `rustls`

**Status:** Accepted
**Date:** October 3, 2026

## 1. Question

**Is the runtime under a Nikaia program - the I/O, the executor's threads, the
HTTP server on top - this project's own, or a finished one bound in; and if
ours, how does it serve each kind of I/O, when does it start, and who tunes it?**

Without an answer, every record that waits on "the runtime" waits on a word:
an HTTP handler has nothing to be called from, a cancelled cleanup has no queue
to park in, and `overlap` has no I/O whose two halves could be in flight
together. `tokio` had appeared in a parenthesis and a roadmap checkbox - chosen
by repetition, not decided. The answer cannot default because the two halves of
I/O have different answers, and the HTTP server sits on exactly the half where
the finished libraries are.

## 2. How others do it

| Language / tool | Its answer | What it costs there | Source |
| :--- | :--- | :--- | :--- |
| Rust, `tokio` | readiness (`epoll`) for everything; file I/O on a blocking thread pool | a regular file is always "ready", so every file read is a hand-off to a pool thread and a wake-up back | the superseded records' §1, from memory, not re-checked |
| Rust, `hyper` on `tokio` | a finished HTTP server over a readiness runtime | it pulls bytes from I/O it can *ask*; under completion I/O that needs a copy through an intermediate buffer, and the choice of server becomes the choice of I/O for sockets | the same; [ADR-289](adr-289.md) §2 |
| Linux `io_uring` | completion: the kernel performs the operation and reports it | no thread is involved; absent on older kernels, forbidden in some sandboxes, and nonexistent off Linux | the same |
| `rustls` | TLS as bytes in, bytes out | none here: it has no opinion about how bytes arrive | the same |

What does not transfer: `tokio`'s thread pool for files is exactly the cost a
completion queue removes, and a language whose overlap is written in the source
([ADR-292](adr-292.md)) has a reason to want two file reads to cost nothing
together that a library for Rust programs does not.

## 3. Options, weighed

| Question | Option | Why it lost, or won |
| :--- | :--- | :--- |
| The HTTP server | adopt `hyper` | it decides socket I/O for us and bridging it to completion I/O spends most of what completion was for; unmaking it later means replacing the server, not the plumbing |
| | **write our own** (D1) | HTTP is a grammar over bytes with a frame boundary, which [ADR-296](adr-296.md) exists for, and it exercises untrusted input and escaping on something real |
| TLS | write our own | years of security-critical work where a mistake is not slowness |
| | **bind `rustls`** (D2) | it constrains nothing about how bytes arrive |
| Files | a pool of threads, pre-started | removes thread creation and still pays a wake-up per pair |
| | **completion, blocking fallback chosen at run time** (D3) | no thread is involved, so a pair costs what one submission costs |
| A readiness wait | a worker blocked in a poller per wait | with one I/O worker by default, one wait that has not answered blocks every other |
| | one poller, a registration kept across waits | saves little beyond add-and-delete, and couples a socket's lifetime to the registry (§6) |
| | **one poller, arm on the caller, add and delete around each wait** (D8, D9) | nothing occupies a thread while it waits, and the hop - the real cost - is gone |
| When it starts | per operation, or lazily | a thread started per pair costs a wake-up per pair |
| | **before `main`, from a generated wrapper** (D4) | a link-time constructor has nowhere to report the drain's outcome |
| Tuning | build-time keys in `nikaia.toml` | the operator who runs the program is not the person who compiled it |
| | **a runtime file read at startup** (D5) | |

The number that decided the file half: on a running runtime a pair of file
reads on the completion path adds nothing measurable over reading them one
after the other, while the same pair on a pre-started thread pool adds a flat
wake-up of about 38 µs. The number that decided the readiness half: a wait
round-tripped through a worker cost about 35 µs, of which the hop to the worker
was about 28 and keeping a registration across waits about 6.

## 4. Decision

### D1 — The HTTP server is Nikaia's own, and `hyper` is not adopted.

A finished server would have to be given I/O it can *ask* for data, and
completion I/O *reports* data instead; bridging the two costs a copy through an
intermediate buffer. Adopting one would decide the socket half of D3 for us, and
undoing that would mean replacing the server rather than the plumbing under it.

The positive reason is larger: an HTTP request is a grammar over bytes with a
frame boundary ([ADR-296](adr-296.md)), its bytes are untrusted by construction
([ADR-010](adr-010.md)), and its responses are where escaping is the template's
contract ([ADR-017](adr-017.md)). Where the server lives - a package `http`
over `std`'s socket - is [ADR-289](adr-289.md)'s.

### D2 — TLS is never ours. `rustls` is bound, as a Rust dependency.

It is bound through [ADR-002](adr-002.md) D1's passthrough like any other Rust
crate. It takes bytes and produces bytes and has no opinion about how they
arrive, so unlike a finished HTTP server it decides nothing about D3.

### D3 — I/O is split by kind: completion for regular files, readiness for everything else.

A regular file goes to `io_uring` where the machine has it, with the blocking
path as the fallback where it does not - an older kernel, a sandbox that
forbids the syscalls, a target without either. The fallback is chosen **at run
time**: a binary built where `io_uring` exists runs where it does not, and the
probe is the ring failing to open. `fs::map` is not on this path; it hands back
memory the operating system owns.

**A regular file is the exception and everything else is the rule.** A pipe, a
terminal and a socket signal readiness honestly and block only while there is
nothing there; only a regular file is always "ready" while the read blocks in
the kernel anyway. So sockets and pipes are served by readiness, and how a
readiness wait is served is D8-D12. Standard input is a stream and not a
regular file, so it is not on the completion half; its read stays on the
worker path and is awaitable through the bell ([ADR-121](adr-121.md) D4).

Both halves live behind one `std` surface, so that the next change of mechanism
is a `std` change and not a compiler change: the choice is made at startup,
inside `std`, where a compiler could not have made it, and an `overlap`
([ADR-292](adr-292.md) D2) is served without the emitter knowing which
mechanism serves it. A regular-file operation on a runtime with nothing else in
flight runs on the calling thread instead ([ADR-263](adr-263.md) D1).

What the I/O threads run is `std`'s and nothing else: a worker's inbox is a
closed, private list of operations, and none of them carries a closure. That is
what makes [ADR-037](adr-037.md) D2's promise - nothing the user wrote runs
concurrently at `no` - a property of the types rather than of review.

### D4 — The runtime starts before `main`, and `user_parallelism` says what starts.

An I/O thread already running costs no thread start per operation, so it is
running before the first statement the user wrote. At `user_parallelism = no`
that is all that starts: the I/O workers, and everything the user wrote on the
main thread. At `yes` a pool for user code starts with it. The I/O workers are
the compiler's threads, not the user's, which is why they start at `no` too
([ADR-037](adr-037.md) D2).

`main` belongs to the runtime. The emitter renames the program's entry point
and writes a `main` that starts the runtime, calls it, and then finishes the
runtime. It is **generated code and not a link-time constructor**, because
finishing is the drain at exit ([ADR-297](adr-297.md) D6) and it has an outcome
to report. Which pool starts is written in by the **compiler**, because
`user_parallelism` is a build switch and not a runtime setting. Only the plain
shapes - `fn main()` and `fn main() throws`, no parameters, nothing returned -
are wrapped; a wrapper that guessed at a signature would be worse than none.

### D5 — Tuning is a runtime configuration file, read at startup.

`nikaia.toml` keeps what the **compiler** must know - `target` and
`user_parallelism` ([ADR-037](adr-037.md) D5). What the person running the
program tunes on the machine it runs on is read when it starts, from
`nikaia-runtime.toml` in the working directory, or from the file
`NIKAIA_RUNTIME_CONFIG` names outright (one binary, several deployments). The
keys are spelled as `nikaia.toml`'s are:

* `io-workers` - default `1`;
* `user-pool` - the pool for user code at `yes`, default `0`, meaning as many
  threads as the machine has;
* `io-method` - default `auto`, pinnable to `uring` or `blocking`. Pinning
  `uring` on a machine without it is a **failure to start**, not a silent
  fallback: the point of pinning is to find out whether it is there;
* `cleanup-deadline` - how long the drain at exit waits
  ([ADR-297](adr-297.md) D6), default `30s`.

[ADR-289](adr-289.md) D24 adds `send-file`, for how a file reaches a socket.
Any other key is a typo and fails, as under `nikaia.toml`'s `[build]`.
`cleanup-deadline` belongs here and not in `nikaia.toml`; a manifest that still
carries it is accepted and told where it went, because refusing it would fail
a manifest written to the specification that once documented it.

### D6 — HTTP/1.1 first. HTTP/2 is named as unbuilt until it is built.

HTTP/1.1 is the grammar D1 is about. HTTP/2 - header compression, flow control,
stream multiplexing - is a different order of work, and wherever the
documentation names it, it says it is not built.

**The risk is named rather than discovered.** A fresh HTTP/1.1 parser's
failure mode is request smuggling: a `Content-Length` and a
`Transfer-Encoding` that disagree, a header sent twice, a chunked body with an
edge case, and two servers in a chain then see two different requests. It is
met by a test corpus and a fuzzer written alongside the parser, not an audit
afterwards.

### D7 — A Rust crate may bring its own runtime, and two rules keep that sound.

[ADR-002](adr-002.md) D1 promises crates.io, so a program may depend on a crate
that starts threads and an event loop of its own. That is allowed, under two
rules:

* **A value may cross into a foreign thread only if it may cross any thread.**
  At `user_parallelism = no` a `Shared` may be a plain count
  ([ADR-037](adr-037.md) D3), and a foreign runtime that moves it would make
  that unsound. The structural `Send` check of [ADR-005](adr-005.md) §5 refuses
  such a crossing as `NK2502`, at **both** settings, because `user_parallelism`
  bounds what the program runs at once and a foreign runtime's threads are not
  the program's; a described call is asked the same through its `threads`
  column ([ADR-290](adr-290.md) D6, D7). **The rule reaches only as far as the
  foreign crate is honest**: a Rust API that writes `unsafe impl Send` about a
  type that is not puts the value on another thread with nothing complaining,
  and no frontend check can see into the callee's body to catch it. So the
  honest statement is conditional: a crossing is refused where the signature
  that carries it is true.
* **A `Cleanup` may not be owned by a foreign task.** A cancelled cleanup parks
  with *this* runtime ([ADR-297](adr-297.md) D5), and a foreign runtime's
  shutdown will not drain that queue; a `Cleanup` handed across is a cleanup
  that may never run.

What needs no rule: nothing is known about a foreign crate's effects, so its
`touches` is absent, so it reaches and orders against everything
([ADR-292](adr-292.md) D3). Interop cannot silently break the ordering
guarantee; it only makes the program that uses it slower.

### D8 — A readiness wait is a registration on one poller for the process, armed on the calling thread.

There is one poller for the process with one thread inside its `wait`.
Registering is an `epoll_ctl` and does not block, so there is nothing to hand
to anybody: the caller arms and gets a future. When the kernel answers, the
poller's thread fills the slot, wakes the waker and rings the bell.
**Nothing occupies a thread while it waits for something that has not
happened.** With one I/O worker by default (D5), a wait that occupied the
worker blocked every other wait in the process - a ceiling on the default
configuration, not a slowness, and the shape an HTTP server has exactly (a
server waiting on `accept` while a connection waits on `read`).

What a program writes is unchanged: this is the mechanism under D3's readiness
half, not its surface.

### D9 — The hop to a worker is what is removed; a registration is added and deleted around each wait.

The shape was chosen by measurement and not by the plan's wording: the plan
said *keep registrations*, and the hop to a worker turned out to be most of the
cost while keeping a registration across waits is a small part of it (§3). So a
wait adds its registration and deletes it when it is answered, and keeping one
across waits is left open (§6).

### D10 — A registration is *outstanding*, exactly as a worker operation is.

The runtime's count of pending operations includes registrations, and the drain
at exit ([ADR-297](adr-297.md) D6) waits them out. The park asks *is anything
outstanding* before it sleeps, and the drain asks it before it lets a program
go. A registration that leaves wakes the drain, as an answer arriving does.

### D11 — The bell stays, because a `Waker` does not reach a parked executor.

[ADR-121](adr-121.md) D1's bell is what wakes a thread asleep in the ring's
`io_uring_enter` or on the condvar, and neither watches a waker. So the poller's
thread rings it as a worker does, and the waker it also wakes is for an
executor that honours one.

### D12 — A cancelled wait costs nothing: dropping the future deletes the registration.

For a socket that is a connection the program stopped caring about, which is
the case a server meets most.

## 5. Consequences

* **Every record that waited on "the runtime" has one.** An HTTP handler
  ([ADR-289](adr-289.md)) runs on it, a cancelled cleanup
  ([ADR-297](adr-297.md) D5) has a queue to park in, and two file reads in an
  `overlap` cost what one submission costs on a machine with a completion queue.
* **One thread serves many connections at `user_parallelism = no`**, because no
  wait occupies a thread (D8), which is what [ADR-289](adr-289.md) D10 rests on.
* **The dependency surface grows** by `rustls` and, on Linux, an `io_uring`
  binding. Neither reaches a `.nika` file: D3's `std` surface is what a program
  sees.
* **The fallback is not free.** Where the machine has no completion queue, a
  pair of file reads pays a thread wake-up; starting the runtime early is
  necessary for a free pair and not sufficient.
* **A worker operation is one that does something**, where blocking a thread is
  the work rather than the waiting; readiness is not one of them.
* **D7's first rule is conditional** on the honesty of a foreign signature, and
  the second can only be enforced once the cleanup [ADR-297](adr-297.md) parks
  exists.

## 6. What this does not decide

* **Keeping a registration across waits.** It is worth a small part of what is
  left of a wait, and it wants the *socket* to own the registration and
  deregister on close - a lifetime coupling between `net::Connection` and the
  registry.
* **Waking one task instead of every pending one.** The bell rings and the
  executor polls every pending future, which at one thread is a handful; a
  server with a thousand connections is the measurement that would move it.
* **What a timeout does to a server.** Per-registration deadlines exist and
  nothing in `net` passes one; a slow peer is met by the server's caps
  ([ADR-289](adr-289.md) D13).
* **What `io_uring` adds for sockets** - mainly batching syscalls - is not
  measured, and nothing here moves sockets to completion.
* **HTTP/2, keep-alive, chunked bodies and TLS's place in the server** are later
  steps ([ADR-289](adr-289.md) §6).
