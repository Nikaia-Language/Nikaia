# ADR-055: The Emitted Rust Is `async` Where a Function Can Pause

**Status:** Accepted · **Built:** all five steps of §6, at both settings of `user_parallelism` — see §6
**Related:** [ADR-027](adr-027.md) D1 and D2 (the `sync` property, which **is**
this decision's input — already inferred, per function, in the safe direction),
[ADR-023](adr-023.md) D8 (the same shape one property over: `throws` becomes a
`?`, and this makes *can pause* become an `.await`),
[ADR-038](adr-038.md) D3 and D4 (the I/O and the runtime this drives, and why the
executor is ours), [ADR-037](adr-037.md) D2 (`user_parallelism`, which decides how
many threads the executor has and nothing about what a program means),
[ADR-005](adr-005.md) §1 (written over *implicit async* from the start),
[ADR-006](adr-006.md) (`Cleanup`, whose whole reason is that any function may
pause), [ADR-050](adr-050.md) D6 (which is **unbuildable** without this),
[ADR-004](adr-004.md) D2 (the rule this puts under the most pressure),
Part I 1.2 (what a switch may change), Part II 11.2 (the sentence this makes true)

## 1. Context

**The language was specified as implicitly async, and the lowering never was.**

That is not a contradiction anybody introduced; it is a gap that has been open
since Stage 0 began, and both halves are written down. [ADR-005](adr-005.md) §1
reasons about *"an I/O suspension point, which implicit async inherits free from
`async fn`'s"*. [ADR-006](adr-006.md) exists because *"any function may pause at
I/O"*. [ADR-027](adr-027.md) infers, for every function, whether it can pause.
Meanwhile the emitted Rust contains the word `async` **zero** times, and a pause
is a thread that blocks.

For most of what a program does, the difference is invisible: a blocking read and
an awaited read return the same bytes. It becomes visible at exactly one place,
and that place is `spawn`.

**`spawn` is where the gap stops being harmless.** Part II 11.2 says a task at
`user_parallelism = no` is *"interleaved on the same thread"*, and Part I 1.2 says
a build switch changes *how* a program runs and never *what* it computes. Two
synchronous Rust closures cannot interleave on one thread — there is no point at
which either yields — so with a synchronous lowering `spawn` at `no` has only
these readings:

* **run the body at the `spawn`**, which is a legal *schedule* of `yes` but
  deadlocks the program where `yes` would not, and makes Part II 11.2's sentence
  false;
* **run it at the `.join()`**, which silently drops a task nobody joins — and
  Part I 8.2's own example keeps no handle;
* **refuse `spawn` at `no`**, which makes a library that uses one un-compilable
  where it is consumed, the thing Part II 11.2 exists to prevent.

Each of the three costs something the specification already promised. So the
lowering is what has to move.

## 2. Decisions

### D1 — A function is a plain `fn` exactly where `sync` says so, and an `async fn` otherwise.

**The input already exists and needs nothing new inferred.**
[ADR-027](adr-027.md) D1 computes, per function, over the call graph, resolving
into a library's ledger: *"a function is `sync` when every call it makes resolves,
and every callee is `sync`"*. That property is "cannot pause", which is exactly
the question `async fn` asks.

**And its conservatism is already the safe direction**, which is why this is a
lowering change and not an analysis change. [ADR-027](adr-027.md) D2 takes the
claim away from a function whose call the compiler cannot resolve — so an
unresolved call makes a function *not* `sync`, which here makes it `async`. An
`async fn` that never awaits is a future that finishes on its first poll; a plain
`fn` that needed to pause is a program that does not compile. The error the
inference can make is the cheap one.

A `sync` a source **asserts** stays asserted ([ADR-027](adr-027.md) D4) and stays a
plain `fn`. An assertion that is wrong is already refused.

### D2 — A call to a function that can pause gets an `.await`, and that is not resolution.

```nika
let text = fs::read_to_string(path)      // `read_to_string` can pause
```

```rust
let text = nikaia_std::fs::read_to_string(path).await;
```

**The precedent is one property over.** [ADR-023](adr-023.md) D8 makes a call to a
`throws` function carry a `?` — punctuation the emitter writes where the ledger
says the callee can fail, and nothing the source spells. This is the same
mechanism reading the neighbouring column: where the ledger says the callee can
*pause*, the call carries an `.await`.

So [ADR-011](adr-011.md) D2's *"name for name, and the emitter resolves nothing"*
survives intact. `.await` is not a name and nothing was looked up to place it: the
ledger was consulted about the callee, which is what the ledger is for, and it is
the same consultation the `?` already makes.

### D3 — The executor is ours, and it drives the I/O that is already there.

[ADR-038](adr-038.md) D3 built the I/O: completion for files, readiness for
everything else, both behind one `std` surface. D4 starts it before the program's
first statement.

**So a second runtime is not bound.** A `tokio` or a `smol` beside `rt` would be
two event loops in one process, which is what D7 is about for a *foreign* crate
and is no better when we do it to ourselves. What is needed is an executor — a
task queue and a waker — over the completion and readiness sources that exist.
That is the smaller half of an async runtime, and the half `rt` does not have.

`rt::start` becomes the thing that drives `main` to completion rather than the
thing that starts threads beside it.

### D4 — `user_parallelism` decides how many threads the executor has, and nothing else.

| setting | executor |
| :--- | :--- |
| `no` | one thread — the program's own. Tasks interleave on it at their suspension points. |
| `yes` | the pool [ADR-038](adr-038.md) D4 already starts. |

**This is what makes Part II 11.2's sentence true**, and it is the whole reason
the owner chose this answer over the reachable ones in §1: at `no` a task really
is *interleaved on the same thread*, because a suspension point is now a place
where the executor may run something else rather than a thread that blocks.

And it keeps Part I 1.2 exactly: the set of schedules narrows from "any" to "one
at a time", and a program's meaning does not change. `no` remains
[ADR-037](adr-037.md) D2's *"nothing the user wrote ever runs concurrently"* —
interleaved is not concurrent.

### D5 — `spawn` hands back a `TaskHandle`, and `.join()` is an `.await`.

```nika
let handle = spawn fn { process(path) }
let result = handle.join()
```

The body becomes a future the executor owns, and the captures move into it, which
is Part I 8.3's `@detached` rule and Rust's `move` closure meeting at the same
place. `.join()` awaits the handle. Both are the same at either setting, which is
Part II 11.2's *"uniform API"*.

A task nobody joins still runs: the executor owns it, so nothing is dropped by a
program that spawns and forgets — which is Part I 8.2's own example.

### D6 — What this costs is written down rather than discovered.

**Every signature that can pause changes shape.** A reader comparing the two
languages sees `async fn` where the Nikaia said nothing, which puts
[ADR-004](adr-004.md) D2's *"the text a person reads is the text that is
compiled"* under more pressure than any other lowering does. It is still honest —
the function *can* pause, and Nikaia's answer to "which ones" is `sync`, which is
written where it is true rather than where it is not. But the generated Rust stops
looking like a transcription in this one respect, and that is a real cost.

**Three of async Rust's sharp edges arrive with it**, and none is hypothetical:

* **Recursion.** An `async fn` that calls itself needs its future boxed, or
  `rustc` refuses with a recursive type. A recursive Nikaia function that can
  pause is an ordinary program, so this has to be handled rather than met.
* **A borrow across a suspension point.** It is sound in Rust and it constrains
  the lifetimes the emitter writes ([ADR-008](adr-008.md)), so a view held across
  an `.await` is a case the view analysis has never been asked about.
* **`Send` on a spawned future.** At `yes` the executor moves a task between
  threads, so the future must be `Send` — which is the structural check
  [ADR-005](adr-005.md) §1 Group B already runs on what a task *captures*, now
  also asked of everything the body holds across a pause.

**`sync` becomes load-bearing.** Today it is a claim the compiler checks and
nothing acts on; here it decides a function's shape in the emitted program. That
is what [ADR-027](adr-027.md) was for, and it means a regression in the inference
is now a regression in the output rather than in a note.

## 3. What this makes buildable

**`spawn`** (`docs/open-work.md`), and the five records the list says wait on
it — Part II 11.2, [ADR-040](adr-040.md) D1's task half,
[ADR-045](adr-045.md) D2, Part II 12.2's counter, and
[ADR-050](adr-050.md) D2's `overlap`.

**[ADR-050](adr-050.md) D6 in particular, which is unbuildable without this.** It
says *"a branch is started up to its first suspension point before any branch that
cannot suspend is run"* — a sentence about a suspension point that the emitted
program did not have. With D1 and D2 it has them, and D6's schedule is something
an executor can be asked for.

**And `fs::read_both`, measured and unreachable.** The reason a statement pair
degraded at `no` was named *"no event loop, no sidecar and no async lowering
yet"* — [ADR-038](adr-038.md) quotes it and says two of the three had gone. This
is the third.

## 4. What this does not decide

* **Whether `std`'s surface keeps its blocking shape anywhere.** A function that
  cannot pause stays a plain `fn` by D1, and some of `std` genuinely cannot —
  `text::digit_value` does arithmetic. Which entries are which is a reading of
  `std.contracts`, not a decision.
* **Whether a Nikaia program may be *called from* Rust.** An `async fn` is harder
  to call than a `fn`, and nothing in this repository does it yet.
  [ADR-038](adr-038.md) D7's foreign-runtime rules are about the other direction.
* **How a recursive pausing function's future is boxed** — where the `Box::pin`
  goes, and whether the emitter writes it always or only where recursion is
  detected. D6 names the problem; the answer is an implementation reading.
* **`.await` as a Nikaia spelling.** Part II 11.2 writes `handle.await`, and this
  record makes `.join()` the built form. Whether the language also offers the
  field-looking spelling is a question about Part II 11.2's own text.

## 5. Rejected

* **Run the body at the `spawn`, at `no`.** The cheapest answer, and §1 says what
  it costs: Part II 11.2's sentence becomes false, and a program deadlocks at one
  setting that runs at the other. It was offered and the owner refused it.
* **Bind `tokio`.** It brings an executor *and* an I/O layer, and
  [ADR-038](adr-038.md) built the second one already. Two event loops in one
  process is the state D7 treats as a hazard when a foreign crate causes it.
* **Make every function `async`.** Simpler than reading `sync` — and it throws
  away the one thing `sync` is for, makes `text::digit_value` a future, and
  removes the reason to write the word.

## 6. What is built

**Step 1's single-threaded half**, and the order matters because each step is
testable on its own:

1. **The executor** in `rt`, over the completion and readiness sources
   [ADR-038](adr-038.md) D3 built. One thread at `no`, the pool at `yes`; `main`
   is what it drives.

   **The `no` half is built** — `rt::exec`: a task queue, a `Waker` written out
   by hand over an atomic flag, `block_on`, a `Slot` a task's value leaves
   through, and `Yield` as the smallest suspension point there is. The decisive
   test is `two_tasks_interleave_on_one_thread`, which is Part II 11.2's
   sentence and was unreachable before: two synchronous closures have no point
   at which either gives the thread up. A task nobody joins still runs (D5), and
   a `Slot` wakes whoever is waiting on it, which is what makes `.join()` a
   suspension point rather than a wait.

   **The `yes` half is built too**, and it is the second executor that
   sentence predicted rather than a use of `rayon`'s: a pool of **closures**
   cannot hold a future to be polled again later, which is what a task that
   pauses is. `rt::pool` is a queue of futures over the same worker count
   (`user-pool`), and `rayon` keeps `fs::map`'s UTF-8 check and the parallel
   piece driver.

   **One difference from the `no` half, and three things follow from it.** A
   task may be polled on a thread that did not start it, so: its future must
   be `Send` (D6); a waker has to reach the queue from any thread, so a task is
   an `Arc<Cell>` a waker pushes back rather than a flag one loop reads; and
   **exactly one thread at a time may wait in the I/O**, because the ring is
   behind a lock and a thread inside `io_uring_enter` is woken by the kernel
   and by nothing else. That thread is the **pilot**, and the others wait on
   the pool's bell.

   **`main` does not take the I/O park at `yes` while the pool is carrying
   tasks**, for the same reason: it waits on the runtime's bell instead, and
   everything that could wake it rings that — a completion the pilot noticed, a
   `Slot` filled by a task, a task finishing. Without it a `.join()` across a
   thread would be a `main` asleep in the kernel that a pool thread could not
   reach.

   **What a wake during a poll costs is the reason for four states.** The
   future is out of its cell while it runs, so a waker arriving then must not
   queue it — and if it only declined, the wake would be lost. It is recorded,
   and the worker that finishes the poll re-queues.

   **Measured, on four cores**: four tasks of the same size take 1.58 s at `no`
   and 0.65 s at `yes`, which is what `user_parallelism` is a switch for and
   what Part II 12.2's counter was waiting on.

   And `block_on` **panics rather than parks** where a task is waiting and
   nothing can wake it. Until step 3 a pausing `std` entry blocks the thread
   instead of returning a future, so that state means a future returned
   `Pending` without arranging a wake - a defect in `std`, and a hang is the
   worst way to report one.
2. **D1 and D2 in the emitter** — `async fn` where the ledger's `sync` column
   says the function can pause, and an `.await` at every call to one. The
   ledger already reaches the emitter; `sync` is already in it.

   **Built.** The `.await` goes before the `?` for the reason D2 gives, and the
   program's own `main` is driven by `rt::exec::block_on` where it can pause and
   called directly where it cannot — so a program with no I/O pays for no
   executor.

   **The negative half is what carries it.** Across ten examples, **22**
   functions are `sync` and **17** can pause, so the column holds real
   information and §5's *"then make everything `async`"* objection does not
   apply: that would be the same diff and a lie about what a call costs.

   **A method call's answer comes from the checker**, the way its `?` already
   does: `stats.add(5)` names `add` and only a type checker knows what it goes
   to ([ADR-028](adr-028.md)). `Checked::pausing_methods` is
   `fallible_methods` one column over, and narrowed the same way — a name that
   in one statement is both a pausing call and a call that is not is in neither
   set.

   **`std` is deliberately not consulted.** A pausing `std` entry still blocks
   its thread until step 3, so awaiting one would be awaiting a value rather
   than a future; that is what makes this step compilable on its own instead of
   having to land with step 3. Since it is what the emitter asks about that
   decides, no corpus program is refused for calling one.

   **§2 D6's first edge arrived from the corpus**, not from reasoning:
   `examples/json/src/main.nika`'s `show` and `longest` are both recursive and both
   pausing, and *"recursion in an async fn requires boxing"* about the generated
   file is the Part III C.1 class. So a call that closes a cycle of pausing
   functions puts its future behind a pointer.

   **And the boxing is a property of the call, not of the callee.** `countdown`
   boxes the call it makes to itself; the call `main` makes to it holds that
   future exactly once, is finite, and pays no allocation. `A -> A` beside
   `B -> B` where `B` also calls `A` is what makes *"both are in a cycle"* the
   wrong test — nothing about `B -> A` is recursive — so the test is that the
   callee can reach the caller again, which is what closing a cycle is. The
   graph over-approximates in the other direction: a method call draws an edge
   to every pausing name it could be, because boxing a call that did not need it
   costs one allocation and missing one is a program that does not compile.

   **A lambda whose body pauses is refused, and by the lowering rather than by
   the checker.** Rust has no stable `async` closure, so there is nothing to
   write. The refusal is deliberately not a type error: `examples/fortunes.nika`'s
   route handler is a lambda that queries a database and is a *correct* program,
   and refusing a correct program is the one thing the compiler may never do
   (Part III C.4). So it still checks clean and only a build meets the limit —
   which is also where step 3 and step 4 close it, once `std`'s own signatures
   say which parameters take something that may pause and a lambda handed to one
   can be a closure that returns a future.

   **What step 2 does not reach, and has no corpus case for:** a recursive
   pausing **method**. The emitter has no key for a method call — that is the
   checker's — so a cycle through one is not boxed. `docs/open-work.md` carries
   it with that evidence.
3. **`std`'s own pausing entries** become `async`, which is the largest single
   diff and the one with no decisions in it.

   **Built, and it had two decisions in it.** What "no decisions" missed is that
   a signature becoming `async` is the easy half; a *body* that actually
   suspends is a mechanism, and the vehicle a pair of statements travels on is
   a closure.

   **The executor is now the one place a program parks.** Before this,
   [ADR-038](adr-038.md) D3's file operations blocked the calling thread — the
   ring waited in `io_uring_enter`, the fallback waited on a reply channel. A
   file operation is now a **slot** on the ring, or a worker's reply, behind one
   `rt::io::InFlight`; polling it never blocks, and `exec::block_on` waits in
   the I/O when nothing else on the thread can move. So a suspension point is
   a place the executor runs something else, which is what step 1 built the
   queue for and what Part II 11.2 promises.
   * **No I/O future stores a waker**, and that is the design rather than a
     shortcut: what a read waits for is the I/O, the executor is the only thing
     that parks, and it re-arms everything it holds when the I/O moves. A waker
     rung inside the future would be a spin — a ready task, polled round after
     round, and never a park to wait in.
   * **The park reads a generation before it polls.** A completion that arrives
     between the poll and the park has already moved that count, so the park
     returns at once instead of waiting for a wake that has already happened.
     The fallback needs it because its reply channels are one per operation and
     nothing can wait on *whichever finishes first*; a worker bumps the count
     and wakes whoever is parked.

   **The first decision: an overlapped pair whose halves pause needs a different
   vehicle.** [ADR-033](adr-033.md) D10's pool vehicle is `rayon::join`, which
   takes **closures** — and Rust has no stable `async` closure, so a pausing
   half has no shape there. A vehicle taking two futures had to exist instead —
   an `async`
   *block* is one, and what it does at `user_parallelism = no` is Part II 11.2's
   own sentence: both polled, whichever suspends gives the thread to the other,
   no thread wake-up at all where the pool's costs ~48 µs. The choice is per
   **group** and not per function, because a function may be `async` for a call
   that has nothing to do with the group — and the pool's closure pair was still
   what a pair that could not pause got.

   **Both of those vehicles are gone**, with the automatic grouping itself
   ([ADR-050](adr-050.md) D1): what the argument produced and what outlived it is
   the finding that a pausing branch needs **futures**, which is what step 5's
   `overlap<n>` is built on.

   **The second: `cli::args` was never a pausing entry and the ledger said it
   was.** An absent `sync` line means *not* `sync`, which is this file's own
   conservatism — and reading the vector the process was started with is memory.
   Nobody had classified it. It surfaced the moment `std`'s pausing entries were
   awaited: `cli::args()` became `cli::args().await` and `Args` is not a future.

   **`std::io` is `async` and does not suspend yet**, which is D3's own split
   rather than something this step left half done: that mechanism serves
   **files**, and a stream needs the readiness half, which is built for sockets
   and not wired to standard input. An `async fn` that never awaits finishes on
   its first poll, so a caller sees what it saw before. `fs::map` is the same
   shape for a different reason — a mapping has no transfer to complete.

   **And one soundness bug, which the corpus found.** `rt::uring`'s rule 3 —
   *"the next operation reconciles before it submits"* — reclaims a slot an
   abandoned call left behind, and it read *"finished and nobody in a call for
   it"* as free. That was true while every caller finished its operation inside
   the call that started it. A future does not: it is started at its first poll
   and its answer taken at a later one, and in between the slot is finished and
   nobody is in a call. So the buffer the kernel had filled was dropped and the
   read came back as another operation's bytes —
   `a_group_of_four_compiles_and_runs` printed `ccc leer` for `zwei vier`. A
   slot is now *owned* by its handle until its answer is taken, and the
   handle's own `Drop` gives it back, so a future dropped before it finished
   still returns its slot.
4. **`spawn` and `TaskHandle`** (D5), and `NK2101` with them — the move into a
   task is what the diagnostic is about.

   **Built, at `no`.** `spawn fn { … }` is `TaskHandle::start(async move { … })`,
   `.join()` is an `.await` read off the ledger like any other pausing call, and
   both are what Part II 11.2 calls the uniform API. Two tasks reading two files
   are both in flight before either finishes, on one thread, which is that
   section's own sentence about something a *program* writes rather than about
   `std`'s futures.

   **An `async` block and never a closure**, for the reason step 3 gave: a
   task's body may pause, and Rust has no stable `async` closure. `move` is
   Part I 8.3's implicit move and Rust's `move` meeting at the same place.

   **Three things the build settled**, and each was a sentence in the
   specification that was not true yet:

   * **`spawn` took `( expr )`**, which Part I 8.2 called *"a bug in the parser
     and not a second form"*. It takes the trailing lambda of 5.3 now, so there
     is one lambda form in the language; the parenthesised spelling stays as a
     sentence rather than as an alternative, because programs were written
     against it. A lambda that **names** an argument is `NK2103`: a task is
     handed nothing, and dropping the name silently would make the body refer to
     something nothing declares.
   * **A task nobody joins did not run.** `block_on` returned the moment `main`
     was ready, so the task was a future in a queue nobody polls again — and D5
     says it runs, which Part I 8.2's own example needs, since it keeps no
     handle. `main`'s value is held until the queue empties.
   * **`.await` was a spelling the specification offered** on a handle, beside
     `.join()`. Part I 8.1 says a Nikaia program contains the word nowhere, and
     a test reads the corpus to hold it — so the two contradicted each other and
     D5 is what settles it: `.join()` is where two *tasks* meet, and the
     `.await` is the compiler's to write.

   **`NK2101` is narrow, and the narrowing is the work.** Only where the type is
   **known** and a move takes the value away. A number, a `bool`, a `char` and a
   **view** are copied — which is why `let message = "Hello"` is *not* Part I
   8.3's case and `"Hello".to_string()` is; a handle on a `Shared[T]` is
   duplicated, which is the exemption 8.3 states
   ([ADR-040](adr-040.md) D1, D5); a type nothing describes is not claimed about
   at all (Part III C.4); and an **assignment** between the task and the later
   use clears it, because giving the name a value again is a correct program.
   What it takes back is `rustc`'s *"borrow of moved value"*, whose advice named
   a **closure** the program does not have (C.1).

   **What is not built is the thread.** At `yes` a task moves between threads, so
   its future must be `Send` (§2 D6) — and that executor is step 1's `yes` half.
5. **[ADR-050](adr-050.md) D2's `overlap`**, which its own §5 orders after
   `spawn`.

   **Built**, and it needed less from this record than the order suggested. What
   it wanted was a vehicle that takes **futures** rather than closures — the
   same thing step 3 needed for an overlapped pair — and `std` grew one per
   arity, `overlap2`..`overlap8`. `spawn` itself is not in it: D4 says an
   `overlap` is not a task, so a branch is an `async` block that borrows rather
   than an `async move` one that owns.

   **D6 is where this record's work shows.** *"A branch is started up to its
   first suspension point before any branch that cannot suspend is run"* was a
   sentence about a suspension point the emitted program did not have; it is the
   argument order now, read off the same `sync` column D1 reads.

**Steps 1–3 are done, and the risk they were said to carry did not arrive.**
*"Until step 3 lands, a program that calls a pausing `std` entry will not
compile, so the three land close together or behind a switch"* turned out not to
bind: step 2 asks the **emitter** what pauses, and it was written to ask about
this program's own functions only. A pausing `std` entry stayed a plain call
with no `.await`, so the corpus compiled and ran between the steps and each one
was testable on its own, which is what §6 wanted from the order in the first
place.

**All five steps are done at `user_parallelism = no`, which is the default**, so
the thing this record was written for exists: `spawn` lowers, `overlap { … }`
parses and runs, and what a task means at `no` is what Part II 11.2 said it
was — **and at `yes` too**, where a task means a thread.

**All five steps are done at both settings of `user_parallelism`.** Five
records were checked and unrunnable when this was written, and every one of them
runs: Part II 12.2's counter is on more than one core, and
[ADR-045](adr-045.md) D2's lock in a task is a program — four tasks bumping one
`SharedMut[i64]` on four threads print every increment, which needed this
record's thread and [ADR-064](adr-064.md)'s type and could not be run with
either one alone.

**What this record does not carry to the end is D6's `Send` as a *refusal*.**
The pool's starter asks for it, so a task holding something that may not cross
