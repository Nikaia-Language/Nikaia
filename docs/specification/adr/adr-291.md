## 1. Question

**What may a program write where a value is taken apart — at a `let` and at a
`match` arm — and what does each form promise?**

Six questions meet at that place:

* Part I 8.1.2's `let (user, rights, prefs) = overlap { … }` and Part II 12.5's
  `let (tx, rx) = …` need a `let` that takes more than one name.
* A value that arrives and is not wanted — a tuple's half, a parameter a shape
  dictates, a lambda's argument — needs a way to be ignored without a name
  nobody reads, and that way must not *discard* a value the source says is
  *bound*, as Rust's `let _ =` does.
* `match` needs more than a literal and a path with bindings (`examples/calc`
  wants to match `step`, not `step.0`). A range pattern brings a second
  question: Rust's inclusive pattern is `..=`, and `..` must mean one thing.
* The catch-all arm needs a spelling that is not the ignore pattern's.
* A `match` missing a case must be refused in this compiler's words, not
  `rustc`'s on a Nikaia line, since Part I 3.4's first sentence promises every
  case is handled.
* `match s { Shape::Named(n) => … }` must not move the `String` out of `s` where
  the arm only reads it, or a second read of `s` is a correct program refused.

They are one record because they are one construct read from two ends: what a
pattern may be, which character means what inside it, when a set of arms is
complete, and what a binding takes.

## 2. How others do it

| Language | Its answer | What transfers | Source |
| :--- | :--- | :--- | :--- |
| Rust | Full patterns at `let` and `match`; `_` is the *wildcard* and `let _ = x` drops a temporary at once, which is how a guard's release is timed; `_name` silences the unused warning; `a..b` exclusive, `a..=b` inclusive, and only `..=` in a pattern; a guard is `if`; a non-exhaustive `match` is refused; a `match` on a place binds by value and moves | The lowering of every shape here is Rust's, verbatim; the coverage rule is the same, so the two answers agree. Not the word *wildcard*, not `let _ =`, not the range spelling, not moving by default | D1, D7, D13, D19, D23 |
| Kotlin, Swift | `a..b` includes its end and `a..<b` excludes it | The pair D13 takes, read the same way | D13 |
| Every neighbouring language | A guard is `if` | D11 | D11 |

## 3. Options, weighed

| Question | Rejected | Why it lost |
| :--- | :--- | :--- |
| How much a `let` takes apart | A pattern language at `let` | `match` has patterns; neither site needs them, and a bigger answer is a decision rather than the repair (D1) |
| | A second statement variant | Additive and cheaper, and a walk that has to remember it is a walk that will forget it (D2) |
| | Comparing a tuple's width with the names | A value this compiler cannot see is `?`; refusing it would refuse a correct program (D3) |
| | Ignoring `let (a, b): T` | It drops something the author wrote (D4) |
| What `_` is | A name, as it was | `let _ = f()` then means *discard* below and *bind* above |
| | Rust's `let _ = expr` to time a drop | The one thing it is used for is the one thing a reader cannot see in it; a resource is closed by name or ends with its scope (D7) |
| | `_name` for *bound but unused* | No warning to silence; a name not meant to be read should not be there (§6) |
| A guard's word | `where` | A second word for a condition, [ADR-276](adr-276.md)'s cost for nothing (D11) |
| A range pattern | Rust's `..=` in a pattern, `..` exclusive elsewhere | A reader from Rust looks for `..=`, and `1..5` would mean one thing here and another there |
| | `..` exclusive in an expression, inclusive in a pattern | Both forms parse in both places and mean different things; the compiler cannot help a reader hold the rule (D13) |
| | Keeping `..=` beside an inclusive `..` | Two spellings of one range, the defect [ADR-140](adr-140.md) removes (D14) |
| | `..<` in a pattern | A pattern stays one shape; the end is moved instead (D13) |
| | Migrating over several changes | The old spelling keeps parsing and changes meaning, so the corpus would mean something nobody wrote in between (D15) |
| The catch-all arm | `_`, as before | Nothing arrives at that arm, so the ignore pattern's character says the wrong thing; two spellings would be [ADR-140](adr-140.md)'s state again (D16) |
| | A new word | `else` is reserved and already means *the branch taken when nothing before it matched* (D18) |
| Coverage | Leaving it to `rustc` | The reader gets the backend's words on a Nikaia line, Part III C.1's class (D19) |
| | Refusing where the type is unknown | A refusal on a guess is a correct program refused, C.4's worse mistake (D21) |
| An arm's bindings | `match &s` | Every binding a reference, numbers too: `r > 0` compares `&i64` with `i64`, and the arms need a `*` the source does not write |
| | `match s.clone()` | A copy the program did not write ([ADR-282](adr-282.md) D7) |

The number that decided: no `.nika` file in `examples/`, `tests/` or
`crates/nikaia-std/` wrote a bare `_` or a `..=` range, which is what made D7 and
D14 free.

## 4. Decision

### D1 — A `let` takes one name, or a flat tuple of names — not a pattern language.

```nika
let (user, rights, prefs) = overlap { … }          // Part I 8.1.2
let (tx, rx) = channel::bounded(100)               // Part II 12.5
```

What the two sites need is taking apart a tuple whose arity is known; `match`
is where patterns are.

### D2 — One form of `let`, read by every reader of the tree; an analysis that cannot answer for several names declines.

A `let` holds a list of names, so every walk of the tree has to say what it does
with several. The checker binds each name to the part at its index, or to `?`;
the emitter writes Rust's tuple pattern; `views` marks every name a carrier.
Three decline, each on the safe side: `contracts::order` goes opaque rather than
reorder a statement binding several names, `contracts::sharing` records no
handle so each part stays at [ADR-037](adr-037.md) D6's atomic floor, and `dsl`
skips, because a deferred block is one value.

### D3 — A tuple's width is not compared with the names.

A value whose type this compiler cannot see is `?`, and refusing a destructure
of one would refuse a correct program ([Part III C.4](../30-nikaia-tooling.md)).
The day a tuple's width is known for certain is the day to refuse it here.

### D4 — A written type on a destructuring `let` is refused, `NK1136`.

`let (a, b): T = …` cannot say which name `T` is about; refused rather than
ignored.

### D5 — A nested tuple at a `let` is refused with a sentence that names the shape.

It does not parse, and the parse error carries a note saying that the shape is
what is missing, recognised from the rendering as in [ADR-279](adr-279.md) D2.

### D6 — `_` is the ignore pattern, and it stands where a name would be bound.

```nika
let (name, _) = pair()                      // a position of a destructured tuple
fn handle(event: Event, _: Context) { … }   // a parameter a shape dictates
xs.map fn(_, value) { value * 2 }           // a lambda's argument
match point { (0, _) => "on the axis", else => "off it" }   // a part of a pattern
```

`_` means *ignore a value that arrived* — neither bind it nor use it — and is
not called a wildcard. It is not a name: `_count`, `_0` and the `_000` of
`1_000` still are. Two `_` in one list are fine, and a parameter written `_`
still carries its type. The whole `match` arm is **not** one of its positions:
that arm is `else` (D16).

### D7 — `let _ = expr` is refused, `NK1144`, and `_` is never a value.

A call made for its effect is written as the call; a resource is closed by name
or ends with its scope (Part I 6.4). `x + _` does not parse.

### D8 — What `_` ignores is not moved, and a temporary it belonged to ends with the statement.

`let (a, _) = place` binds `a` and nothing else, so [ADR-094](adr-094.md) D4's
view rule holds: where `a` is only read, the place is not moved.

### D9 — `_` lowers to Rust's own `_`, so no binding exists below to warn about.

An ignored parameter is `_: Context` in the ledger's signature column, and its
`keeps` answer is never *kept*, so a caller lends it.

### D10 — `match` takes six more shapes: a tuple, an or-pattern, a range, a guard, a nested pattern, and `..` for a struct's rest.

```nika
match point {
    (0, 0) => "origin",                       // a tuple
    (0, y) | (y, 0) => "on an axis",          // an or-pattern
    (x, y) if x == y => "diagonal",           // a guard
    else => "elsewhere",
}

match code {
    200..299 => "ok",                          // a range, inclusive at both ends
    else => "other",
}

match event {
    Event::Click(Point { x, .. }) => x,         // nested, and `..` for the rest
    else => 0,
}
```

A tuple pattern's parts are patterns, so nesting is recursion. Every
alternative of an or-pattern binds the same set of names, `NK1155`, because the
arm's body does not know which one matched. The guard stands on the arm, not on
an alternative.

### D11 — A guard is `if`.

### D12 — `..` in a pattern is inclusive at both ends.

`200..299` matches `200` through `299`: a pattern is a set of values, with no
counting to `n` in it.

### D13 — So `..` is inclusive everywhere, and the exclusive range is `..<` — in a `for`, a slice and anywhere else, never in a pattern.

`for i in 0..<n` stops at `n - 1`. One meaning per spelling, after Kotlin and
Swift. A pattern that wants *up to, not including* moves its end: `200..298`.

### D14 — `..=` is refused, naming `0..n`.

`..` says what `..=` said; keeping it would be two spellings of one range.

### D15 — The migration of every range is one change, with the pages and the corpus in it.

Every `a..b` that meant the exclusive range became `a..<b` at once, because the
old spelling keeps parsing and changes meaning.

### D16 — A `match`'s catch-all arm is `else`, and `_` in that position is refused, `NK1150`.

```nika
match code {
    200 => "ok",
    404 => "not found",
    else => "other",
}
```

The message names the replacement.

### D17 — `_` keeps every other position: a tuple's, a parameter's, and a part inside a pattern.

These are the positions where a value did arrive (D6).

### D18 — `else` costs no word, and lowers to Rust's `_`.

It is reserved already and already reads as *the branch taken when nothing
before it matched* ([ADR-132](adr-132.md)).

### D19 — A `match` covers every case, and the refusal is this compiler's, `NK1151`.

A `match` over an **enum** is complete when every variant is named, and needs
no `else`; an or-pattern covers one case per variant it names. Over anything
else it needs an `else` (or a bare name, D20), because the set is not
enumerable in arms — `bool` is written out as the case that is neither: `true`
and `false` are a complete `match`. A **guarded arm covers nothing**, since the
values its guard turns away reach the arms below. `NK1151` names what is
missing: the variants, or `else`.

```nika
match op {
    Op::Plus  => a + b,
    Op::Times => a * b,       // complete: the enum has two variants
}
```

### D20 — A bare name is a catch-all, and covers.

`other => …` binds and matches anything, read by the same rule as `else`.

### D21 — Where the scrutinee's type is not known, nothing is claimed.

The backend's answer stands until the type is known
([Part III C.4](../30-nikaia-tooling.md)). This is the one place the rule is
weaker than it reads.

### D22 — Over a place the function owns, an arm's bindings are typed from the variant.

A name, or a field of one, that is not itself a view: a positional variant's
parts in order, a variant with named fields by name, a library's variants from
its ledger entry. A temporary and a view's parts are unchanged. A binding the
variant does not type — inside a nested pattern or an or-pattern — stays as it
was.

### D23 — A part that does not copy and that the arm only reads is lent, so the place is whole after the `match`.

It is `ref n` below. The arm **keeps** the part — and takes it — where it hands
it to something that keeps it (a `push`, a field, a rename, a callee whose
`keeps` says so, [ADR-293](adr-293.md)), calls a method on it that changes or
takes it, assigns to it, or returns it or hands it back as the arm's value. A
number, a `bool` and a `char` are copied as before.

### D24 — The typing is the checker's everywhere it reaches.

A method on a bound part resolves, so what it pauses, fails with and touches is
counted where it was *unknown*.

## 5. Consequences

* Part I 8.1.2's line is a program; a `let` over a tuple reads the parts by
  name instead of `r.0`.
* A reader who sees `_` knows a value arrived and was ignored on purpose; one
  who writes `let _ = f()` is told to say what they meant. A lambda handed to a
  two-argument function type can ignore one without inventing a name.
* `..` has one meaning, at the cost of a character on the exclusive range,
  which is the form written most.
* `match` and `if` say *otherwise* with one word, and `_` has one reading.
* An `enum` that gains a variant makes every `match` over it without an `else`
  a refusal **here**, across a package boundary too, since the ledger carries
  the variants ([ADR-203](adr-203.md)). The cost is one walk per `match`.
* A `match` over a name that only reads leaves the name usable; a part kept is
  taken, as any hand-over is.
* **What it costs:** a list of names on `let` read by every walk; the ignore
  pattern in four positions; the pattern rules, the binding-set rule and the
  range spelling; the refusals `NK1136`, `NK1144`, `NK1150`, `NK1151`,
  `NK1155` and the `..=` and `..<`-in-a-pattern refusals.

## 6. What this does not decide

* **A type on one part of a destructuring `let`** (`let (a: i64, b) = …`):
  written nowhere, and a decision when it is.
* **What `contracts::order` and `contracts::sharing` decline** (D2): deliberate
  holes on the safe side, closed by carrying several names, not by a new rule.
* **`_name`, bound but deliberately unused.**
* **A binding with `@`** (`n @ 1..5`), a seventh shape that waits for a program.
* **An exclusive range in a pattern** at all, rather than its spelling.
* **Ranges as coverage**: whether a set of ranges covers an integer is
  arithmetic not asked for; an `else` covers meanwhile.
* **A nested pattern's completeness**, the same question one level down;
  [ADR-246](adr-246.md) decides what reaches through a boxed part.
* **Whether an unreachable arm is refused**, the mirror of D19.
* **`else` with a guard** (`else if x > 0`), which nobody writes and a guarded
  pattern covers.
